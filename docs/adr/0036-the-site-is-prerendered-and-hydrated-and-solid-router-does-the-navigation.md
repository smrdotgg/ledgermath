# The site is prerendered and hydrated, and Solid Router does the navigation

Until this change, https://ledgermath.com was static HTML and nothing else: each page rendered once at build time, no JavaScript file served, every link an ordinary navigation. Going from the home page to `/docs/` took what felt to the maintainer like 50 to 100 ms, and he found that unacceptable: "I'd rather not have the project if the navigation is not instant." He wants every page there is and every page there will be (the documentation, about thirty pages, comes next, and the console after it) to "act like a single-page application that's already been pre-rendered". Two ways were proposed and turned down (below). His decision, on 2026-11-26: "just use whatever the official Solid 2.0 thing is", which is Solid Router. He also wants it simple and ordinary, and the first load as it is. This records how it was built. `site/src/app.tsx`, `site/src/entry-client.tsx`, `site/src/entry-server.tsx`, `site/src/Document.tsx` and `site/scripts/build.ts` hold it; the README ("The website") says how it reads.

## The decisions

1. **Each page is still rendered to complete HTML at build time, and the browser hydrates it as one Solid application.** The build makes two bundles with Vite and Solid's plugin (`ssr: true`): the server's renders each page once with `renderToString`, and the browser's is one script, `assets/app-<hash>.js`, that each page loads as a module from its `<head>`. A module script runs once the HTML is parsed, but it starts `hydrate()`, which takes over the body without rendering it again, only once the browser reports the page's first contentful paint (`src/entry-client.tsx`). Hydration takes the main thread for its whole length, tens of milliseconds on a phone, and the review of #105 found that started at once it put the first frame off (Chromium with its CPU slowed four times: a median of 256 ms against `main`'s 152); after the paint, the first frame comes as before, and `check-browser` holds the order on every page load (the mark `hydrate` after the paint entry). A browser without Paint Timing (or without `PerformanceObserver`) reports no paint, so there the script waits for what the page's text waits for, the body being shown (the inline script hides it, by a class on `<html>`, from before the body is read until the face the stylesheet sets is ready; if the face fails, or has not come 3 s after the first of the site's stylesheets loaded, it shows the body with its text in a fallback font), and then for two animation frames, the second asked for inside the first: a callback of the second runs only once the first, which shows the text, has been painted. `check-browser` holds that too, with Paint Timing hidden from the page and the font made 300 ms late so that the paint comes after the script has run: the mark `hydrate` comes after the frame's paint time (`paintTime`). (On 2026-11-28 the inline script was found never to hide the page on a first visit: it ran before the stylesheet's `<link>`, so no `@font-face` was known yet and `document.fonts` answered that the font was ready. It now hides the page at once and, once the stylesheet has loaded, waits for the face the stylesheet sets; a face that fails, or has not come 3 s after the first of the site's stylesheets loaded, is replaced by a fallback font in the frame that shows the page. Showing the page takes the class away first, so that nothing that throws can leave the page hidden. The browser's entry waits for the body being shown alone, no longer for the font as well, so that a font that never answers no longer keeps the page from being taken over, and takes that path too where `PerformanceObserver` is missing, where it threw before.) The browser puts that frame on the screen a little later, from its compositor, which the main thread being busy with hydration does not hold up. The price is a longer wait after the first paint before a click is the router's (below). The document around the body (the `<head>`, the font preloads, the inline script for the flags and the font) is the build's and is never hydrated: `Document.tsx` wraps it in `<NoHydration>` and the application in `<Hydration>`, which is what `hydrate()`'s own documentation prescribes when the server renders a whole document and the client hydrates part of it.

2. **Navigation inside the site is Solid Router's** (`@solidjs/router` 2.0.1, which requires `solid-js` and `@solidjs/web` 2, as the site has; SolidStart still requires Solid 1, so it is the router with the site's own build). Links are plain `<a href>`; the router intercepts a click on one by delegation and renders the page in place, pushes the address, and scrolls to the top or to the `#…` target. It marks the links to the page on screen with `aria-current="page"`, in the built HTML too. Back and forward restore the scroll position by the browser's own restoration, as for any page: the router's, on by default, is turned off (`scrollRestoration: false`, an option it documents), because it saves an entry's position only from a scroll event and restores nothing for an entry that never had one. Going back to a page the reader never scrolled then left it wherever the page after it had been scrolled, and back after the browser's own jump to `#numbers` kept the jump's position in Firefox and WebKit. A page here renders in the same task as its address changes, so the browser's restoration finds it: in Chromium, Firefox and WebKit every case of the browser checks and the scratch probes came back where it was left. `check-browser` holds it, with a page that was never scrolled among them. It leaves to the browser the links to another origin, those with `target`, `download` or `rel="external"`, and clicks with a modifier key or another button than the first. The routes are the pages of `src/pages.text.ts`, each at its address and at its file's (`/docs`, `/docs/` and `/docs/index.html`, which the host all serves).

   The site gives `target="_self"` to its links that are not page changes, the router's own way to leave a link to the browser: a file that is not a page (`third-party-notices.txt`; the documentation's `.md` files and `llms.txt` to come) and a place on the page on screen (the header's "Numbers" on the home page, `/#numbers`, which is the browser's jump there and a page change everywhere else, `/?napkin` included). The browser's jump moves the reader and the keyboard focus to the place; the router's would only scroll. `bun run check` fails on a link of either kind without it (`scripts/check-output.ts`).

   Four things a page load gives and a router does not, where Solid has no answer of its own, are done in the root layout of `app.tsx` in the plainest way that works. After a change of the path or the query, the keyboard focus goes where a page load would put it, on the element the address's `#fragment` names or else at the top (`<body>`), so that Tab goes on from there (after "Numbers" from `/docs/`, into the table), and a screen reader is told the new page's title through a polite live region, as SvelteKit does. A link to the address already on screen, which the router leaves as it is, starts the page again at its top (or its fragment), with the focus there and the title announced, as a document navigation would; and a link to the same page at another fragment or none (LedgerMath, `/`, from `/#numbers`), which the router takes without a change of path, moves the focus as a document navigation would too, to the place it names or else the top, so that it is not left on the link. A fragment that does not decode (`/#%`, a `%` not followed by two hex digits) names no element, as an id that is not on the page names none, and the focus goes to the top: nothing read from the address throws inside a navigation, where an uncaught error stopped every navigation after it. The router's own scroll to a link's fragment decodes it without that care, so `bun run check` fails on a link whose fragment does not decode. The page's feature flags follow its address, by the rule of the inline script. And an address no route knows (a link that should have had `target`) is handed to the browser with `location.assign`, so the host answers for it instead of the application showing an empty page. The last two links are seen in `useBeforeLeave`, which the router calls before every navigation of its own.

3. **Everything a page shows is in the one script, so a click fetches nothing.** The script holds every page's code and the figures the pages were rendered from: the build takes what the pages render from the tree (`pageData` in `src/data`, plain JSON, about 7 KB compressed) and compiles the same JSON into both bundles (Vite's `define`), so the page the browser renders after a click is the page the build wrote. With nothing left to fetch, no preloading is configured: the router's preload strategies load a route's lazy code and run its preload functions, and the site has neither. The script was 44.8 KB compressed when this was built (Solid, the router and the pages about 38 KB, the figures 7 KB); `scripts/check-output.ts` holds it under 60 KB.

   **When the documentation and the console come.** While the script stays under its budget, a new page is a new route in the same script. Past it, the documentation becomes a lazy route subtree (`children: () => import("./docs/routes")`, one chunk for all of it) and the console a `lazy()` component, and the router preloads them with `eagerPreload({ all: true })`, which loads every link's code once the first page has loaded and the browser is idle, links mounted later included, and with `intentPreload()` for a link clicked before that: it preloads when the pointer rests on a link for 20 ms, when the link takes the focus, or when a touch starts on it. On a touch screen there is no resting pointer, and a touch comes some tens of milliseconds before its click, which a small chunk from a nearby edge can meet and a slow connection cannot; the eager strategy is what makes the click free there, once the browser has been idle. `viewportPreload`, for links that stay in view, and `tapPreload`, on the pointer going down, are the router's other two. A chunk the browser has not loaded yet when the click comes is fetched then, and the old page stays until it arrives (the router holds the navigation).

   A documentation page is Markdown rendered to HTML at build time (#64, decision 9), so in the application it is a route whose component holds that page's HTML, made by the build from the Markdown files; its links to other pages of the documentation are plain links the router takes, its links to its own headings and to the `.md` files carry `target="_self"`, and the checks hold all of that as for any page. The console is a route of the same application whose heavy code (its tables, its charts, its reading of the API) is in a lazy component of its own, so the other pages never carry it; it reads `https://api.ledgermath.com` when it renders, and shows its own wait for the data, which is the console's business, not the navigation's.

4. **Every page works without JavaScript**, as ordinary links between complete pages: what is shown is in the HTML, and the checks hold that as before (`check-output`'s fixed words outside any script, `check-browser`'s lines with a figure). Before the script has run, a click is an ordinary navigation too. This revises #64's decision 5, "A console … It is the one page that needs JavaScript": every page now loads JavaScript, for its navigation; the console is still the one page whose content will need it.

5. **A page's `<title>` and description are Solid's head registry's** (`useHead`, in `@solidjs/web` 2): the server's render writes them into the page's `<head>`, and in the browser they change with the page.

6. **What a long-open tab shows.** The script holds the figures of the build that wrote it, so a tab left open across the six-hourly rebuilds shows the figures it loaded, on every page, until the reader loads a page again; the "Latest runs" dates on the home page say how old they are. Nothing is fetched after the first load, so a deploy, which replaces every file, never leaves an open tab asking for one that is gone.

## Rejected

- **A script of our own that fetches the next page's HTML and swaps it in.** Turned down by the maintainer as "too artisanal": it is navigation code of our own to keep, where the framework has an answer.
- **The browser's speculation rules** (prefetching or prerendering the next page). Turned down because not every browser has them: Chromium does; Firefox and Safari do not prerender. A prerendered page is still a new document, and a page not yet prerendered is an ordinary navigation.
- **The figures as a JSON file fetched by the page.** A click would need a request unless the file were preloaded, and on a touch screen that cannot be promised.
- **Splitting the script by route now.** With two pages there is nothing to gain; it is decision 3's answer for later.

## Measured

On 2026-11-26, on a 2-vCPU cloud machine (an Intel Xeon at 2.9 GHz, headless, no GPU), with `site/scripts/measure-navigation.ts`, 30 clicks per browser, alternating between `/` and `/docs/`, on the built site served locally and on this change's Vercel preview: no click made a request or loaded a document. From the click to the next frame (medians, then the slowest):

| | Chromium | Firefox | WebKit |
|---|---|---|---|
| to `/docs/`, local | 14 ms, 15 | 6 ms, 13 | 14 ms, 18 |
| to `/docs/`, preview | 15 ms, 136 (one click; the next slowest 18) | 7 ms, 10 | 13 ms, 24 |
| to `/`, local | 17 ms, 27 | 26 ms, 45 | 21 ms, 35 |
| to `/`, preview | 17 ms, 24 | 28 ms, 44 | 28 ms, 43 |

The site workflow's runner, in Chromium: 13 ms to `/docs/`, 15 to `/`. A click to `/`, whose table is most of the site's markup (about 420 elements, with 85 figures formatted and long drawn paths), costs more than a frame on that machine in Firefox and WebKit: it is the home page being built and laid out. With Chromium's CPU slowed four times, as a slower phone would be: 24 ms to `/docs/` (at most 79) and 90 ms to `/` (at most 133). The same clicks as ordinary navigations to `https://ledgermath.com`, the site before this change, took 55 to 97 ms (medians, by browser and direction) to the new page's first paint, up to 198 ms, with three requests each; with the CPU slowed four times, 111 and 120 ms, up to 205.

On 2026-11-27, after the review's changes and with the home page of #106 (the strip chart beside "Continuous Napkin Math"), measured locally against `main` as it then was, built from the same tree, the clicks to `/` were 16.5 ms in Chromium (at most 16.8), 29 in Firefox (37) and 23 in WebKit (46), and 55 ms with Chromium's CPU slowed four times (81); to `/docs/` 15, 8 and 14 ms, and 17 slowed (40). No click made a request.

**The first load.** It shows what it did and transfers about 45 KB more, the script, which the browser fetches beside the stylesheet and the font. On 2026-11-27, cold loads of `/` taking turns with `main`'s (30 each in Chromium, 20 in Firefox and WebKit, the medians, then the 90th percentiles):

| first contentful paint | `main` | this change |
|---|---|---|
| Chromium | 68 ms, 96 | 72 ms, 84 |
| Chromium, CPU slowed four times | 140 ms, 152 | 152 ms, 168 |
| Firefox | 58 ms, 124 | 68 ms, 106 |
| WebKit | 41 ms, 83 | 48 ms, 60 |

Before hydration waited for the paint, the same loads slowed four times gave 256 ms against `main`'s 152. What is left, a few milliseconds at the median and within the spread, is the larger HTML (Solid's hydration markers, about 4 ms of it slowed four times, measured with the script left out) and the script's own fetch and first run, which come before the first frame. The application took over a median of 25 ms after the first paint in Chromium (35 at the 90th percentile), 44 in Firefox, 54 in WebKit, and 92 ms with Chromium slowed four times (99), where before it had, as a rule, taken over before the first paint; until then a click is an ordinary navigation.

## What is not instant, or not as a page load would be

- **A click before the application has taken over** is an ordinary navigation: from the first paint until 25 to 55 ms after it on the measuring machine, about 90 ms on a phone-class CPU, and longer on a slow connection, which fetches the 45 KB script.
- **A click to the home page** takes one or two frames on a slow machine, and 55 to 90 ms on a phone-class CPU (above): the page is built in the browser, with no request. Making it cheaper means a lighter home page or keeping a page's elements alive between visits, which the router does not do; neither is attempted here. A click to `/docs/` stays within a frame or two even then.
