# A Benchmark may declare how an observed value matches its declared one, and that function is Method code

Each observed key in a Benchmark's declaration names the parameter it observes and may carry a `matches(declared, observed, env)` function, where `env` is the role's part of the Run's environment object; a key without one is matched by equality. This exists because some declared values have no literal in the output: `threads: "all"` is matched by the thread count equalling the box's online CPUs, which only a function over the environment can say. The function is pure, is pinned by the manifest commit every Run records, and is part of the comparison Method for that Benchmark's Runs, so changing it is a Method change under ADR-0012: CI re-judges every Run of the Benchmark and appends a Verdict where the answer moved. Equality alone was rejected because it cannot express the cases above, and a declarative vocabulary of our own was rejected because it would grow into a language. This does not reopen ADR-0020, which forbids functions in requirements: a requirement is hashed into the setup hash, rendered on the website, and matched by Annotation scopes, so it needs a spelling nobody has to execute, while a `matches` function is executed once per Run at ingest and its only product is the Verdict. The cost is that purity cannot be proven by CI, only exposed by a re-judge, and that the website can show the rule only as source.
