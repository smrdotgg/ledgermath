# The documentation is rendered from Markdown and served as Markdown, each page a chunk loaded ahead

LedgerMath's documentation is how an agent, or a person, learns what the data API's numbers mean (#64, decision 9: "Docs have one source. Written in Markdown in the repository; the build renders HTML pages, publishes each page's Markdown beside it and an index for agents"). By 2026-11-27 its content existed as Markdown: three hand-written pages (`site/content/docs/`), the start-here page (`site/content/docs/index.md`, #112), the API reference that `scripts/api-reference.ts` generates from the schemas and never keeps (#108), and each benchmark's README, written to be its page (#107). `https://ledgermath.com/docs/` was still a placeholder. This records how the pipeline that publishes it was built, and what was decided with the maintainer before it was: one source; every page also plain Markdown, at its address with `.md` added and at its address for `Accept: text/markdown`; `/llms.txt`; agents told where to look; "View as Markdown" and "Copy page"; long descriptions folded with `<details>`; and, above all, navigation that is instant on every page of the site ("I'd rather not have the project if the navigation is not instant", ADR-0036). `site/scripts/docs.ts`, `site/scripts/build.ts`, `site/src/app.tsx`, `site/src/docs/Page.tsx` and `site/deploy/vercel-config.ts` hold it; the README ("The website", "The documentation") says how it reads.

## The decisions

1. **One source, rendered at build time.** Each page is one Markdown file, and the build renders its HTML from it: the HTML and the Markdown the site serves cannot differ. The pages, by section (the order of the list of pages, of `/docs/`'s contents and of `llms.txt`): start here, `/docs/`, the start-here page followed by every other page with its description ("All pages"; before that file existed, the contents alone); the API reference, generated afresh at every build by running `scripts/api-reference.ts` into a directory of the build's own; a page per benchmark the schedule runs, from its README, in the home table's order; then the machines page (generated), the Methods, the prices, the glossary and any other hand-written page, at the address its path gives. The generator needs the repository's packages, so the `site` workflow's build job installs them now, as both production deploys already did.

2. **The parser is `marked`**, 18.2.0, pinned exactly as `site/package.json` pins everything, a development dependency: it runs in the build and nothing of it is served (a build test looks for it in every script). It is maintained (a release most weeks in 2026), has no dependency of its own, renders GitHub-flavoured Markdown (tables, autolinks, strikethrough, raw HTML for `<details>`), and gives the tokens, so the build rewrites links and names headings on them rather than on the HTML. `markdown-it` follows CommonMark more closely but brings five packages of its own for GFM's autolinks; `micromark` with its GFM extensions is the most exact and brings dozens; Bun's built-in `Bun.markdown` costs no package, but its output is the runtime's, changing with Bun's version unannounced, and it gives no tokens to rewrite. The content is plain enough that `marked`'s few departures from CommonMark do not show.

3. **The content's contract is held by the build.** No front matter, no image, no HTML but `<details>` and `<summary>`, the first line `# Title`, the first block after it a paragraph (the description: the page's `<meta>`, its line in `/docs/` and in `llms.txt`). A source that breaks it fails the build, naming the file and why, as does every link with no target: a `/docs/…` address that is no page, a `#…` that is no heading of its page, a file of the repository the checkout lacks, an address outside the site that the site does not link to. `scripts/lib/docs-addresses.ts` is held to the pages both ways. Links become the site's own: `/docs/…` and `https://ledgermath.com/docs/…` are the router's; a `#…` on its own page carries `target="_self"` (the browser's jump, ADR-0036); a README's relative link to a file becomes the file's address on GitHub, on main, in the served Markdown too; links to the API stay. Headings take GitHub's anchors, which the generated pages link to. Since the content is not edited by the pipeline, a table whose header row starts empty (two in `http_get`'s README) is rendered with its first column as row headers, and one that is empty throughout with no header row, so that a screen reader can name every cell; and each table scrolls in a box of its own, named for its headings and numbered where two share them.

4. **Where a link may leave the site, restated.** Until now a link out had to be named whole in `OUTSIDE_LINKS`, a rule written before the repository was public "so no link goes to the source repository". The documentation links the repository's files (sources, schemas the API does not serve) and the API, so `bun run check` now passes a link under `https://api.ledgermath.com/`, under `https://github.com/smrdotgg/ledgermath/blob/main/` or `…/tree/main/` (`REPOSITORY_FILES`) to a file or directory the checkout has, or one of `OUTSIDE_LINKS` (Napkin Math's repository); nothing else.

5. **Every page is also Markdown.** At its address with `.md` added (`/docs/glossary.md`), or `index.md` in it for an address that ends in a slash (`/docs/index.md`, `/docs/api/index.md`), as llms.txt's convention (v2, checked on 2026-11-27 at <https://llmstxt.org>) has it; and at its own address when the request says `Accept: text/markdown` at full weight. Vercel serves the files as they are; the deploy's `config.json`, which `site/deploy/vercel-config.ts` writes from the built files, adds `Content-Type: text/markdown` to the Markdown, `Vary: Accept` to every answer at a page's address, and one route per page that answers `Accept: text/markdown` with its Markdown. One route per page, not the one rule the earlier experiment proved: with `index.md` for a slash address, only the files say which Markdown is a page's, and `/docs/api`, `/docs/api/` and `/docs/api/index.html` must all find `docs/api/index.md`. A page without its Markdown would answer an agent with 404, so the deploy refuses such a site, `bun run check` fails on it, and the live check after each production deploy asks for `/docs/` as Markdown. The home page has no Markdown: it is not a documentation page, and its figures in another form would need a check of their own (below, "Left out").

6. **`/llms.txt`**, generated from the page list: the site's name as the title, what LedgerMath is as a quote (the home page's description), where the numbers are, then each section's pages, each a link to its Markdown with its description. An index of the same pages, nothing of its own. Agents are told where to look: a comment at the top of every page, before `<html>`; `<link rel="describedby">` to `/llms.txt` on every page, as the convention asks; and on each documentation page `<link rel="alternate" type="text/markdown">` to its Markdown, through Solid's head registry, so that it follows the page after a click.

7. **The documentation's pages are routes of the one application**, under one layout, `/docs`, which stays while the reader goes from page to page (the header, the breadcrumb, the controls, the list of pages, the footer; `site/src/docs/Page.tsx`). Each page's body is a `lazy()` component whose module holds the page's HTML, which the build writes with every page's title and description (`virtual:ledgermath-docs`): a chunk of its own, rendered into an `<article>`'s `innerHTML`, which hydration leaves as the server wrote it. The server renders with every body loaded first and with the browser's build manifest (Solid's Vite plugin's `virtual:solid-manifest`, passed to `renderToString`), so that the page's `<head>` asks for its own chunk (`modulepreload`, at low priority) and hydration imports it before it takes the page over (Solid's own `_assets`). Solid's runtime, which the chunks import too, is a chunk of its own beside the application's script, and the `<head>` asks for it beside it. No navigation code of our own was added but one guard: a click to a page whose chunk this tab has not loaded yet loads it first, the page on screen staying, and, if it cannot be loaded (a deploy since the tab opened has replaced it, or the network is down), leaves the click to the browser, which loads the page whole; without it the router stopped on the failed import (`REACTIVITY_HALTED`), and no click worked after it.

8. **What is loaded ahead, and when.** The router's own preloading: `eagerPreload({ all: true })`, every link's chunk once the page has loaded and the browser is idle, links mounted later included; and `intentPreload()`, a link's chunk at once when the pointer rests on it for 20 ms, it takes the focus, or a touch starts on it. A documentation page lists every page, so once it has loaded, every chunk comes; the home page links 15 of them (its header's "Docs" and the benchmarks' names). `eagerPreload` skips a reader whose browser asks to save data (Save-Data, or a 2g connection); `intentPreload` does not, so such a reader loads what they point at or touch, and nothing else. ADR-0036 expected one chunk for the whole documentation, a lazy route subtree. It is a chunk per page instead: a reader who lands on a documentation page would otherwise wait for every page's HTML (181 KB compressed) before the application took over, where now it waits for its own (1.4 to 21 KB); a reader saving data loads only the pages they go toward; and a page's chunk changes only when that page does.

9. **Two controls on every documentation page.** "View as Markdown", a plain link to the `.md` with `target="_self"` (a file, which the router leaves to the browser); and "Copy page", which fetches the `.md` when pressed and puts it on the clipboard (a `ClipboardItem` holding the fetch where the browser allows it, which keeps the press's permission to write, else the text once it has come), says so in a status, and is hidden without JavaScript by the `scripting` media feature, so a page read without JavaScript shows only what works. The Markdown is fetched rather than carried in the chunk, which would double what is loaded ahead for a control seldom pressed.

10. **The look.** The site's header and footer, its colours in both schemes, its pixel type for headings and chrome; the body of a page, which is long text, tables and code, in the reader's own system fonts (`system-ui`, `ui-monospace`), which read easily at length and cost no file; links in running text underlined, so that they stand apart from it without colour. On a wide screen the list of pages stands to the left of the page and stays in view; on a narrow one it follows the page, and "Docs" in the breadcrumb leads to `/docs/`, which lists every page too. The page comes first in the document, so the keyboard and a screen reader meet it before the list.

11. **The API's own pointer.** `v1/index.json`'s `docs`, which named the README's section on GitHub until the documentation had pages, names `https://ledgermath.com/docs/api/` (`DEFAULT_DOCS`). It keeps the schema's pattern, the publish gate does not compare it (the table of contents changes with every update; `tests/api-gate.test.ts` passes), and the API's words now name nothing of the repository: the one exception `tests/api-words.test.ts` held is gone.

12. **The checks.** `site.yml` runs on a change to anything the site is built from (`site/`, `benchmarks/`, `schemas/`, `scripts/`, `docs/`, `schedule.json`, the root's packages), so a broken link fails the pull request, not the next rebuild of production; `site/deploy/fresh.ts` reads the same list. `bun run check` reads the documentation back from the built `llms.txt` and holds each page to its title and description, to its Markdown and to its `<head>`'s alternate, and holds the budgets below. `bun run check:browser` loads every documentation page (four of them in both schemes, the rest in light) for the checks it made of the two pages there were, goes round a route of clicks between documentation pages and to and from the home page, and checks the documentation's own: the keyboard reaches the breadcrumb, both controls and the list of pages; "Copy page" copies the Markdown byte for byte; a link to a heading of another page lands on it, focused; a page whose chunk is gone loads whole; without JavaScript only "View as Markdown" shows. Its job's time limit is 20 minutes, from 10.

## Budgets, restated

`bun run check` held two weights: a page with everything it loads, under 300,000 bytes compressed, and the JavaScript it loads, under 60,000. With chunks, "everything it loads" means two things, so there are four:

| Budget | Before | Now | Measured on 2026-11-27 |
|---|---|---|---|
| A page's first load: the page and what it loads to show itself and be taken over (the stylesheet, both fonts as the check counts them, the application, a documentation page's own chunk) | 300,000 | 300,000 | 118,914 (home; 113 KB before) to 159,011 (`http_get`'s page) |
| The application: its script and what that imports, every page alike | 60,000 (the JavaScript a page loads) | 60,000 | 54,712 (44,800 before the documentation) |
| One documentation page's chunk | none | 40,000 | 1,442 (machines) to 21,409 (`http_get`) |
| Every chunk the application may load ahead, together | none | 250,000 | 181,164 for 28 pages |

The browser check weighed the bytes a page transferred under 300,000; it now weighs the first load the same way and the chunks loaded ahead apart, under 250,000. Past the last budget, preload fewer pages ahead (`viewportPreload` for links in view, or intent alone) rather than raise it.

## Rejected

- **One chunk for the whole documentation** (ADR-0036's plan): above, decision 8.
- **Each page's Markdown in its chunk**, so that "Copy page" needs no request: it doubles what is loaded ahead.
- **Rendering Markdown in the browser**: it would ship a parser and render on every visit what the build renders once.
- **A script of our own that fetches a page's HTML and swaps it in**: turned down already (ADR-0036) as navigation code of our own; the router's lazy routes and preloading do it.
- **One routing rule for every page** (the earlier experiment's): decision 5.

## What is not instant

- **A click before the application has taken over** is an ordinary navigation, as before (ADR-0036): from the first paint until 18 to 25 ms after it in Chromium, 65 to 96 ms with its CPU slowed four times, and longer on a slow connection. On a documentation page that wait includes the page's own chunk, which its `<head>` asks for beside the script, at low priority.
- **A long page on a slow phone.** A click builds the page's body from its HTML in the browser: on the machine above, the two longest pages, the Series file's reference and `http_get`'s, take about 20 to 26 ms, a frame or two; with the CPU slowed four times, 85 to 99 ms (at most 148), where the other pages take about 50. Keeping a page's parsed body between visits, or parsing it ahead in idle time, would cut that; neither is done here.
- **A click whose page has not been loaded ahead yet**: in the moment between a page's load and the browser's next idle period, or for a reader who asks to save data and has not pointed at or touched the link. The page on screen stays while the chunk (1.4 to 21 KB) is fetched, one round trip, and then changes in place. If it cannot be fetched (a deploy since the tab opened replaced it, or the network is down), the browser loads the page whole.
- **A click from the home page into the documentation** builds the documentation's layout and its list of every page as well as the page. With the CPU slowed four times it took 44 ms at the median, and one click of eight took 125 ms.

## Left out

- The home page as Markdown. Asked for with `Accept: text/markdown`, `/` answers its HTML (with no `Vary`), whose comment points to `/llms.txt`. A Markdown home page would hold its figures, which `check-figures` holds only in the HTML.
- A chunk's file name and the address of the module it was built from, which the application carries for each page (Solid's `lazy()` names its module), include a directory the build names at random, so the application's script differs from one build to the next even with the same sources; it did already, with the figures.
