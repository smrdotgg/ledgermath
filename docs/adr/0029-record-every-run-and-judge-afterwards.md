# Record every Run truthfully and completely, and judge afterwards

ADR-0001 to ADR-0028 record a design that was specified in detail before any of it was built. It tried to prove a Run comparable before the Run could count: a frozen manifest, CPU profiles, declared values checked against observed ones at ingest, a controller over SSH, Checkpoints, and transition runs as merge gates. The build plan of 2026-11-09 (#36) replaced it with one rule: **record every Run truthfully and completely, and judge afterwards.** Each Run is a true and complete record, and comparability is worked out afterwards, by a versioned Method, from what the Runs say. The case that decides between the two is `m5.large`, which lands on one of two Intel generations. The specified design bound one CPU profile and terminated a box that landed on the other. Here the benchmark runs on whatever lands, the Run carries the dump that says which processor it was, and a Method splits the Series by processor; this also shows how often each processor turns up. The first Runs were written on 2026-11-10. This ADR records the decision as built: which earlier ADRs stand, which terms of `CONTEXT.md` are in force, and the decisions made while building that shape the Run record. `CONTEXT.md` and the earlier ADRs stay as written, as the plan says.

## The working rules

These are the plan's five rules, in its own words:

1. **A Run is self-describing.** It carries the params it was given, the provider's own words for where it ran, the hash of the binary that ran, and the box's environment dumps. A Series is a query over Runs. A boundary is any recorded fact that differs between two consecutive Runs.
2. **Only the Run record is forever.** Scripts, Methods, the site and the schedule can be rewritten without touching a stored Run. Rigor, and ADRs, go to the Run record.
3. **Collect generously, interpret later.** A dump that was not taken can never be recovered. A wrong interpretation is fixed by a new Method version.
4. **A check earns its place from data.** Any gate from the spec can be added later, as a Method over the same Runs, when the Runs show the problem happens.
5. **The box is stock.** A benchmark runs as an ordinary process on a default image, with nothing wrapped around it. A changed setting is run only when that setting is what is being measured, and the Run records it.

## Decisions made while building

These shape the Run record or cannot be changed cheaply later. The detail is where each one points.

1. **A Run names its stdout blob and holds no copy of its events.** The stdout blob is the only source of a Run's events. Runs written before step 5 keep their `events` and are never edited, and every reader reads the blob for every Run (`readStream`, `methods/run.ts`). This is decision 4 of #43, agreed on 2026-11-11, and it replaces decision 1 of #37.
2. **Dumps and other evidence are blobs named by hash.** Every `sha256:<hex>` in a Run names `blobs/sha256/<hex>` in the Runs bucket: the binary, the source archive, the runner's file list, the resolved flags, stdout, stderr, and each dump. A dump is an index of sections, and a section that does not change is stored once. A Run is uploaded only after every blob it names is in the bucket (#37, decision 2; `README.md`).
3. **An execution that never started has no Run.** A failed build, or a binary that could not be started, is recorded in the boot summary (`boots/<yyyy>/<mm>/<dd>/<boot>.json`), which accounts for every execution the schedule names (#37; `README.md`).
4. **Static linking, with `memory_read`'s dynamic build run beside it for a week.** Each boot builds `memory_read` both ways and runs both, taking turns at going first. Every other benchmark is built static only (#37, decision 6; #42, decision 2). The comparison is check 5 on #38, expected on 2026-11-17, and its outcome is not yet known. If the two builds give the same numbers, the dynamic build is dropped. If not, the size of the difference is written on #37 and the choice is made again with the numbers.
5. **The binary is built on the box, and its bytes are kept.** Each boot builds from the deployed commit's source archive with the image's own gcc and `-march=native`. It records the compiler, the command and the resolved flags, and keeps the bytes that ran as `binary.blob` (#37). What is established, as of 2026-11-11 17:00 UTC (check 3 on #38, first answer): each of the 70 combinations of benchmark, build and instance type that had run had exactly one binary hash across its boots, with three boots over two days on `c6i.8xlarge`. `c6i.8xlarge`, `i4i.2xlarge` and `m5.large` built the same bytes, while `c8i.2xlarge` and `c8a.2xlarge` each built their own, as `-march=native` does on another processor. Still to be confirmed: the same over a full day of scheduled boots on all five types, due after 00:30 UTC on 2026-11-13. Until then a Method splits on the binary's hash. If the builds turn out not to be identical, a Series is split on source commit, compiler and flags instead, and the hash is only recorded (#36, "What could prove this wrong"; #39, decision 6).
6. **The image is pinned by ID.** The `-runs` stage launches `ami-03499a87bbb39a09a` (Amazon Linux 2023.12.20260710.0), and the image changes only when that line changes (#37). AWS marked the image deprecated on 2026-10-08. It still launches by ID, and nothing has been decided for the case where AWS removes it.
7. **A Series is a query over Runs, split by a Method on recorded facts.** `series` v1 keys a Series on benchmark, params, build, instance type and zone ID. It groups the Series' Runs by the binary, the runner, the sample count, the image, and the dump sections `cpuid`, `lscpu`, `sys_cpu`, `kernel`, `process` and `packages`. Before comparing, it leaves out the values set anew at every boot: the hypervisor's TSC frequency in cpuid leaf `0x40000010`, `lscpu`'s BogoMIPS, and the host name in `uname -a`. It never splits on `source_commit` or `source`, and it lists every dump section that changed between consecutive Runs, whether split on or not (#39; `methods/README.md`).
8. **The box prepares its instance-store disk and records everything it did.** `runner/provision.py` makes a default XFS file system on an empty instance-store disk and writes the disk Fixtures. Every command, exit code, output and timing goes to the dump section `provision`, and nothing else on the box is changed (#42, decision 4). The disk a parameter set means is one of its params, so the two disks are two Series (#42, decision 3).
9. **A Service's keys are never written.** The short-lived keys a Service benchmark receives exist only in the runner's memory and in that execution's environment. No Run, blob, dump, boot summary, log or command line holds them, and the Run lists them by name in `service.secret_inputs` (#43; `README.md`, "The Service benchmarks").
10. **An error response's body is not kept.** The Run records the body's length, S3's `Code`, `Message`, `RequestId` and `HostId`, and the names of the body's elements. It keeps neither the body nor its digest, because S3 repeats the session token or the key ID in some error bodies (#43; `benchmarks/http_get/README.md`).
11. **Prices are records like Runs.** Each day's price file, `prices/<yyyy>/<mm>/<dd>/aws.json`, goes into the Runs repository once and is never edited. It holds AWS's own records for what is measured, verbatim, and names each source by versioned URL, version, size and SHA-256. A price is cited as the file, the SKU and the rate code (#45, decisions 1 to 3).
12. **A citation of a derived number carries the Method's version and the moment its data ended.** A Series citation reads `[lm:series/<id>/<number>/<statistic>@v1,<moment>]`, where `<moment>` is the start of the Series' newest Run at the time. An answer can therefore be checked after more Runs arrive (#47; `README.md`, "The agent skill").

## The terms of `CONTEXT.md`, as built

| Term | Status | As built |
|---|---|---|
| Run | In force, with a difference | One execution of one benchmark binary with one parameter set on one box, written whether it succeeded or failed (`schemas/run.schema.json`). It holds the params and Service inputs it was given, and it names its stdout and stderr blobs instead of holding what the binary emitted. There is no Station, and an execution that never started has no Run. |
| Series | In force, with a difference | A query over Runs: in `series` v1, the Runs that share benchmark, params, build, instance type and zone ID, grouped by split facts. Failed Runs are shown and left out of every percentile. No Verdict or Annotation is involved. |
| Annotation | Not built | The plan replaces it with a dated notes file, which does not exist yet. |
| Verdict | Not built | Whether a Run counts is the decision of the Method that reads it. |
| Ledger | In force, with a difference | The Runs repository (Run files, boot summaries and price files, added and never edited) together with the bucket of blobs. It holds no Annotations, Verdicts or Build records, and it stays private until step 7 (#47). |
| Method | In force as defined | Two exist, each named and versioned: `series` v1 and `requests` v1 (`methods/README.md`). |
| Derivation | In force, with a difference | A Method's file holds one Derivation per Series, carrying all of that Series' numbers and naming the Method, its version, and every Run by id, path and sha256. A price is cited from its price file, not from a Derivation. |
| Benchmark | In force, with a difference | One directory, `benchmarks/<name>/`, holding the source, a `README.md` (what it measures, its params, its observed values, its own events) and a `Makefile`. It declares no roles and has no PRD there. It is built on the box per named build, and its bytes can differ by processor. |
| Variant | In force, with a difference | Called a parameter set: one entry of a benchmark's `params` in `schedule.json`. It has no name, it is not immutable, it requires nothing of the box, and the Run records it as `params`. |
| Role | Not built | A benchmark declares no roles. A Service benchmark names its Service in its schedule entry. |
| Target | In force, with a difference | An entry of `schedule.json`'s `targets`: an EC2 instance type, its zone, and its boot times. There is no Kind, identity schema or slug, and each Run records the provider's own words in `provider`. |
| Machine | In force as defined | The built docs call it the box. It boots AWS's stock Amazon Linux 2023 image, pinned by ID, fresh for every boot, and runs the binary as root. |
| Service | In force, with a difference | Named by a schedule entry (`"service": "s3_fixtures"`, the stage's private bucket of Fixtures, the only one so far) and recorded in the Run's `service`. It is not a target in `schedule.json`. |
| Kind | Not built | `provider.name` (`aws`) says whose words a Run's provider fields are. |
| Target Instance | Not built | Each Run names the instance it ran on by AWS's own identifier (`provider.instance_id`), but no Provisioner creates it for a Station. |
| Station | Not built | A Series is a query over Runs. The schedule is written in benchmarks, parameter sets and targets. |
| Visit | In force, with a difference | Called a boot: one fresh launch of one target, never a reboot of a kept box. During it the box runs the executions `schedule.json` names for its instance type, one Run each. The Runs of one boot share `boot`, and the boot summary accounts for every execution, including any that did not run. |
| Artifact | In force, with a difference | The bytes that ran, named by `binary.blob` and kept as a blob. They are built on the box, and the facts of the build (compiler, command, resolved flags, source) are in each Run, not in Build records. |
| Event | In force, with a difference | As defined; the contract is `docs/dev-log.md` section 2. A Run's events are the lines of its stdout blob. A Run also holds the params and Service inputs it was given, so events and observed facts are not all it holds. |
| Observed counterpart | In force, with a difference | Benchmarks report the observed counterparts of their params in `observed` events. Nothing requires every param to have one, and nothing compares the two when a Run is written. `scripts/check-disk-runs.ts` compares the disk benchmarks', as a check. |
| As-booted value | Not built | The box is stock: there are no state keys, and the dump records what was there. |
| Fixture | In force, with a difference | Made by `runner/provision.py` at every boot (the disk Fixtures) or by the `-runs` stage at deploy (the S3 objects), both from the pattern in `benchmarks/harness/c/lm_fixture.h`. No Provisioner makes them for a Station. |
| Provisioner | Not built | `runner/provision.py` prepares the box's disks and Fixtures at boot and records what it did. It declares no keys, establishes no state and creates no instances. |
| Manifest | Not built | `schedule.json`, freely edited, says what runs. The "runner manifest" that `scripts/check-runs.ts` checks is the list of runner files a Run's `runner` names, which is a different thing. |
| CPU profile | Not built | The Run records the compiler's resolution of its flags (`binary.resolved_flags`), and its dump records the processor. |
| Capture | In force, with a difference | Called the environment dump: taken raw and unmasked before and after every Run, as an index of sections each stored as a blob. Nothing is frozen per target, and nothing compares it when a Run is written. |
| Build record | Not built | See Artifact. |
| Archive | In force, with a difference | The Runs bucket's `blobs/sha256/<hex>`: content-addressed, versioned, and holding every blob a Run names. It has no index, Checkpoint or compliance copy, and it stays private until step 7. |
