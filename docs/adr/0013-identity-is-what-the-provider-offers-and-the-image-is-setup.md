# Identity is what the provider offers, and the image is setup

A Target's identity holds only the coordinates the provider's catalog names, in the provider's own words: the Kind, its location, and the product name within the Kind (an instance type, a storage class), and never the operating system, which the Kind's Provisioner pins to one exact image and bumps by pull request on a stated cadence. An operating system family in identity, as the first #13 resolution's example had, was rejected because the exact image is already pinned by the provisioner bundle inside the setup hash, a family code pins nothing on top of it, and a Series would end at every operating system generation instead of continuing with an explained boundary. Tracking the provider's latest image was rejected because a new image arrives about weekly and a boot image cannot be verified by alternation on bare metal, so every Machine Series would be cut into weekly unverified segments. The cost is that every bump is an annotated boundary, so bumps are quarterly; for side-by-side comparison an optional `image` field names one image family by the provider's public parameter path and pins that Target to the family for its life.
