# An error response is evidence, not a failed Run

Every response a Service Benchmark receives is an event, including a `503`, a `403`, a timeout, and a reset connection, each carrying the status, every header verbatim, the bytes received, and the body hash; the Run completes when the binary completes, and which samples count is a Method's decision, visible in the Derivation. Failing the Run on the first error was rejected because it discards the good samples and the evidence of the error together, and because the AWS request ids in the error's headers are exactly what a reader would take to the provider. The Verdict is untouched by an error as such, since it compares declared with observed; a Run in which no request succeeded still fails, because the Fixture's observed hash is then missing. The cost is that Methods must say what they did with errored samples, and that a Series can carry Runs whose samples are partly unusable.
