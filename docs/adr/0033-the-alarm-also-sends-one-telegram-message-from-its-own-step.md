# The alarm also sends one Telegram message, from its own step

ADR-0032 made the alarm issue the route by which stopped publishing reaches the maintainer, and the data API is about to be public. The maintainer said on 2026-11-23 that GitHub's own notifications (email, the phone app) land among many others and may not be seen promptly; Telegram is where the maintainer looks. This records how the alarm also reaches the maintainer there. `scripts/lib/telegram.ts` and `scripts/alarm.ts` (`pingText`, `pingSafely`) hold it; the README ("The alarm", "A Telegram message") says how it reads.

## The decisions

1. **Sent from inside the alarm, in the alarm's own step of the `runs` workflow.** Not by a workflow started by `issues` or `issue_comment` events: the alarm posts with the workflow's own `github.token`, and "events triggered by the `GITHUB_TOKEN` will not create a new workflow run", except `workflow_dispatch`, `repository_dispatch` and some `pull_request` events (GitHub's docs, "Triggering a workflow from a workflow", read on 2026-11-23). Not by a following step either: it would have to learn from the alarm what was posted (through `GITHUB_OUTPUT`, which the workflow's tests keep out of `runs.yml`, or a file), and to run after an alarm that failed, so its own condition and failure would be one more thing to hold. Inside the alarm, the facts are at hand, and the guarantees below are tested by running the alarm's script as the step runs it.

2. **When: every time the alarm writes to GitHub, and when it had something to post and it failed.** The issue opened, a comment because something changed, the all-clear comment, a drill; and a pass that failed after it tried to write, or failed (GitHub unreachable) with something stale, and the alarm then fails as before. A failed post is one of two things, and the message says which: **not made** (GitHub answered 400 to 499, its status kept even when its body is cut off; or GitHub could not be read; or the post was refused before it was sent), and the message says "this run could not post an update", which claims nothing of what the issue already says; or **unconfirmed** (GitHub did not confirm the write: no answer, a whole 5xx, or a 2xx cut short or not understood, so the post may be there), and the message says "GitHub did not confirm the write", true of every such case, never that the post was not made. Two independent verifications found earlier words false: "the issue does not say what follows" of a comment GitHub had recorded before it cut its answer short, and of an issue that already held the verdict when reading its comments failed; and "no whole answer came back" of a whole 503. The issue's address is in the message whenever the issue is known: noted as soon as the marked issue is found, before its comments are read, or from the one a comment went to, or the number an opening returned (`notingTracker`). The drill's post is judged the same way, starting from the issue the pass learned, so its own lookup failing does not lose it. A pass that writes nothing sends nothing; a pass that fails before it can tell whether it owed a post, with nothing stale, sends nothing either. One message per run, sent last, after every post, so one bounded wait covers it: a run that comments and drills sends one message saying both, and one whose drill alone fails says the comment was made and the drill's post was not, and exits 0.

3. **What it says: fixed words, the verdict's counts, two addresses.** Plain text, no `parse_mode`. Which kind of post, the number of stale watched Series of how many, whether the price files are stale, whether publishing is raised, whether the copy job failed, the issue's address (its number accepted only as a positive whole number) and the run's (`ACTIONS_RUN_URL` and a numeric `GITHUB_RUN_ID`, as ADR-0032 builds it). Nothing S3, the check's child or the environment said: the rule of ADR-0032, decision 6, applied to the message, so not even the API finding's state, only that it is raised. The message has at most two posts' lines and bounded numbers, so it is a few hundred characters, far under Telegram's 4,096, by construction; `pingSafely` refuses a longer one all the same.

4. **It never changes the alarm.** Sent after everything else; given up after 15 seconds (`SEND_BUDGET_MS`, the maintainer's own tool's timeout), with a backstop one second later for any `Messenger`, then at most two seconds for its line in the step summary. It never throws. Its outcome is one of a closed set (sent, no whole answer in time, no answer, an HTTP status, an answer not understood, not accepted); a message not sent is a warning annotation and a step-summary line in fixed words, never the request's address (it holds the token) and nothing of Telegram's answer but the status. No second try. The alarm's verdict, posts, marker and exit code are those of a run without Telegram, so a Telegram outage never fails the first job and never skips the `publish` job. With either secret unset (a fork, or never set), a notice and nothing else. A token not shaped like one (digits, a colon, letters, digits, `_` and `-`) is never put in an address. The request is made with `verbose: false`, so Bun never traces it: with `BUN_CONFIG_VERBOSE_FETCH` set (`1` or `curl`), Bun's trace writes a request's address and body to stderr before any of our handling runs, which printed both keys in the first version (found by the same verification). The alarm's own calls to GitHub are made with `verbose: false` too: in `curl` mode the trace printed their `Authorization` header, the workflow's token, as it does on `main`. The check of the API bucket runs in a child whose environment never holds `BUN_CONFIG_VERBOSE_FETCH` (`CHILD_ENVIRONMENT`), so its signed S3 request is not traced either. Of the answer, the reader returns a tagged result, so a body that reads `timeout` is an answer not understood, never a timeout.

5. **The secrets stay in one place.** `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` are referenced only in the alarm step's own `env` in `runs.yml`, which runs on its schedule and by hand, never for a pull request; no job- or workflow-level `env`, no other workflow, nothing that hands over every secret. The check's child does not get them (`CHILD_ENVIRONMENT`). A test reads every file under `.github` and fails on any other reference; it judges each job's `secrets` by its parsed value, so `secrets: "inherit"` and `secrets: 'inherit'` fail like `secrets: inherit` (the first version matched the spelling and let a quoted one through), and fixtures of every such case, a reference elsewhere and a `pull_request` trigger must each be rejected.

6. **Telegram is reached through `Messenger`, as GitHub through `IssueTracker`.** Tests use a fake `Messenger` and, for the real `TelegramBot`, a stand-in server; the script takes `--telegram-endpoint` for the stand-in and `--telegram-budget-ms` for a shorter wait than `SEND_BUDGET_MS` (never a longer one: it is refused), and the workflow passes neither (a test holds that). The tests exercise stalls with a short wait and assert the production value on its own, and time no process: the test runner's timeout guards against a hang. No new dependency: Bun's `fetch` with an abort timeout.

## What it does not catch

A run whose first job fails outright before the alarm runs, or a workflow that does not run at all, sends no message: GitHub's failed-run email is then the only word, as ADR-0032 says. That the message reaches the maintainer's phone is confirmed once by hand, with the drill (README, "Turning it on", step 0).
