# Publishing is watched by what the API bucket holds

ADR-0031 put the data API's tree into a private bucket from a `publish` job of its own, whose failure was a red job and GitHub's failed-run email, nothing more; turning the API on waits for a tested route by which a stale or failed publish reaches the maintainer (README, "Turning it on", step 0). This records the route. `scripts/lib/api-freshness.ts` and `scripts/alarm.ts` hold it; the README ("The alarm", "The data API's publishing") says how it reads.

## The decisions

1. **The existing alarm raises it, in its issue, by its rules.** The alarm already runs in every run's first job, opens one issue or comments on the open one, and writes only when what it reports changes. Publishing is one more thing it reports, with one more field in the state its posts carry (`stale_api`), and it says once, on the open issue, when the data API is published again.

2. **Judged by the bucket, never by a job's conclusion.** Publishing can stop many ways: the `publish` job fails, is skipped (its first job failed, or `API_BUCKET` was unset), is cancelled, never runs, or its preflight refuses the bucket. In every one, the table of contents, `v1/index.json`, is not written again. Reading the bucket catches them all with one rule; reading jobs would need a rule per way, and would miss the ways no job records.

3. **The evidence is `Last-Modified` of `v1/index.json`.** S3 sets it from its own clock as the object is written; no writer can. The upload writes that object only as its last act, after every phase (in the last phase when it changed, otherwise as the stamp of ADR-0031), so it moves on every upload of a new run that succeeds and on nothing else the workflow does. Rejected as evidence, and kept only as a lead in the alarm's words: the run in the object's metadata, which is whatever the uploader passed (an upload by hand can record any number, which is why the README has "A run recorded too high") and would need a call to GitHub to become a time; and the tree's own `newest_run_started_at`, which says when the newest Run started and so stands still when the boxes do, however well publishing works. `Last-Modified` moves without the workflow only when a person writes the object with their own credentials.

4. **Two scheduled runs in a row, each given an hour.** A scheduled run (00:00, 06:00, 12:00, 18:00, 22:40 UTC; a test holds the list to the workflow's crons) has missed when `v1/index.json` was last written before its scheduled time and an hour has passed since; two missed raise the alarm. The runs after the last publish are consecutive, so two missed are two in a row, and one late or failed run raises nothing. The hour is ten times what the runs took from 2026-11-11 to 2026-11-21 (2 to 5 minutes late, about a minute long, publish included), and less than the 80 minutes from 22:40 to 00:00, so the 22:40 run counts at the next run's alarm. The alarm runs before its own run's `publish` job, so it judges the runs before; the hour also keeps a run's own scheduled time from counting at its own alarm. A threshold in hours was rejected: the schedule's gaps are uneven, and one failed run can leave the tree as old, when an alarm looks, as two failed in a row (12 hours: the 06:00 run failing, seen at 12:00; the 22:40 and 00:00 runs failing, seen at 06:00), so no number of hours raises the second without the first. Counted by the schedule, it fires at the run after the second miss, with the tree 12 to 18 hours old; a test plays every scheduled run of three days at several lateness and holds it to that.

5. **No table of contents, or a bucket that cannot be read, is raised at once.** No `v1/index.json` means no publish has finished there: expected only between setting `API_BUCKET` to a new bucket and its first publish, which the README's set-up says, and otherwise the variable naming another bucket. A bucket that cannot be read (refused, missing, or a 5xx or no answer after three tries) leaves whether publishing works untold, and the `publish` job reads it with the same role and variable. Waiting a second pass for either would need a memory the alarm has only while an issue is open. The read is a `GET`, not a `HEAD`: a `HEAD`'s 404 has no body, and a missing bucket would look like an empty one.

6. **Reading never fails the first job.** Whatever S3 answers, or does not, is a finding in the alarm's words. The first job still does not publish and writes nothing to the bucket; its role, which may already list the bucket and read its `v1/*` (`RunsApiUploadPolicy`), gains nothing.

7. **`API_BUCKET` unset raises nothing while `PUBLIC_API` is `off`, and is raised otherwise.** Unsetting it is how publishing is stopped on purpose, and while nothing is served a stopped bucket harms no reader; the step summary says the bucket is not watched. Once the switch has left `off`, readers are served, or soon will be, what the bucket holds, so a variable unset by mistake is raised. The alarm reads the committed `PUBLIC_API.state`.

## What it does not catch

A workflow that does not run at all, or a first job that fails before the alarm's condition (the Runs repository checked out), reports nothing: the alarm runs in the same workflow. GitHub's failed-run email is then the only word. That the alarm issue's notification reaches the maintainer depends on their GitHub settings; it is confirmed once by hand (README, "Turning it on", step 0).
