# Publishing is watched by what the API bucket holds

ADR-0031 put the data API's tree into a private bucket from a `publish` job of its own, whose failure was a red job and GitHub's failed-run email, nothing more; turning the API on waits for a tested route by which a stale or failed publish reaches the maintainer (README, "Turning it on", step 0). This records the route. `scripts/lib/api-freshness.ts` and `scripts/alarm.ts` hold it; the README ("The alarm", "The data API's publishing") says how it reads.

## The decisions

1. **The existing alarm raises it, in its issue, by its rules.** The alarm already runs in every run's first job, opens one issue or comments on the open one, and writes only when what it reports changes. Publishing is one more thing it reports, with one more field in the state its posts carry (`stale_api`), and it says once, on the open issue, when the data API is published again.

2. **Judged by the bucket, never by a job's conclusion.** Publishing can stop many ways: the `publish` job fails, is skipped (its first job failed, or `API_BUCKET` was unset), is cancelled, never runs, or its preflight refuses the bucket. In every one, the table of contents, `v1/index.json`, is not written again. Reading the bucket catches them all with one rule; reading jobs would need a rule per way, and would miss the ways no job records.

3. **The evidence is `Last-Modified` of `v1/index.json`.** S3 sets it from its own clock as the object is written; no writer can. The upload writes that object only as its last act, after every phase (in the last phase when it changed, otherwise as the stamp of ADR-0031), so it moves on every upload of a new run that succeeds and on nothing else the workflow does. Rejected as evidence, and kept only as a lead in the alarm's words: the run in the object's metadata, which is whatever the uploader passed (an upload by hand can record any number, which is why the README has "A run recorded too high") and would need a call to GitHub to become a time; and the tree's own `newest_run_started_at`, which says when the newest Run started and so stands still when the boxes do, however well publishing works. `Last-Modified` moves without the workflow only when a person writes the object with their own credentials.

4. **What is counted: elapsed scheduled slots since the bucket was last written; two raise the alarm.** The slots are the workflow's scheduled times (00:00, 06:00, 12:00, 18:00, 22:40 UTC; a test holds the list to the crons). A job judges only slots whose publish should have finished an hour before the job started (its first step notes when), and never its own run's slot or a later one, because the alarm runs before its own run's `publish` job; a scheduled run's own slot is the latest time of the cron that started it (`github.event.schedule`), and a run started by hand has none. The hour is ten times what the runs took from 2026-11-11 to 2026-11-21 (2 to 5 minutes late, about a minute long, publish included), and less than the 80 minutes from 22:40 to 00:00, so the 00:00 run's job judges the 22:40 slot. What that guarantees: two scheduled runs that fail in a row, with nothing published between, raise the alarm at the run after them, the tree then 12 to 18 hours old; one failed run never raises it, however late the runs start. It is a count of slots, not of failed runs: a failed run followed by a publish by hand counts from the hand publish, since the bucket was written then (the 22:40 and 00:00 runs failing around a hand publish at 23:50 leave one slot counted at 06:00); and a very late start is never counted against its own run, which the next run's job judges, while a publish that lands after the next slot's time hides that slot too. A threshold in hours was rejected: the schedule's gaps are uneven, and one failed run can leave the tree as old, when an alarm looks, as two failed in a row (12 hours: the 06:00 run failing, seen at 12:00; the 22:40 and 00:00 runs failing, seen at 06:00). A first version judged up to an hour before the alarm's own time, and so counted a late run's own slot (the 22:40 run failing and the 00:00 run starting an hour late raised the alarm before the 00:00 run could publish); an independent verification found it, and tests now play every scheduled run of three days with seeded lateness up to 79 minutes and runs started by hand between the slots.

5. **No table of contents, or a bucket that cannot be read, is raised at once.** No `v1/index.json` means no publish has finished there: expected only between setting `API_BUCKET` to a new bucket and its first publish, which the README's set-up says, and otherwise the variable naming another bucket. A bucket that cannot be read (refused, missing, or a 5xx, no answer or an answer that stalls, three times) leaves whether publishing works untold, and the `publish` job reads it with the same role and variable. Waiting a second pass for either would need a memory the alarm has only while an issue is open. The read is a `GET`, not a `HEAD`: a `HEAD`'s 404 has no body, and a missing bucket would look like an empty one. Only its headers are used: the body of a 200 is cancelled unread.

6. **The read is bounded: 20 seconds in all.** Each try may take 5 seconds, about fifty times what it takes; the second and third come 1 and 2 seconds after a 5xx, no answer, or a try that ran out of time, so three tries take at most 18 seconds. Of an error's body at most 2 KB are read, for at most a second, and what reaches the issue of anything S3 or an error says is one line, without backticks, of at most 300 characters. The alarm's own verdict comes after the read, so the read must never hold it up long; a first version waited for whole bodies with no deadline, and a response that trickled could have used up the job's 30 minutes.

7. **The check is done whole and guarded, so the rest of the alarm never depends on it.** `watchApiBucket` does, before anything is posted, everything of the check: when the job's judgement ends, the read, the judgement, the alarm's words and the line for the step summary. Anything thrown anywhere in it becomes "The check of the API bucket failed", raised like a bucket that cannot be read (with nothing else stale, that opens an issue the alarm without the bucket would not have opened: a check that cannot run is something to know), and the stale Series and price files are judged and written exactly as without the check; the step summary's write is best-effort, warned of and passed over. A first version wrote the step summary unguarded, and a summary path that was a directory ended the alarm before its verdict. `runAlarm` takes only the check's finished strings.

8. **`API_BUCKET` unset: nothing is raised while `PUBLIC_API` is `off`, and the alarm is raised in any other state.** Unsetting it is how publishing is stopped on purpose while nothing is served; once serving is on (`dark`, `closed` or `on`), a missing bucket name means publishing has stopped. The bucket is not read either way, and the step summary says the variable is unset. The alarm reads the committed `PUBLIC_API.state`.

9. **A drill shows the route without touching publishing.** The workflow's `workflow_dispatch` input `alarm_drill` (off by default; a scheduled run has no inputs) makes only the alarm's check read a name no bucket can have, `LEDGERMATH_ALARM_DRILL`, and say in the issue that it is a drill; the `publish` job never sees the input and publishes to `API_BUCKET` as on any run, and the next ordinary run clears the drill with its single recovery comment. Rejected: pointing `API_BUCKET` at a wrong name for the drill, which would redirect every `publish` job started meanwhile.

10. **Reading never fails the first job, and its role gains nothing.** The first job still does not publish and writes nothing to the bucket; its role may already list the bucket and read its `v1/*` (`RunsApiUploadPolicy`).

## What it does not catch

A workflow that does not run at all, or a first job that fails before the alarm's condition (the Runs repository checked out), reports nothing: the alarm runs in the same workflow. GitHub's failed-run email is then the only word. That the alarm issue's notification reaches the maintainer depends on their GitHub settings; it is confirmed once by hand, with the drill (README, "Turning it on", step 0).
