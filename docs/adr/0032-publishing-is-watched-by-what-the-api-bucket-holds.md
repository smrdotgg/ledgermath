# Publishing is watched by what the API bucket holds

ADR-0031 put the data API's tree into a private bucket from a `publish` job of its own, whose failure was a red job and GitHub's failed-run email, nothing more; turning the API on waits for a tested route by which a stale or failed publish reaches the maintainer (README, "Turning it on", step 0). This records the route. `scripts/lib/api-freshness.ts`, `scripts/check-api-publishing.ts` and `scripts/alarm.ts` hold it; the README ("The alarm", "The data API's publishing") says how it reads.

## The decisions

1. **The existing alarm raises it, in its issue, by its rules.** The alarm already runs in every run's first job, opens one issue or comments on the open one, and writes only when what it reports changes. Publishing is one more thing it reports, with one more field in the state its posts carry (`stale_api`), and it says once, on the open issue, when the data API is published again.

2. **Judged by the bucket, never by a job's conclusion.** Publishing can stop many ways: the `publish` job fails, is skipped (its first job failed, or `API_BUCKET` was unset), is cancelled, never runs, or its preflight refuses the bucket. In every one, the table of contents, `v1/index.json`, is not written again.

3. **The evidence is `Last-Modified` of `v1/index.json`.** S3 sets it from its own clock as the object is written; no writer can. The upload writes that object only as its last act, after every phase (in the last phase when it changed, otherwise as the stamp of ADR-0031), so it moves on every upload of a new run that succeeds and on nothing else the workflow does. Rejected as evidence, and kept only as a lead in the alarm's words: the run in the object's metadata, which is whatever the uploader passed, and the tree's own `newest_run_started_at`, which stands still when the boxes do, however well publishing works.

4. **The rule is age, nothing else: the alarm is raised by the first check made more than 14 hours after the last successful publish.** One constant, `MAX_PUBLISH_AGE_MS`, which the code, the tests and a test of the README's words read. The check's inputs are `Last-Modified` and the time of the check, so a re-run of an old run, a run started by hand and a late run all judge alike, and none can clear a real alarm. What it means for the schedule, whose runs are at most 6 hours apart (a test holds the crons to that): after one failed publish, the next check comes at most 12 hours after the last publish, plus however late that run's alarm step runs after its slot, so it stays quiet when the alarm runs less than two hours after its slot (and may raise when it runs later: the 06:00 publish failing and the noon run's alarm checking at 14:04 raises it). Publishing that has stopped is raised by the first check made after 14 hours; with on-time runs, that is between 16 h 40 m and 19 h 20 m after the last scheduled publish, and later by however late that check runs. Not promised: two failed runs either side of the short gap from 22:40 to 00:00 can pass unnoticed when the next publish succeeds; publishing has then recovered. An earlier wording ("one failed publish does not raise unless a run starts more than two hours late"; "within about 20 hours") was wrong in both halves, as an independent verification showed with the cases above and a hand publish at 16:00 followed by a noon check made at 14:00; the simulation now places each alarm at a varying time after its slot and asserts these statements.

5. **No table of contents, or a bucket that cannot be read, is raised at once.** No `v1/index.json` means no publish has finished there: expected only between setting `API_BUCKET` to a new bucket and its first publish, and otherwise the variable naming another bucket. A bucket that cannot be read (refused, no credentials, or a 5xx or no answer three times; a single 5xx is tried again quietly) leaves whether publishing works untold, and the `publish` job reads it with the same role and variable. The read is a `GET`, not a `HEAD`, because a `HEAD`'s 404 has no body and a missing bucket would look like an empty one; only its headers are used, the body of a 200 is cancelled unread, and at most 2,048 bytes of an error's body are read.

6. **Nothing the check or S3 says in words reaches the issue.** The repository is public; an issue must carry no mention, link or token-shaped string from elsewhere. The check reports a result from a closed set (published with its date and run, empty, refused with the HTTP status, no credentials, server error with the HTTP status, no answer, no date, unset), which the alarm validates field by field and renders in fixed sentences; a check that gives no result is "the check of the API bucket failed" for one of four reasons (killed after the budget, exited with code N, output not understood, could not be started), also in fixed words. What S3 or the check said goes to the job's log. A first version quoted S3's message and the check's output, clipped; a mention and a Markdown link survived the clipping.

7. **The check runs whole in a child process with only what it needs, in a process group killed after 20 seconds.** The alarm starts `scripts/check-api-publishing.ts`, which reads, judges for its line in the step summary, writes that line itself and prints its result. Its environment is `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` and `GITHUB_STEP_SUMMARY` and nothing else: not `GITHUB_TOKEN`, and not `PATH` or `HOME`, which Bun does not need to run it; the bucket, the time and `PUBLIC_API`'s state go as arguments, and the Region is in the code. It leads a process group of its own; the alarm kills the group with `SIGKILL` after `CHECK_BUDGET_MS`, and as soon as the child exits in any case, so nothing it starts outlives it or holds its pipes open. A kill, a non-zero exit or output that is not a result is "the check of the API bucket failed", raised like a bucket that cannot be read (with nothing else stale, that opens an issue the alarm without the check would not have opened: a check that cannot run is worth knowing), and the alarm's verdict on the Series and price files is what it would be without the check. The alarm writes nothing on the check's behalf; a guard inside its own process could not bound a step summary that blocks on a synchronous write.

   **Accepted: the stale-Series verdict waits for the check, at most 22 seconds** (the 20-second budget and two seconds' grace for the pipes to close). An independent verification measured 1.2 seconds for a 200 ms budget with a grandchild holding the pipes. That wait is the price of one issue and one comment rather than two posts per run. The alarm starts the child before it reads the Runs repository, so the wait overlaps work it does anyway.

8. **`API_BUCKET` unset: nothing is raised while `PUBLIC_API` is `off`, and the alarm is raised in any other state.** Unsetting it is how publishing is stopped on purpose while nothing is served; once serving is on (`dark`, `closed` or `on`), a missing bucket name means publishing has stopped. The alarm reads the committed `PUBLIC_API.state` and passes it to the check.

9. **A drill is exactly one notification and touches nothing else.** The `workflow_dispatch` input `alarm_drill` (off by default; a scheduled run has no inputs) makes the alarm, after its ordinary pass, post one comment on the open alarm issue saying it is a drill, with the run's link, and that nothing is wrong; with no issue open, it opens the issue with those words as its body and posts no comment, since a second post would be a second notification. It reads nothing and carries no state marker, so an open finding stays reported and the next pass writes as it would have. An issue opened only by a drill is closed by the maintainer. A drill that cannot post says so in the log and the step summary and does not fail the job: the `publish` job runs only when the first job succeeded, so a failed drill must not skip a publish. Rejected: pointing `API_BUCKET` at a wrong name for the drill, which redirects every `publish` job started meanwhile; and making the check read a name no bucket can have, which replaced the bucket's state in the issue with a synthetic error and hid an open real finding.

10. **Every post fits GitHub's limit.** GitHub refuses an issue or comment body over 65,536 characters, and the post with it. With all 187 watched Series stale, the alarm's most important case, the body on `main` was 87,890 characters, so nothing would have been posted. Every body the alarm posts is built under `MAX_BODY_CHARS`, 60,000, the hidden marker included: the summary and its counts, the copy job's warning, the price finding and the bucket finding always; as many stale Series as fit, in sorted order; then one line saying how many more are not shown and that the run's log and step summary list every one (the alarm writes the complete list to the step summary, under that summary's limit of 1 MiB). The marker carries the number of stale Series and a 64-bit hash of the whole sorted set instead of the list, so it stays a few hundred characters whatever their number: the same set gives the same hash, so a repeat pass stays quiet, and any change to the set, shown in the post or not, changes it. Posts written before, whose marker listed the Series, read as the same state. A body over the limit is refused before it is sent, and a post GitHub refuses (422) fails the alarm loudly and is not sent again.

11. **Reading never fails the first job, and its role gains nothing.** The first job keeps exactly its steps and its alarm step's condition; it still does not publish and writes nothing to the bucket, and its role may already list the bucket and read its `v1/*` (`RunsApiUploadPolicy`).

## Rejected: counting scheduled slots

The first three versions of this change counted the scheduled slots (00:00, 06:00, 12:00, 18:00, 22:40 UTC) that had elapsed since the bucket was last written, and raised at two, so that "one failed run raises nothing, two in a row do" would hold exactly despite the schedule's uneven gaps. Each independent verification found a new way for it to be wrong: a late start counted the run's own slot against it (fixed by judging only up to an hour before the job started, which needed a step that noted the start); a publish by hand between two failures reset the count; and a re-run of an old scheduled run, its job started days later and its cron that of another day, judged a different set of slots from an ordinary run at the same moment and could clear a real alarm. The machinery (a cron reader, the run's own slot, a judgement cut-off, a workflow step recording the start time) bought a sharper boundary than the age rule's at the cost of inputs that differ from run to run. The age rule gives up exactness at the short 22:40 to 00:00 gap, where publishing has recovered anyway, and has two inputs that every run sees alike.

## What it does not catch

A workflow that does not run at all, or a first job that fails before the alarm's condition (the Runs repository checked out), reports nothing: the alarm runs in the same workflow. GitHub's failed-run email is then the only word. That the alarm issue's notification reaches the maintainer depends on their GitHub settings; it is confirmed once by hand, with the drill (README, "Turning it on", step 0).
