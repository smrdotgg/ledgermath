# Publishing is watched by what the API bucket holds

ADR-0031 put the data API's tree into a private bucket from a `publish` job of its own, whose failure was a red job and GitHub's failed-run email, nothing more; turning the API on waits for a tested route by which a stale or failed publish reaches the maintainer (README, "Turning it on", step 0). This records the route. `scripts/lib/api-freshness.ts`, `scripts/check-api-publishing.ts` and `scripts/alarm.ts` hold it; the README ("The alarm", "The data API's publishing") says how it reads.

## The decisions

1. **The existing alarm raises it, in its issue, by its rules.** The alarm already runs in every run's first job, opens one issue or comments on the open one, and writes only when what it reports changes. Publishing is one more thing it reports, with one more field in the state its posts carry (`stale_api`), and it says once, on the open issue, when the data API is published again.

2. **Judged by the bucket, never by a job's conclusion.** Publishing can stop many ways: the `publish` job fails, is skipped (its first job failed, or `API_BUCKET` was unset), is cancelled, never runs, or its preflight refuses the bucket. In every one, the table of contents, `v1/index.json`, is not written again.

3. **The evidence is `Last-Modified` of `v1/index.json`.** S3 sets it from its own clock as the object is written; no writer can. The upload writes that object only as its last act, after every phase (in the last phase when it changed, otherwise as the stamp of ADR-0031), so it moves on every upload of a new run that succeeds and on nothing else the workflow does. Rejected as evidence, and kept only as a lead in the alarm's words: the run in the object's metadata, which is whatever the uploader passed (an upload by hand can record any number), and the tree's own `newest_run_started_at`, which stands still when the boxes do, however well publishing works.

4. **The rule is age, nothing else: raised when `v1/index.json` was last written more than 14 hours before the check runs.** One constant, `MAX_PUBLISH_AGE_MS`, which the code, the tests and a test of the README's words all read. The check's inputs are `Last-Modified` and the current time, so a re-run of an old run, a run started by hand and a late run all judge alike, and none can clear a real alarm. What it guarantees: scheduled runs are at most 6 hours apart (a test holds the workflow's crons to that, and the constant to two such gaps and two hours), so after one failed publish the bucket is at most 12 hours old when the next run's alarm looks, plus that run's lateness; 14 hours leaves two hours for lateness, so one failed publish does not raise the alarm unless a run starts more than two hours late. Publishing that has stopped is raised by the first alarm that runs once the bucket is 14 hours old, which is at most about 20 hours after the last publish. What it does not promise: two failed runs either side of the short gap from 22:40 to 00:00 can pass unnoticed when the next publish succeeds, which is fine, since publishing has then recovered.

5. **No table of contents, or a bucket that cannot be read, is raised at once.** No `v1/index.json` means no publish has finished there: expected only between setting `API_BUCKET` to a new bucket and its first publish, and otherwise the variable naming another bucket. A bucket that cannot be read (refused, missing, no credentials, or a 5xx or no answer three times; a single 5xx is tried again quietly) leaves whether publishing works untold, and the `publish` job reads it with the same role and variable. The read is a `GET`, not a `HEAD`, because a `HEAD`'s 404 has no body and a missing bucket would look like an empty one; only its headers are used, the body of a 200 is cancelled unread, at most 2,048 bytes of an error's body are read, and what reaches the issue of anything S3 says is one line of at most 300 characters.

6. **The check runs whole in a child process, killed after 20 seconds.** The alarm starts `scripts/check-api-publishing.ts`, which reads, judges, words, writes its own line to the step summary and prints its report as one line of JSON; after `CHECK_BUDGET_MS` the alarm kills it with `SIGKILL`. A kill, a non-zero exit or output that is not a report is "the check of the API bucket failed", raised like a bucket that cannot be read (with nothing else stale, that opens an issue the alarm without the check would not have opened: a check that cannot run is worth knowing), and the alarm's verdict on the Series and price files, which comes after, is what it would be without the check. The alarm writes nothing on the check's behalf. A guard inside the alarm's own process was not enough: a step summary that blocks on a synchronous write cannot be bounded by catching errors, and an independent verification held the check for 20.5 seconds that way.

7. **`API_BUCKET` unset: nothing is raised while `PUBLIC_API` is `off`, and the alarm is raised in any other state.** Unsetting it is how publishing is stopped on purpose while nothing is served; once serving is on (`dark`, `closed` or `on`), a missing bucket name means publishing has stopped. The alarm reads the committed `PUBLIC_API.state` and passes it to the check.

8. **A drill posts one comment and touches nothing else.** The `workflow_dispatch` input `alarm_drill` (off by default; a scheduled run has no inputs) makes the alarm, after its ordinary pass, post one comment on its issue, or open the issue with it, saying it is a drill, with the run's link, and that nothing is wrong. It reads nothing and carries no state marker, so an open finding stays reported and the next pass writes as it would have. An issue opened only by a drill is closed by the maintainer. The `publish` job never sees the input. Rejected: pointing `API_BUCKET` at a wrong name for the drill, which redirects every `publish` job started meanwhile; and making the check read a name no bucket can have, which replaced the bucket's state in the issue with a synthetic error and hid an open real finding.

9. **Reading never fails the first job, and its role gains nothing.** The first job keeps exactly its steps and its alarm step's condition; it still does not publish and writes nothing to the bucket, and its role may already list the bucket and read its `v1/*` (`RunsApiUploadPolicy`).

## Rejected: counting scheduled slots

The first three versions of this change counted the scheduled slots (00:00, 06:00, 12:00, 18:00, 22:40 UTC) that had elapsed since the bucket was last written, and raised at two, so that "one failed run raises nothing, two in a row do" would hold exactly despite the schedule's uneven gaps. Each independent verification found a new way for it to be wrong: a late start counted the run's own slot against it (fixed by judging only up to an hour before the job started, which needed a step that noted the start); a publish by hand between two failures reset the count; and a re-run of an old scheduled run, its job started days later and its cron that of another day, judged a different set of slots from an ordinary run at the same moment and could clear a real alarm. The machinery (a cron reader, the run's own slot, a judgement cut-off, a workflow step recording the start time) bought a sharper boundary than the age rule's at the cost of inputs that differ from run to run. The age rule gives up exactness at the short 22:40 to 00:00 gap, where publishing has recovered anyway, and has two inputs that every run sees alike.

## What it does not catch

A workflow that does not run at all, or a first job that fails before the alarm's condition (the Runs repository checked out), reports nothing: the alarm runs in the same workflow. GitHub's failed-run email is then the only word. That the alarm issue's notification reaches the maintainer depends on their GitHub settings; it is confirmed once by hand, with the drill (README, "Turning it on", step 0).
