# The home page is rebuilt after every publish

Since 2026-11-25 https://ledgermath.com is the home page of design v9 (#90): a static site, every figure read at build time from a tree of the data API. The first deploy was made by hand. The maintainer asked: "We should rebuild it whenever a new benchmark is published. That will be the mechanism in which the numbers on the landing page are kept fresh." This records how. The job `site` of `.github/workflows/runs.yml`, the job `deploy-production` of `.github/workflows/site.yml` and `scripts/read-api-tree.ts` hold it; the README ("Where it is deployed") says how it reads.

## The decisions

1. **The runs workflow rebuilds and deploys the site, in a third job after `publish`.** The job `site` runs only when `publish` succeeded (never when it failed, was skipped or was cancelled), and only on main (a scheduled run, or one by hand on main). It builds the page by the rule of decision 2, runs `bun run check` against the files it read and compares the notices, deploys to Vercel production with `site/deploy/deploy.sh`, and checks the live pages. The deployment records the commit that was checked out, not the run's `GITHUB_SHA`.

2. **The rule: production deploys take turns, and each builds the page from what the API bucket holds when its turn comes.** Two jobs deploy production: `site` in runs.yml, after each publish, and `deploy-production` in site.yml, after a push to main. Both hold one concurrency group, `site-deploy-production`, with `queue: max`: one runs at a time, a running one is never cancelled, and every one that arrives meanwhile waits. Inside the group each does, in this order:
   1. has the site's sources: `site` checks out main as it is now, never its run's commit; `deploy-production` deploys its own commit only if main has not moved on in the site's files (`site/deploy/fresh.ts`), and otherwise skips and passes;
   2. takes AWS credentials with the role the `publish` job uses, which may read and write the bucket's `v1/*`; these jobs only read, and the keys are given to the reading step alone (the action's outputs, not the job's environment), so the build, the checks and the deploy never hold them;
   3. reads the tree from the API bucket itself (decision 4): not the edge, whose cache can be five minutes behind an upload, and not an artifact;
   4. builds the site from exactly those bytes and checks it;
   5. deploys, and checks the live site.

   **Why that is enough.**
   - What the page shows is what the bucket held when the job read it. The bucket is the record of what is published (the `publish` job writes it; the edge serves it), so the page shows a tree the public API served, whatever was run again and whichever artifact a job happened to download.
   - Deploys come one at a time and each reads the bucket afresh, so the last one to run deploys the newest tree there was when it read. The bucket only moves forward (the upload refuses a run lower than the one it records, `OlderTree`), and a publish that ends after a deploy's read is followed by its own `site` job, which waits its turn and reads again. A job whose turn comes late reads the same bucket and deploys the same page again, which is harmless. No job asks whether its tree is the newest: there is no check of trees at all, no run ids, no artifact ids, no reading of GitHub's record of runs. A test holds that none creeps back into a production deploy or a script.
   - The sources' side is as it was: `site` checks out main inside the group; `deploy-production` keeps `fresh.ts`.

   **What it does not cover.**
   - Between a successful publish and its rebuild (about a minute, and longer if the queue is busy), the page shows the tree before, which the bucket no longer holds; the edge's own cache may serve the previous table of contents for up to five minutes anyway.
   - If the upload finished and the `publish` job's own last step, its check of the bucket, then failed, the bucket already holds the new tree but no `site` job runs: the page stays on the previous tree until the next successful publish, a re-run of a `site` job, or a deploy by hand.
   - The "one publication" check sees only what the three files say about each other: the table of contents' address and the Series list's, the count of Series, the newest Run's start, and the newest price file's date. When they disagree (an upload under way, the table of contents being written last), the reader reads them again, three times in all, ten seconds apart, then fails, writing nothing, and production keeps the build it had. A difference it cannot see passes: Runs or boot summaries that arrived late, or a Method's figures that changed while all of those stayed the same; the page may then show the newer list's figures under the older table of contents' rounds until the next rebuild.
   - An upload that stopped halfway makes every deploy fail until the next publish only when the three files then disagree on something the check compares. One that stopped before it changed any of them leaves the previous files readable, and the page is built from them.
   - A deploy by hand from this machine is outside the group (README).

   **Rejected, after two verifications of #93.** Working out which tree is published from GitHub's record of runs and artifacts. The first version compared run ids, so a run run again in full could have its first tree put back by a delayed deploy. The second gave a tree an identity, the run and the artifact `api` its `publish` job took, but recomputed the artifact from the artifacts GitHub still lists, so the same history gave another answer once an artifact had expired or been removed, and its search returned at the first success before it had checked the page of runs it was reading. Each round found another way for the inference to be wrong; the bucket needs none. Rejected as well: building from a tree fetched from `https://api.ledgermath.com` (its cache can be five minutes behind), and from the run's own artifact `api` (a run run again in full holds more than one, and the one a job downloads by name need not be the one its `publish` job uploaded).

3. **site.yml's production deploy follows the same rule.** Its build job still builds every commit from the public API's tree, as a gate and for previews, with no AWS credentials. Once site.yml is enabled again, a pull request from a fork gets no credential of any kind; a pull request from a branch of this repository gets the Vercel token in its preview's deploy step, as it did before this change, and never the AWS role. `deploy-production`, on main only, builds again inside the group from the bucket, with the role, and deploys that; it does not deploy the build job's artifact. The role trusts any workflow of this repository on `refs/heads/main` (`infra/runs/github-role.ts`), so nothing needs to change in AWS before site.yml runs again; it needs only to be enabled once the repository is public. (It was, on 2026-11-25: below.)

4. **The tree is read from the bucket by `scripts/read-api-tree.ts`.** It starts at `v1/index.json` and reads only the keys the table of contents' links give for the files the page needs (the Series list and the newest price file): each link must be under the table of contents' own address and a plain path to a JSON file under `v1/`, and that path is the key; it never builds one. Each read is one signed `GET` through the repository's own S3 client (`S3ApiStore.read`, `scripts/lib/api-upload.ts`), within 30 seconds and under its file's size limit, following no redirect (a 3xx is a refusal: the key was checked, an address S3 points to was not). What it says when it fails names the file, the refused field, the key, the HTTP status and S3's error code from a closed list: never a value refused from a file (an address can carry a signature), and never S3's own message. The check that the files are of one publication, the retry and the all-or-nothing write are those `site/scripts/fetch-tree.ts` already had, reused. `tests/read-api-tree.test.ts` holds it to that against a stand-in for S3.

5. **The tree is cut once after each round of boots.** `5 0,6,12,18 * * *` (00:05, 06:05, 12:05 and 18:05 UTC) replaces `40 22 * * *` and `0 */6 * * *`. The 22:40 run cut the 22:10 round while its last boxes were still running, a time that suited an older pipeline: the tree then showed that round with only the boots that had ended. A round's last box is scheduled at :50. A launch more than ten minutes late is refused (`LATEST_START_MS`), and the reaper, every five minutes, asks EC2 to end any box older than 50 minutes (`MAX_AGE_MS`), so by those limits the round has ended by HH+1:55. The scheduled run comes ten minutes after that, and four hours before the next round's first boot. A test holds the crons to `schedule.json` and those limits. What the schedule promises is only that a scheduled run is set to start after every box of the round has ended by those limits. A tree can still hold part of a round when a run starts during one (one started by hand, or a scheduled run that GitHub starts, or that waits for its runner, more than four hours late), or when a box outlives the limits (the reaper asks for a box to be ended and does not confirm that it was). The API's own words allow for that: a month file changes when a Run or a missing boot summary arrives late. Considered: 05:30, five minutes after the last boot's 35-minute budget ends. A boot that runs to its budget still has its upload to do then, and one launched late, or ended by its 45-minute shutdown, is still running.

   What depends on the times:
   - **The alarm's 14 hours** (ADR-0032) assume runs at most 6 hours apart; they are now exactly 6 hours apart, so the threshold stands. Publishing that has stopped is now raised 18 hours after the last on-time publish (before: between 16 h 40 m and 19 h 20 m). Two failed publishes in a row are now raised by the next run's check, when every alarm runs less than two hours after its slot: the short gap from 22:40 to 00:00 that let them pass is gone.
   - **A late start.** GitHub started the runs at the top of the hour 7 to 15 minutes late on 2026-11-24. A late start cuts the same round, later. Only a start more than four hours late would reach into the next round.
   - **The stale Series' 48 hours** depend on the boots, not on these times, and are unchanged. `prices.yml`, at 03:17 and 15:17, stays more than two hours from every run (a test holds it).
   - **The cutover** of the README ("Moving the schedule to the production account") is planned around these times; its words follow them.

6. **A failed rebuild is a red job, and the notice says what production serves, as far as it is known.** The job's last step names the step that failed, in an error at the top of the run's page and in its summary. Before the deploy step, nothing on Vercel changes, and the notice says production keeps the build it had. A failure of the deploy step itself is not confirmed either way: `deploy.sh` calls Vercel with `--prod` and only then reads and checks the receipt, so production may already serve the new deployment; the notice says so, and to look at the project's deployments in Vercel. A live check that fails after a deploy step that succeeded cannot undo it, and the notice says the new build is served. Nothing tells the maintainer beyond the red run and GitHub's own failed-run e-mail; #87 is about that.

7. **The Vercel token stays in the deploy steps.** In runs.yml only the `site` job's deploy step sees `VERCEL_TOKEN`, `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID`; in site.yml, only the deploy steps of its two deploy jobs. A test reads every file under `.github` and fails on a reference anywhere else, on secrets handed over whole, and on runs.yml being started by a pull request, as the test of the Telegram secrets does (ADR-0033).

## While site.yml is disabled

site.yml stays disabled until the repository is public (README, "Where the workflows run"). Until then, only the `site` job deploys production by itself, and a push to main reaches ledgermath.com with the next publish's rebuild, within six hours, or sooner by hand.

**Ended on 2026-11-25.** The repository was made public on the maintainer's word (#47), the self-hosted runner and the variable that named it were removed, and all four workflows, site.yml among them, were enabled; every job runs on GitHub's hosted runner `ubuntu-24.04` (README, "Where the workflows run"). What holds now: production is deployed both ways, by the `site` job after every publish and by site.yml's `deploy-production` after a push to main that touches `site/` or site.yml, each by the rule of decision 2, in the one group. Neither cancels the other; each waits its turn. A push to main that touches neither starts no deploy and reaches ledgermath.com with the next publish's rebuild, as above.
