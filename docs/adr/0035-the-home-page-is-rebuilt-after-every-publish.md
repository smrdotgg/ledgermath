# The home page is rebuilt after every publish

Since 2026-11-25 https://ledgermath.com is the home page of design v9 (#90): a static site, every figure read at build time from a tree of the data API. The first deploy was made by hand. The maintainer asked: "We should rebuild it whenever a new benchmark is published. That will be the mechanism in which the numbers on the landing page are kept fresh." This records how. The job `site` of `.github/workflows/runs.yml`, the job `deploy-production` of `.github/workflows/site.yml` and `site/deploy/published.ts` hold it; the README ("Where it is deployed") says how it reads.

## The decisions

1. **The runs workflow rebuilds and deploys the site, in a third job after `publish`.** The job `site` runs only when `publish` succeeded, so the API serves the tree the page is built from: never when `publish` failed, was skipped or was cancelled. It runs only on main (a scheduled run, or one by hand on main). It builds from the artifact `api` its run's `publish` job uploaded, taken by that artifact's id (decision 2), runs `bun run check` against that tree and compares the notices, deploys to Vercel production with `site/deploy/deploy.sh`, and checks the live pages. The deployment records the commit that was checked out, not the run's `GITHUB_SHA`. Rejected: building from a tree fetched from `https://api.ledgermath.com`. Its cache can serve the previous table of contents for five minutes after an upload, so the page could show the tree before while the API shows the new one.

2. **Production deploys take turns, and each deploys only what is current when its turn comes.** Two jobs deploy production: `site` in runs.yml, after each publish, and `deploy-production` in site.yml, after a push to main. Both hold one concurrency group, `site-deploy-production`, with `queue: max`: one runs at a time, a running one is never cancelled, and every one that arrives meanwhile waits. When its turn comes, each checks two things, and deploys only if both hold:
   - **The site's sources are main's.** `site` checks out main as it is when the job starts, never its run's commit. `deploy-production` deploys its own commit only if main has not moved on in the site's files (`site/deploy/fresh.ts`).
   - **The tree is the newest published**, by its identity (`site/deploy/published.ts check`).

   Otherwise the job skips the deploy, passes, and says why in its summary. After any production deploy, ledgermath.com holds main's site as it was when that job's turn came, built from the newest tree published by then. The tree is never older than the one it held before: the newest published tree only moves forward (the upload refuses a run lower than the one the bucket records, `OlderTree`, and a run's attempts come one after another), and deploys come one at a time.

   **A tree's identity is `RUN/ARTIFACT`**: the run of runs.yml that published it and the id of the very artifact `api` its `publish` job uploaded. The run alone is not enough. A run run again in full keeps its id, keeps an artifact `api` of each attempt and publishes the new one, so a deploy that carried only the run would pass the check and could put the first attempt's tree back (found by the verification of #93, at `b726f95`). The newest published tree is that of the latest successful `publish` job of the run with the highest id that has one. Its artifact is the one that job's download took: of the run's artifacts named `api` made when it started, the highest id, which is how `actions/download-artifact` picks among artifacts of one name (the ids do not follow the order the artifacts were made in: in run 45516617507, `page`, made 13 seconds before `api`, has the higher id). So on a run run again in full, the `publish` job, which takes the artifact by its name, may upload the earlier attempt's tree; the site follows whatever it uploaded. Having `publish` take its own attempt's artifact by id is a change to that job, left out of this one. The identity travels with the tree. The `site` job asks for its run's tree, is told its identity and downloads that artifact by id. site.yml's build takes the newest identity, downloads that artifact by id, and hands the identity to its deploy job, which deploys only if it is still exactly the newest, so a later attempt of the same run counts as newer. No download takes "the artifact named `api`" of a run: it reads the artifact's record, refuses one of another run, of another name or expired, holds the bytes to the digest GitHub gives, and refuses files outside `v1/`.

   **The record is read in full or not at all.** Every list (the runs, a run's jobs, a run's artifacts) is read page by page while the count GitHub gives is more than what has been read, up to a bound; a page that comes back short, or a list past the bound, makes the check fail. At `b726f95` a successful `publish` on the second page of a run's jobs was taken as no publish, and an empty page of runs that claimed two was taken as none. The `publish` job is known by every display name it has had (`PUBLISH_JOB_NAMES`), not by the name in the caller's runs.yml, so a run made with another version of the workflow is still recognised; renaming the job means adding the new name first, and a test holds that first name to runs.yml's.

   **Why a skip is safe.** A newer tree's `site` job starts only after that tree was published, and deploys main's site, as it then is, with it, after the skipped job or before it. When `deploy-production` skips for the tree, that `site` job started after the build chose the older tree, so after the build's commit was on main, and the commit's site goes out with it. A skip relies on that job: if it fails, is cancelled or never runs, ledgermath.com stays on an older build until someone re-runs it, and the skip's message says so. `fresh.ts` already makes the same bargain for the sources.

   **Why GitHub's record, not the API's.** The run a publication records is in the `x-amz-meta-ledgermath-run` header of `v1/index.json`. Read through CloudFront it can be five minutes old, so a check there could see the run before and let an older tree pass. The bucket itself is readable only with AWS credentials, which site.yml does not have. GitHub's record of which runs' `publish` jobs succeeded is exact as soon as the job ends. Rejected as well: a marker in the built site naming its tree, read from production before each deploy. It would put a file in the site and a public read before every deploy, and it would still need an order of trees, which the trees' own files do not give: their newest Run can stand still while a late Run or a new price file changes the figures.

3. **site.yml's production build takes the tree the runs workflow published last**, by its identity (decision 2), and downloads that artifact by id. The build hands the identity to its deploy job, which checks it as in decision 2. A preview is still built from the tree the API serves now. The artifact is kept for a week; with none newer, a production build of site.yml fails, and the site is deployed by hand (README).

4. **The tree is cut once after each round of boots.** `5 0,6,12,18 * * *` (00:05, 06:05, 12:05 and 18:05 UTC) replaces `40 22 * * *` and `0 */6 * * *`. The 22:40 run cut the 22:10 round while its last boxes were still running, a time that suited an older pipeline: the tree then showed that round with only the boots that had ended. A round's last box is scheduled at :50. A launch more than ten minutes late is refused (`LATEST_START_MS`), and the reaper, every five minutes, asks EC2 to end any box older than 50 minutes (`MAX_AGE_MS`), so by those limits the round has ended by HH+1:55. The scheduled run comes ten minutes after that, and four hours before the next round's first boot. A test holds the crons to `schedule.json` and those limits. What the schedule promises is only that a scheduled run is set to start after every box of the round has ended by those limits. A tree can still hold part of a round when a run starts during one (one started by hand, or a scheduled run that GitHub starts, or that waits for its runner, more than four hours late), or when a box outlives the limits (the reaper asks for a box to be ended and does not confirm that it was). The API's own words allow for that: a month file changes when a Run or a missing boot summary arrives late. Considered: 05:30, five minutes after the last boot's 35-minute budget ends. A boot that runs to its budget still has its upload to do then, and one launched late, or ended by its 45-minute shutdown, is still running.

   What depends on the times:
   - **The alarm's 14 hours** (ADR-0032) assume runs at most 6 hours apart; they are now exactly 6 hours apart, so the threshold stands. Publishing that has stopped is now raised 18 hours after the last on-time publish (before: between 16 h 40 m and 19 h 20 m). Two failed publishes in a row are now raised by the next run's check, when every alarm runs less than two hours after its slot: the short gap from 22:40 to 00:00 that let them pass is gone.
   - **A late start.** GitHub started the runs at the top of the hour 7 to 15 minutes late on 2026-11-24. A late start cuts the same round, later. Only a start more than four hours late would reach into the next round.
   - **The stale Series' 48 hours** depend on the boots, not on these times, and are unchanged. `prices.yml`, at 03:17 and 15:17, stays more than two hours from every run (a test holds it).
   - **The cutover** of the README ("Moving the schedule to the production account") is planned around these times; its words follow them.

5. **A failed rebuild is a red job, and the notice says what production serves, as far as it is known.** The job's last step names the step that failed, in an error at the top of the run's page and in its summary. Before the deploy step, nothing on Vercel changes, and the notice says production keeps the build it had. A failure of the deploy step itself is not confirmed either way: `deploy.sh` calls Vercel with `--prod` and only then reads and checks the receipt, so production may already serve the new deployment; the notice says so, and to look at the project's deployments in Vercel. A live check that fails after a deploy step that succeeded cannot undo it, and the notice says the new build is served. Nothing tells the maintainer beyond the red run and GitHub's own failed-run e-mail; #87 is about that.

6. **The Vercel token stays in the deploy steps.** In runs.yml only the `site` job's deploy step sees `VERCEL_TOKEN`, `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID`; in site.yml, only the deploy steps of its two deploy jobs. A test reads every file under `.github` and fails on a reference anywhere else, on secrets handed over whole, and on runs.yml being started by a pull request, as the test of the Telegram secrets does (ADR-0033).

## While site.yml is disabled

site.yml stays disabled until the repository is public (README, "Where the workflows run"). Until then, only the `site` job deploys production by itself, and a push to main reaches ledgermath.com with the next publish's rebuild, within six hours, or sooner by hand.
