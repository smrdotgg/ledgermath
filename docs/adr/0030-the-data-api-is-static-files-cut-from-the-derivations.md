# The data API is static files cut from the Derivations

LedgerMath's first readers are agents, and what they read is a data API (#64, decision 1). It is a tree of small static JSON files, each kind with a JSON schema, regenerated by the `runs` workflow from the Derivations that workflow already makes and from the daily price files (and, since 2026-11-24, the boot summaries, for the newest rounds of boots: rule 12). It is a re-cut of the Derivations, not a new Method: it computes no statistic, and every number in it is a Derivation's, written exactly as the Derivation holds it, or a count of what the Runs and boot summaries record (rule 4). The decisions below were agreed with the maintainer on 2026-11-18 and 2026-11-19 (#64 and its two last comments); `scripts/build-api.ts` builds the tree and `scripts/check-api.ts` checks it (README, "The data API"). The tree is built in private and kept as the workflow's artifact `api`. Serving it is ADR-0031: built behind a switch that is off, with the checked tree uploaded to a private bucket after every run; making it public needs the maintainer's explicit go.

## The layout

Everything is served from one host, `https://api.ledgermath.com`, and the tree is laid out exactly as it is served from that host's root:

| Path | Holds |
|---|---|
| `v1/index.json` | The table of contents: the list's address, every price file held with the newest marked, the schemas, the docs' address, the template of a blob's address, and the layout the files are written in (rule 9); and the newest rounds of boots, each with its figures and its boots' summaries (rule 12, since 2026-11-24) |
| `v1/series.json` | One row per Series: what it is (benchmark, params, build, instance type, zone ID), how many Runs, its oldest and newest Run, a summary of each Method's Derivation of it, and the `url` of its own file; and each Method's own words, with the Run files it could not read |
| `v1/series/<id>.json` | One Series: its identity and span, each Method's words and summary (percentiles, groups and their facts and figures, section counts, counted and failed Runs), the points of its newest 12 Runs, and its months, each with its address, its count of Runs, its first and last start, and the month file's sha256 and size in bytes |
| `v1/series/<id>/<yyyy-mm>.json` | One month of a Series: every point of the Runs that started that month (UTC, by the Run's start), each Method's under its key, each with the sha256 of its Run file and an `evidence` link to it, and series v1's entries for the pairs of consecutive Runs whose later Run started that month |
| `v1/prices/<yyyy-mm-dd>.json` | That day's price file, byte for byte as the Runs repository holds it. There is no summary and no "latest" file |
| `v1/schemas/<name>.schema.json` | The schema of each kind of file: `index`, `series-list`, `series`, `series-month` (kept in `schemas/api/v1/`) and `prices` (`schemas/prices.schema.json`); and `events` (`schemas/events.schema.json`), the schema of one line of a Run's stdout, which describes no file of the tree and is served because both Methods' definitions hold a Run's events to it (since 2026-11-24) |

The evidence is served from the same host at the bucket's own keys, `/runs/<yyyy>/<mm>/<dd>/<id>.json`, `/boots/<yyyy>/<mm>/<dd>/<boot>.json` and `/blobs/sha256/<hex>`. The tree links it and never copies it.

## The rules

1. **Static files, not a server.** A query server is added only when static files demonstrably fail (#64, decision 2). The one large file of Derivations, 60 MB on 2026-11-19, is split into a list, a file per Series and a file per month of each Series.
2. **Every address a reader needs is written in the files.** Each row carries its Series file's `url`, each Series file the `url` of each of its months, each month file its Series file's `series_url`, each point its Run file's `evidence` and its boot's `boot_summary`, each unreadable Run file its `evidence`, and the table of contents every other file's address; a reader never builds an address from an id. One exception is unavoidable: a Run file names its binary, streams and dumps by hash, and a Run file is never edited, so `v1/index.json` gives the blob address as a template, `…/blobs/sha256/{hex}`. All addresses start with a base taken from an option, so a private or test address can stand in for `https://api.ledgermath.com`.
3. **Exact figures, and none loses a digit.** Nothing is rounded, in the API or on the page. Numbers are parsed from the Derivations and written back by `JSON.stringify`, as the Derivations were written, so each reads back as the same number, digit for digit. The build reads every number of both files of Derivations as text too (`scripts/lib/strict-json.ts`, `exactNumbers`), and refuses the file, naming it, the number's place as a JSON Pointer and the number, when the number's decimal value is not exactly the value of what it would write: an integer past 2^53 (`9007199254740993`, written `9007199254740992`), a value past a double's range (`1e400`, Infinity, written `null`) or below it (`1e-400`, written `0`), more digits than a double holds (`0.10000000000000001`, written `0.1`). A number written otherwise with the same value passes (`1e3`, written `1000`). `-0` passes and is written `0`: it is the value zero, which is all a decimal number says, and `JSON.stringify` writes every negative zero as `0`, so no Method emits one. Most numbers (95% on 2026-11-19) have at most 15 characters and no exponent, and are exact without being converted (a double holds 15 significant decimal digits); the rest are converted once. Reading the 60 MB file so costs about 0.25 s more than `JSON.parse` alone. The check reads every file of the tree the same way.
4. **A re-cut, not a Method.** A number the Derivations do not hold is not in the API. The only figures added are taken straight from a Series' points: how many Runs it has, in all and in each month, how many each Method counts and does not, how many groups, and when its oldest and newest Run started, in all and in each month; and, of the tree itself, each month file's sha256 and size (rule 9). The newest is the moment a citation of the Series names (ADR-0029, decision 12). Since 2026-11-24 the table of contents also counts, for each of the newest rounds of boots, what the boot summaries list and how many of the Runs they list the points give as failed (rule 12): counts of recorded facts, never a statistic.
5. **Each Method's output is labelled with its name and version.** A row, a Series file and a month file hold each Method's part under `derivations.<name>_v<version>`, each with its `method`, at the same paths and in the same words as the Method's file, so the two can be compared by eye. A Series can carry two: the 25 `http_get` Series are in both `series_v1` and `requests_v1`, 187 Series in all on 2026-11-19. The build stops if the two Methods cite different Runs for one Series. A Series file carries its Methods' definitions, so it can be read alone. Its readers have the API and nothing else, so no word the tree publishes (its own texts, the Methods' definitions and words, the schemas' descriptions) names what a reader cannot fetch from it: no file or directory of the repository, no README or document section, no issue, pull request or ADR, no function of the code or option of a program. Where a definition once pointed to such a thing, it states the rule (2026-11-23: Method series v1 and requests v1 said a Run counts when its stream obeys "every order rule" of a script of the repository, and each request reads "as the binary's README says"). A definition is the published statement of how a number is made, so its words and the Method's code say exactly the same: where an independent check found they did not (an exit 4 read as proof of a failed request, a request number not said to be an integer, the connection checks stated wider than they are, a sample starting before the previous one ended not stated), the words were changed before the change merged, and no number. A test scans every string of a built tree, but for what is data (what the Runs recorded, and what a Method derived from them for one Series or one Run: a point's failure, a Run file's path), and fails on any such reference (`tests/api-words.test.ts`). What a definition names, the tree serves: both say a Run counts only when each line of its stdout matches the events schema, so the tree serves it at `v1/schemas/events.schema.json`, beside the API's own schemas, its own words held to the same scan. The price files are scanned too, but for AWS's words and identifiers: each price rule's words for what it selects are LedgerMath's. One address stays that cannot be followed while the repository is private: `docs`, the README's section (Costs). The repository was made public on 2026-11-25, and the address can be followed since.
6. **`v1` only ever gains fields.** A field, once in a `v1` file, keeps its name, its type and its meaning, and a reader ignores fields it does not know, so no object in the API's own schemas (`index`, `series-list`, `series`, `series-month`) forbids members it does not list. A new Method, or a new version of one, is a new key beside the old ones. A change that would break a reader is published as `v2`, beside `v1`. The table of contents and every one of those schemas say so. The price files are the exception: each is the Runs repository's price file, byte for byte, and follows its own schema, `ledgermath.prices/1`, whose root and LedgerMath's own objects are closed. The check validates every file against this repository's schemas, with every object of the API's own closed, so a field the schemas do not describe still fails the build. Because the files only re-cut what the Methods emit, the schemas admit everything the Methods can emit, not only what today's data show: a percentile of bytes per second, for one, can be null, when a counted Run's time per repetition is 0; and a percentile of time per repetition, when a counted Run's time per repetition, the mean of its two middle samples, overflows a double.
7. **The same inputs give the same bytes.** File for file, whatever order the Series, price files and boot summaries come in, and whatever order the members of any object come in: known fields are written in the order their schema lists them, and the keys of a free-form object (params, a group's facts, a Method's definitions, a Service's inputs) in JavaScript's default string order, by UTF-16 code unit, which is byte order for the ASCII names in use. Because the order of known fields follows the order of the schemas' properties, reordering a schema's properties would change the bytes of every file and empty every cache; a golden test (`tests/api-golden.test.ts`) compares every file the build writes from a small fixture with a committed copy, so such a change, or any other change to the bytes, shows in review as a diff of the copies, and the test's failure says to raise `layout` (rule 9) when the change is on purpose. No clock is read. A Series file depends only on its own Runs, its Methods' words, its boots' summaries and the base address, so a Series that gained no Run keeps its file byte for byte and caches go on holding it; a month file depends only on its month's Runs, the Runs before them in its Series, the Methods that derive the Series, its boots' summaries and the base (rule 9). No file carries the time it was made. `v1/index.json` and `v1/series.json` carry the data's own moment instead, the start of the newest Run of any Series.
8. **What a Method could not count, or read, is shown.** A Run a Method does not count is a point with `counted: false` and its `failure`, linked to its evidence and counted in the row and the Series file as `failed_runs`. A Run file no Method could read is in no Series; `v1/series.json` lists it under each Method's `unreadable`, with why and its `evidence`.
9. **Each Series is split by month, and a month file changes only for four causes** (#64, decision of 2026-11-19, built before the API goes public). What grows with every Run is in the month files, never in the Series file: each Method's points, and series v1's `differed` entry for each pair of consecutive Runs, filed under the month of the later Run (so the first entry of a month may come from the previous month's last Run). A Run's month is the first seven characters of its `started_at`, which the Run schema writes in UTC to the nanosecond; the check takes it from the Run file itself, not only from the Derivation's copy of it. The Series file keeps everything else: the head, each Method's fixed words, its summary (percentiles, groups with their facts and figures, section counts, how many Runs it counts and does not), the list of its months, and the points of its newest Runs in full, so its latest figures take one request. How many is a fixed count, 12 (three days at four Runs a day), written in every Series file as `newest_runs`; those points are the same, value for value, as their month file's. So the number of points in a Series file is bounded; its summaries still grow with what the data hold: a group for each new combination of the machine's split facts, a value for each new distinct value of a request fact, an entry in `months` for each month. A test builds a Series of 24, 192 and 576 Runs, of one machine and one set of request facts, and finds its Series file of one shape (the same keys, array lengths and string lengths) apart from the month list, and the same size but for the digits of its counts.

    Three lists in the Derivations grow with every Run and are not in the Series file; each is recovered exactly from the month files' points, in order of start, then Run id, by the Method's own rule: the Runs behind each of series v1's percentiles of time per repetition are every counted point, since every counted Run has a time per repetition, an infinite one written null included; behind each percentile of bytes per second, every counted point whose `bytes_per_repetition` is not null, since Method series v1 only ever observes a finite positive one; a group's Runs, under either Method, are the points with its letter, counted or not; and the Runs behind one of a group's percentiles are those, filtered as the Series' are. The build refuses Derivations where any of them is not so (`recoverable()` in `scripts/lib/api.ts`), and the check confirms it against the month files it reads.

    A group's letter is given in the order each first appears, and requests v1's `through` pools the counted Runs that started at or before the point, so both depend only on the Runs before it. But requests v1's `group_through` is the group's pooled figures "when the Series has more than one group": when a Run that started later first brings a second group, the Method gives every earlier point its group's figures in place of null, and every earlier month file would change. The tree writes, in its place, `group_through_as_of_run`: the group's figures as they stood through the point's own Run, which no Run that started later changes (a Run that started earlier and arrives late can: cause (c) below). It is null for two reasons: the Series had had Runs of one group only, up to and including that Run; or the point's group had had no counted Run by then, even when `through`, which pools every group, has figures (a group whose first Run failed, say). The Derivation's `group_through` differs from it only on the points before the first point whose group differs from the first point's, in a Series of more than one group, where every Run is of the first group and the Derivation's value is the point's `through`: a reader takes `through` for exactly those points, and `group_through_as_of_run` as it is for every other. Substituting `through` for any other null would give one group's reader the other groups' figures. The field has its own name because it is not the Derivation's field; the build refuses Derivations where the rule would not give back the Derivation's value (`asOfRun()`), the check compares the tree with the Derivations by the same rule, and a test recovers every point's `group_through` with it, the failed first Run of a second group included.

    The contract, then: For a given layout (the layout of v1/index.json), a month file's bytes change only when (a) a Run that started in that month is added, (b) a boot summary that was missing arrives, (c) a Run arrives late, having started before a Run of the Series already in the files, in that month or an earlier one, or (d) a Method first applies to the Series; otherwise they do not change. These four are the only causes for a given layout: layout increases when LedgerMath changes how the files are written, and only then may a file's bytes change without one of them. A past month is therefore not immutable: each entry of the Series file's months gives its month file's sha256 and size in bytes, so a reader holding a copy can tell whether it is current, and fetches the file again only when the sha256 differs. A Series file and a month file fetched together can still be from different updates of the files: a cache may hold one of them from before the other changed, and an update that stopped halfway leaves them so until the next one. So a reader checks the sha256 of every month file it fetches against the one its Series file lists; on a mismatch, it fetches the Series file again, then the month file, and compares again; while they still differ, it uses neither, and tries again later. What each cause changes: (a) the month gains the Run's point, its pair entry and its count and span; (b) the point's `boot_summary` turns from null into the summary's address, and nothing else; (c) as (a), and in that month and every later one the points after the late Run may change only what depends on earlier Runs: their group, and requests v1's `through` and `group_through_as_of_run` (`through`'s counts rise by exactly what the late Runs it pools add, and not at all when none of them is counted), and the pair entry of the Run right after it then comes from the late Run, as the Derivations do; (d) the Method's block appears, under its key, in every month file of the Series: Method requests v1 derives a Series once any of its Runs' streams holds a request, so a Series whose first Runs failed before their first request gains requests v1's block in its past months when a later Run succeeds. (c) and (d) are what the Methods produce, and the tree neither changes the Methods nor hides what they produce; it says instead which file changed, by its sha256. The contract is written, word for word, in `v1/index.json` (`months`, beside `layout`), in the schemas `series` and `series-month`, here and in the README, and a test holds each to it. Its two sentences before "What each cause changes", the reader's rule for a month file that does not match its Series file (ADR-0031, decision 8), were added on 2026-11-23, while the API was still private: until then the tree's words told a reader holding a copy when to fetch it again, but not what to do when a month file just fetched did not match.

    The layout is a number, `LAYOUT` in `scripts/lib/api.ts`, written in `v1/index.json` as `layout` and described in its schema. It is raised whenever the build changes how it writes the files (the order of a file's fields, the white space between them, a field every file of a kind gains), and only then may bytes change without one of the four causes; editing a schema's words does not raise it, and neither do the data. Nor does a field the table of contents alone gains (`recent_rounds`, rule 12, 2026-11-24): the four causes are a month file's, the table of contents changes with the data at every update and no promise covers its bytes, the gate never compares it, and no other file's bytes change with it, so the tree after such a field is compared with the tree before it strictly, as ever, and the first scheduled run after it needs no new baseline. The golden test fails on any change to the bytes the build writes and says so: if the change is on purpose, raise `layout`, unless only the table of contents changed.

    `scripts/check-api.ts --previous DIR` holds a tree to the contract against the tree before it, and the `runs` workflow runs it against the artifact `api` of the latest run on main created before it that kept one (so a re-run of an older run never compares with a later one); a run keeps that artifact only when its tree passed this check, so the choice rests on the check alone, not on how the run ended nor whether it has (ADR-0031: a run whose publish job failed, or is still going, is a baseline). A previous tree of the same layout and base is compared strictly, always. It must first be whole: every month file its Series files list is there with the size and sha256 listed, and nothing more, and every Series its list has has its file; a previous tree that is not is an error, not a baseline. Then every Series and every month file of it must be in the new tree, each month file byte for byte the same or changed only for the four causes, each recognised from the two trees: (a) and (c) by Run ids the Series holds now and did not before (late when placed, by start then Run id, before a Run the previous tree held), (b) by a point's `boot_summary` going from null to an address and nothing else of that point, (d) by a Method's block present now and in no month file nor the Series file of that Series before. A late Run may change, in the points placed after it, only the fields the check lists by Method (`LATE_RUN_MAY_CHANGE`: the group, and requests v1's `through` and `group_through_as_of_run`), and in the pair entry of the Run right after it only its earlier Run and what it compares (`LATE_RUN_MAY_CHANGE_IN_PAIR`). Where the consequence can be checked without redoing the Method, it is, on every published point after a late Run, in a month file that changed or not: `through` is unchanged when no late Run before the point is counted, and otherwise its counts (`runs`, `requests`, `failed`, `failures`) have risen by exactly what the counted ones add, as their points in the new tree state it; a pair entry whose later Run now follows a late Run comes from it. What the gate cannot establish is that a changed cumulative percentile (of `through` or `group_through_as_of_run`), or a changed letter, is right: that is the Method's doing, and the check against the Derivations establishes only that the tree equals them. The check says so in its output with every comparison. No published Run id may disappear. Every file the build writes must be, byte for byte, what the build writes for the value it parses to (`writerForm()`), so that no file differs from its canonical text, and no byte changes but where a value does: a reordered object, a space added or a number respelt fails the check of the tree itself, not only the comparison.

    A previous tree that is missing, empty, of another layout or built for another base fails the check, unless a human declared a new baseline: `--allow-no-previous`, which the workflow passes only from its `workflow_dispatch` input `new_baseline`. Nothing automatic grants it, so the first scheduled run after `layout` is raised, or after the artifact expired, fails until the maintainer starts a run by hand with that input; the check's step summary says the baseline was declared. Even then, whenever the previous tree can be read well enough to list the Series and Runs it published (from its month files in this layout, or from its Series files' `points` in the layout before the split), no Series and no Run of it may be missing from the new tree, and the check reports how many it compared. A previous tree of the same layout is compared all the same.

    When the gate fails on a real late Run of a kind the allowance does not cover, the tree is not kept (the next run compares with the same earlier tree, and fails the same way), and the fix is a reviewed change, never the new-baseline input, which does not apply to a tree of the same layout: find the field that changed; if the Method's definition makes it depend on earlier Runs, add it to `LATE_RUN_MAY_CHANGE` with its consequence check where one can be made, and to cause (c) in every place the contract is written; if it does not, the Method or the tree is wrong.
10. **Every file has a ceiling of bytes, and the check enforces it** (`CEILINGS` in `scripts/lib/api-check.ts`, each with a sentence on what to do when it is hit). From the data of 2026-11-19 with room to spare: the table of contents 100 KB (6.3 KB then; 23.6 KB on 2026-11-24, with the newest rounds of boots), the list of Series 1 MB (193 KB), a Series file 1 MB (302 KB at most), a month file 5 MB (714 KB at most, for nine days; a full month of `http_get` at four Runs a day is about 2.7 MB), a price file 1 MB (39 KB), a schema 256 KB. A ceiling says a file has outgrown what a reader, an agent above all, should fetch in one request; it is raised only once that is decided, not to make the check pass.
11. **Whatever can be checked mechanically, the check checks.** Beyond what the README lists: every file the build writes is, byte for byte, the build's writing of its own parsed value; `v1/index.json` gives this build's `layout`; every file of the tree is reached from `v1/index.json` by following the links in the files; every schema in the tree is a valid JSON Schema by its meta-schema; every file is of a kind exactly one schema the table of contents lists describes, and every schema file is listed; no number in any file of the tree is one a double does not hold exactly; each entry of a Series file's `months` gives its month file's sha256 and size as the tree holds it; each point's `started_at` is its Run file's; the table of contents' newest rounds of boots, and the summaries it leaves out of them, are, value for value, what the checkout's boot summaries and the Derivations make by the check's own reading of rule 12, each address given a file of the checkout and of a shape the API serves. And in `bun test`: the definitions the Series schema and the month schema share are word for word the same, every file of a built tree is of a kind with a ceiling, and no prose of a built tree names a file, document, issue, pull request, ADR, function or option a reader of the API alone cannot fetch (rule 5).
12. **The table of contents says what was measured most recently: the newest rounds of boots** (added on 2026-11-24, the API being public). The home page lists the latest rounds ("19 Nov 2026, 16:11 UTC · 5 machines · 187 Runs · 0 failed"), and it may show only what the API gives, adding nothing up; an agent asking whether the data are fresh needs the same. `recent_rounds` in `v1/index.json` holds the newest 8 rounds, newest first, each with when its first boot started (`started_at`), how many boots (`boots`) and their instance types, how many Runs they left (`runs`), how many of those are failed (`failed_runs`) and how many are in no Series, how many builds failed and how many executions were not run, in all and by boot (`by_boot`), each boot with its summary's address; the boot summaries in no round (`left_out`, below); and `about`, which says what a round is, what each figure counts and when a round shown changes.

    **A round is worked out from the boot summaries alone.** Nothing a boot records says that the schedule started it, or for which boot time: the launch's scheduled time stays in its payload and its client token, and reaches neither the box, a Run nor a boot summary. The schedule is this repository's configuration, not a recorded fact, and no clock is read (rule 7). So the boots are taken in order of their summaries' `started_at` (then path), and a boot starts a new round when it started more than 40 minutes after the boot before it, to the nanosecond. The schedule starts a round's boots ten minutes apart and its rounds six hours apart, and the launch starts no scheduled boot more than ten minutes late, so a round stays whole with two machine types in a row refused a boot, or one refused and the next as late as a boot may start (about 31 minutes between two boots); rounds stay apart while they are more than 40 minutes apart; a boot started by hand away from the schedule's times is a round of its own, and one started within 40 minutes of a round's boot joins it; a machine type the schedule gains, ten minutes from the others, joins its round. On the 274 boot summaries of 2026-11-10 to 24 it gives 59 rounds: each scheduled round its five boots, the newest still arriving, and the seven boots started by hand five rounds of their own (one boot on 2026-11-10 at 23:36 and one 47 minutes later, two on 2026-11-11 at 13:44, two at 21:23, one on 2026-11-18 at 19:55). The same boot summaries, in any order, give the same rounds and the same bytes. A boot is in the rounds once its summary is, which it writes when it ends, so the newest round may gain boots at a later update: the workflow runs at 22:40 UTC, half an hour into the 22:10 round. **Any round shown may change, not only the newest** (added with the verification of #91): a summary that arrives late joins the round its start falls within, which gains a boot and its figures, may start earlier, and becomes one round with its neighbour when the boot started within 40 minutes of both, so that a round further back moves into the list or out of it; a summary that arrives in conflict with one already read (naming its boot, or listing one of its Runs) takes that boot out, which may split its round; a Run file that arrives late moves its Run from in no Series to counted or failed. `about` says so, and a test joins two shown rounds with a summary that arrives late.

    **Failed is what the Series' own figures say.** A Run is failed when Method requests v1 does not count it, for a Run of a Series requests v1 derives (a Series of requests), and when Method series v1 does not, for a Run of any other Series. A Run of requests that exited 4, a request having failed, is counted by requests v1 with its failed requests (ADR-0028) and not by series v1: it is not failed here, as `requests_v1.failed_runs` of its Series' file does not count it either. A Run the summaries list of which no Method has a point (no Run file in the evidence, or one no Method could read) is in no Series, counted apart (`runs_in_no_series`), neither counted nor failed. Every figure is a count of what the boot summaries and the points hold, one click from its evidence: a boot's Runs, failed builds and executions not run are the lists of the summary its `boot_summary` links, and each failed Run is a point with `counted: false` in its Series' month file. A round's figures are its boots' summed. Eight rounds is two days at four a day: the last whole day is there even while the newest round is still arriving, and the home page's three.

    **In the table of contents, with the layout unchanged.** The table of contents already changes at every update and already carries `newest_run_started_at`; v1 only ever gains fields (rule 6), so no reader breaks, and the field needs no new address, so neither the edge's served shapes (ADR-0031, decision 1) nor the production stage change. `layout` stays 1 (rule 9): no other file's bytes change, the four causes being a month file's. Built from the same inputs, the tree before the change and the tree after it differ in `v1/index.json` and the index schema alone; `check-api.ts --previous` passed with the tree of the scheduled run of 2026-11-24 22:43 UTC as the previous tree (187 month files, every one the same byte for byte) and with `main`'s golden tree of the small fixture, both without `--allow-no-previous`, so the first run after the change needs no new baseline.

    **No boot summary stops the build or the check; one the rounds cannot be told from is left out, and listed** (as built first, the build refused such a file, and the verification of #91 showed that one summary holding `{`, recorded once and never edited, would have stopped every later publish). Every regular file under `boots/` is listed, whatever its name, by the bytes of its name (a third verification found a name that is not UTF-8, decoded and then opened by the text it decoded to, stopped the build), and only one at an address the API serves is opened: any other is left out by its name alone. A path is written with each byte that is not printable ASCII, and each `%`, `"` and `\`, as `%XX`, so two names whose bytes differ stay two and each character is one byte in JSON. Nothing else is read: a symbolic link (to a summary, a directory or nothing) and a directory are not, by the build and the check alike (the check had followed a symbolic link and counted a summary twice). A file is left out, with the first reason that applies, each one fixed sentence (`LEFT_OUT_WHY`): its address is not one the API serves (by `isServedKey`, the list of served shapes the edge is made from: a boot whose id could not be read writes `unknown.json`, which the edge answers 404); it is not strict JSON; it is not `ledgermath.boot/1`; it names no boot, gives no start that is a real UTC time to the nanosecond, no provider with an instance type of 1 to 64 letters, digits, dots, hyphens or underscores, or none, no list of Runs with their ids, or no lists of failed builds and executions not run; it is not at the path its own contents give, `boots/<the UTC day of its own started_at>/<its own boot>.json`, where the runner writes it. Then, across every summary of every day, not only the rounds shown: of two or more of one boot, every one but the one that started first; every one listing a Run whose point is of another boot; and of the rest, every one listing a Run twice or one another lists. A boot left out is in no round. `recent_rounds.left_out` gives how many are left out, of every day, and the newest 8 by path, each with its path (when longer than 120 characters, its first 101, `...` and the first 16 hex digits of the SHA-256 of the whole, so that two paths cut alike are still told apart), its address when served (else null) and why. **What boot summaries can write into the table of contents is bounded, whatever they hold** (#76; the verification of #91 found an instance type of 100,000 characters put the table of contents at 210,936 bytes, over its ceiling, which would have stopped every publish): bounded in bytes as written, not in characters (the third verification found 64 characters JSON writes as six bytes each put the table of contents at 112,048 bytes): an instance type is 1 to 64 letters, digits, dots, hyphens or underscores (AWS's are under 20 characters), one byte each, and a summary giving anything else is left out; a listed path is at most 120 characters of one byte each; every other string has a fixed shape (a start, an address of a served shape) or is one of `LEFT_OUT_WHY`; a round lists at most 12 boots in `by_boot` and `instance_types`, the first by start, while its figures count every boot (a round of the schedule has five); counts are numbers. At every bound at once (eight rounds of twenty boots, twelve listed, every instance type 64 characters, every count 2^53 − 1, eight paths each the longest a path is written), the rounds and the summaries left out take 48,297 bytes as written, which a test measures and holds under 52,000; with the rest of the table of contents of 2026-11-24 (12,076 bytes, growing 124 bytes a day with the price files) that is 60,373 bytes, under the 100,000-byte ceiling. A summary at a served address that cannot be read keeps its address in the list, so a reader can fetch it. The check reads the checkout's summaries itself, leaves out and works the rounds out by its own reading of this rule, compares both value for value, requires every address it gives to be a file of the checkout and of a served shape, and requires `about` to begin, word for word, with the rule and the count it holds the rounds to (`ROUND_RULE`), the rest being free to explain. Throws remain only on one path given twice, which no checkout can hold.

    **Two summaries of one boot, and one that cannot be read, stop no publish either** (found with the verification of #91, on `main` as on the first build of this rule). Until then the build stopped when two files had one boot's name (two boots whose id could not be read, each writing `unknown.json` on its day, would do it), and the check failed when a point's boot had two summaries; it also failed on a single boot whose id could not be read and that left a Run, expecting its point to link `unknown.json`, which its boot (empty) never names, and on a point whose boot's summary cannot be read, which the build linked by name. A first fix, linking the first in path order of the files named by the boot's id, failed a second verification of #91: a real summary of 2026-11-11 copied to an earlier dated path took over 37 month files' links, and every later publish would have failed the gate. **A file added to the Runs data can fill a missing link, and never change or remove one**: that is the rule's one property, and the build keeps it without reading the tree before. A point links its boot's summary: of the files a round can read (each on its own, as above: of a served shape, at the path its own contents give, with what a round needs), the one of its boot that started first; else none, and never an address the edge does not serve (the build refuses one whatever its sources say, and the check tests every point's link against the served shapes). A copy at any other path, a file that cannot be read, a summary named by no UUID (`unknown.json`, or a name of the test fixture's kind) and a symbolic link are no candidate, so adding one changes nothing; a second candidate of a boot started later never displaces the first; what a candidate lists, or what another file lists, does not count, so no later file can take a link away. **One case remains, and no rule without the files' history can close it**: a second summary of a boot, at its own path, claiming an earlier start than the first. Each of the two files is consistent with itself, and only the order they arrived in tells them apart. The one that started first is then the boot's, in the rounds and in its points' links; the other is listed as left out ("another summary of the same boot, at its own path, started earlier"); and the gate refuses the changed link, out loud, until a person settles it. Such a file cannot be a copy: it must be written for a real boot's id with a start of its own, which no box does. A test adds every other kind of file, alone and in pairs, and holds the build, the check, the gate, every link and the ceiling (`tests/api-additions.test.ts`); another shows this case is seen. On the data of 2026-11-24 no month file changes, and the copy of 2026-11-11 at an earlier path changes none either. Three things the rule implies, none of which the real data show, and each of which the gate would refuse out loud: **a summary filed under a day that is not its own `started_at` day**, as the only copy, is not linked, where `main`'s rule linked it by its name; that the move to this rule changes nothing published was checked against the tree published on 2026-11-24 (all 187 month files the same byte for byte), and had such a file existed the gate would have refused the first publish. **A summary rewritten at its address so that it can no longer be read** loses its link, and the gate refuses that: the rule relies on the Runs repository only ever being added to, never edited, as it is. **The open case needs no forged file**: the runner takes `started_at` when its process starts, so two runs of the runner on one booted kernel, one before midnight UTC and one after, write two honest summaries of one boot on two days, the second claiming the later start and the first the earlier; if the later one arrived first and was linked, the earlier one arriving would change the link. The box's script runs the runner once and shuts the box down, so this takes someone running the runner again by hand on a box: that is the precondition.

## Rejected

- **Serving the files of Derivations as they are.** One file of 60 MB, growing with every Run, that a reader must fetch whole to read one number.
- **A file per Method per Series** (`series/<id>/series-v1.json`). A reader would need two fetches for an `http_get` Series, and attribution is already plain from the key.
- **A time of generation in the files.** It would change every file on every run of the workflow, unchanged or not, and defeat every cache. The data's own moment says what a reader needs: how far the data reach.
- **A "latest" price file**, or a summary of the prices. The maintainer ruled it out; the table of contents marks the newest file.
- **Leaving out each Run's samples.** They are evidence; with the split, they cost a month file, not the Series file.
- **A Series file holding every point, or every Run id.** It would pass 30 MB within a year. The lists of Run ids behind the percentiles and in the groups are recoverable from the month files, so they are left out rather than moved.
- **A unit smaller than a month, or a fixed number of Runs per file.** A month is a unit a reader can name and an agent can cite; at four Runs a day its largest file is about 2.7 MB. Files of a fixed number of Runs would have no such name, and their last file would change with every Run.
- **`group_through` exactly as the Method writes it.** Every month file of a Series would change the day a Run first splits it. The tree writes it as it stood through the Run, and the Derivation's value stays recoverable (rule 9).
- **That value under the Derivation's name, `group_through`.** It is not the Derivation's value on the points before a Series' first split, and a reader who took it for that would read a null as "no group figures yet" and reach for `through`; a field's name in `v1` is kept for good, so it is named for what it holds.
- **Telling a tree's layout by its schemas' bytes.** A schema's words can change without a byte of any other file changing, and then a previous tree would be "of another layout" and compared with nothing: one newline in a schema let a tree that had lost a Series pass. The layout is a number the build writes and a human raises.
- **Granting the new baseline automatically** (when the artifact expired, or the layout changed). Each such case let a tree pass compared with nothing. Only a human declares a new baseline, and even then nothing published may be missing.
- **Excusing every change after a late Run.** A late Run before a point let any value of it change, a count of 999 included. Only the fields that depend on earlier Runs may, and their counts are held to what the late Runs add.
- **Rounds from `schedule.json`'s boot times** (rule 12). It is configuration, edited freely (ADR-0029, rule 2): a past day's rounds would change with today's schedule, and a boot by hand fits no boot time.
- **A boot recording that the schedule started it, and for which time** (rule 12). It would be the best fact to group by, but no boot records it so far, the box is not changed for the API, and the Runs already written could never gain it; rounds from the starts serve every boot, those included.
- **A new round when a boot starts more than 60 minutes after the round's first boot** (rule 12, the first proposal). On 2026-11-11 the two boots started by hand at 21:23 became a round's first boots, and that round took the scheduled boots of 22:11 and 22:21, two of them `m5.large`, leaving 22:31 to 22:51 a round of three; measured from the boot before, the two stay apart. It would also split any round longer than an hour, as a schedule of more machine types would make.
- **A gap of 30 minutes** (rule 12). It gives the same rounds on the data so far, but splits a round in which two machine types in a row are refused a boot, which a shortage of capacity in one zone makes likely together.
- **Failed by series v1 for every Run, or by either Method** (rule 12). A Run of requests that exited 4 would be failed here and counted in its Series' figures of requests.
- **Refusing a boot summary the rounds cannot be told from** (rule 12, as first built). The Runs repository is never edited and every update reads every summary again, so one bad file would stop every later publish: the Series and prices would go stale with the rounds. Leaving it out, and listing it, keeps every number true and the API current.
- **Linking a point to the first, in path order, of the files named by its boot's id** (rule 12, second build). A copy at an earlier path took the link over. The candidate must be at the path its own contents give, and the earliest start among candidates wins, so only a file claiming an earlier start at its own path can change a link.
- **Leaving every summary of a boot two name out, and its points unlinked.** A second file arriving would take a link that was published away, which the contract forbids; the one that started first keeps it.
- **Listing every boot of a round, and an instance type of any length.** One file's long string, or many boots in one round, could put the table of contents over its ceiling and stop every publish; twelve boots and 64 characters are far above the schedule's five and AWS's longest.
- **Listing only the summaries left out that could belong to the rounds shown.** One that cannot be read has no start to place it by; its path gives its day, which the list shows, and the count covers every day, so a reader can tell.
- **A file of its own for the rounds** (`v1/rounds.json`, rule 12). A new address the edge does not serve, so a deploy of the production stage, and a second fetch for the home page and for every agent asking whether the data are fresh, for 15 KB.
- **Promising that a past month never changes.** It would be false: a late Run and a Method first applying change past months, and both are what the Methods produce. Changing the Methods, or holding back their output, to keep the promise would make the API a Method of its own (rule 4). Saying exactly when a month file changes, and giving each one's sha256 in the Series file, keeps every number true and lets a reader trust a cached copy anyway.

## Costs

- What grows is the month files. Measured between the builds of two snapshots of 2026-11-19 (`page-3` and `page-4`) in which every Series gained one Run: a month file grows by 4,182 to 4,537 bytes a Run for the 162 Series of the other benchmarks, and 9,943 to 21,951 bytes a Run for the 25 `http_get` Series, whose samples are its requests; a Series file changed by −24 to +27 bytes (the digits of its counts) and, for `http_get`, by up to 822 bytes (one newest point in for another, of a different size). A full month at four Runs a day is so about 0.56 MB, or 2.7 MB for `http_get`; a year adds twelve month files and twelve entries (about 2 KB) to the Series file. The whole tree grows by about 1.8 GB a year at that rate, and the files of Derivations the same way: the `runs` workflow keeps the whole tree as an artifact, for 7 days (the next run's check needs only the latest), and reads the whole of both files of Derivations, every day. Comparing a tree with the one before reads every month file of both: about 2 s on the data of 2026-11-19, on a loaded machine.
- The table of contents lists every price file, so it gains 124 bytes a day, and reaches its ceiling about two years on. Listing the price files by month, as the Series are, would change `v1/index.json`'s shape; it is left until then, and the ceiling's sentence says so. Since 2026-11-24 it also holds the newest rounds of boots: 13.3 KB for eight rounds of five boots, about 300 bytes a boot, growing with the boots a round holds and not with time, and 2.1 KB of words and the summaries left out (at most eight listed, each with one of a fixed few sentences): 23.6 KB in all with 14 price files, which brings the ceiling about 20 months on. Every reader's first fetch is so 15.4 KB larger, about 3.2 KB with gzip. At every bound at once the rounds and the summaries left out take 48,297 bytes as written (rule 12). The build reads every boot summary at every update (274, 3.9 MB, in 4 ms on 2026-11-24); a build took 0.6 s with the rounds as without.
- Once `v1` is served, a published Method version's output keeps its shape for as long as the API serves it (`methods/README.md` already freezes a version once its data are published), and a Method version can leave the files only in a new API version.
- A point's `boot_summary` is null while the Runs repository holds no summary of its boot. The box uploads the summary with the boot's Runs, so a month file (and its Series file, whose `months` gives the month file's sha256) changes once more only if the workflow copies between the two; it is cause (b) of rule 9.
- `docs` names the README's section until the docs have pages of their own (#64, decision 9); the README is readable there once the repository is public, which it has been since 2026-11-25.
