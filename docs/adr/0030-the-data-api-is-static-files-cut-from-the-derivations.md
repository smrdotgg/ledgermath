# The data API is static files cut from the Derivations

LedgerMath's first readers are agents, and what they read is a data API (#64, decision 1). It is a tree of small static JSON files, each kind with a JSON schema, regenerated by the `runs` workflow from the Derivations that workflow already makes and from the daily price files. It is a re-cut of the Derivations, not a new Method: it computes no statistic, and every number in it is a Derivation's, written exactly as the Derivation holds it. The decisions below were agreed with the maintainer on 2026-11-18 and 2026-11-19 (#64 and its two last comments); `scripts/build-api.ts` builds the tree and `scripts/check-api.ts` checks it (README, "The data API"). The tree is built in private and kept as the workflow's artifact `api`. Serving it is the next step, and making it public needs the maintainer's explicit go.

## The layout

Everything is served from one host, `https://api.ledgermath.com`, and the tree is laid out exactly as it is served from that host's root:

| Path | Holds |
|---|---|
| `v1/index.json` | The table of contents: the list's address, every price file held with the newest marked, the schemas, the docs' address, and the template of a blob's address |
| `v1/series.json` | One row per Series: what it is (benchmark, params, build, instance type, zone ID), how many Runs, its oldest and newest Run, a summary of each Method's Derivation of it, and the `url` of its own file; and each Method's own words, with the Run files it could not read |
| `v1/series/<id>.json` | One Series: its identity and span, each Method's words and summary (percentiles, groups and their facts and figures, section counts, counted and failed Runs), the points of its newest 12 Runs, and its months, each with its address, its count of Runs and its first and last start |
| `v1/series/<id>/<yyyy-mm>.json` | One month of a Series: every point of the Runs that started that month (UTC, by the Run's start), each Method's under its key, each with the sha256 of its Run file and an `evidence` link to it, and series v1's entries for the pairs of consecutive Runs whose later Run started that month |
| `v1/prices/<yyyy-mm-dd>.json` | That day's price file, byte for byte as the Runs repository holds it. There is no summary and no "latest" file |
| `v1/schemas/<name>.schema.json` | The schema of each kind of file: `index`, `series-list`, `series`, `series-month` (kept in `schemas/api/v1/`) and `prices` (`schemas/prices.schema.json`) |

The evidence is served from the same host at the bucket's own keys, `/runs/<yyyy>/<mm>/<dd>/<id>.json`, `/boots/<yyyy>/<mm>/<dd>/<boot>.json` and `/blobs/sha256/<hex>`. The tree links it and never copies it.

## The rules

1. **Static files, not a server.** A query server is added only when static files demonstrably fail (#64, decision 2). The one large file of Derivations, 60 MB on 2026-11-19, is split into a list, a file per Series and a file per month of each Series.
2. **Every address a reader needs is written in the files.** Each row carries its Series file's `url`, each Series file the `url` of each of its months, each month file its Series file's `series_url`, each point its Run file's `evidence` and its boot's `boot_summary`, each unreadable Run file its `evidence`, and the table of contents every other file's address; a reader never builds an address from an id. One exception is unavoidable: a Run file names its binary, streams and dumps by hash, and a Run file is never edited, so `v1/index.json` gives the blob address as a template, `…/blobs/sha256/{hex}`. All addresses start with a base taken from an option, so a private or test address can stand in for `https://api.ledgermath.com`.
3. **Exact figures, and none loses a digit.** Nothing is rounded, in the API or on the page. Numbers are parsed from the Derivations and written back by `JSON.stringify`, as the Derivations were written, so each reads back as the same number, digit for digit. The build reads every number of both files of Derivations as text too (`scripts/lib/strict-json.ts`, `exactNumbers`), and refuses the file, naming it, the number's place as a JSON Pointer and the number, when the number's decimal value is not exactly the value of what it would write: an integer past 2^53 (`9007199254740993`, written `9007199254740992`), a value past a double's range (`1e400`, Infinity, written `null`) or below it (`1e-400`, written `0`), more digits than a double holds (`0.10000000000000001`, written `0.1`). A number written otherwise with the same value passes (`1e3`, written `1000`). `-0` passes and is written `0`: it is the value zero, which is all a decimal number says, and `JSON.stringify` writes every negative zero as `0`, so no Method emits one. Most numbers (95% on 2026-11-19) have at most 15 characters and no exponent, and are exact without being converted (a double holds 15 significant decimal digits); the rest are converted once. Reading the 60 MB file so costs about 0.25 s more than `JSON.parse` alone. The check reads every file of the tree the same way.
4. **A re-cut, not a Method.** A number the Derivations do not hold is not in the API. The only figures added are taken straight from a Series' points: how many Runs it has, in all and in each month, how many each Method counts and does not, how many groups, and when its oldest and newest Run started, in all and in each month. The newest is the moment a citation of the Series names (ADR-0029, decision 12).
5. **Each Method's output is labelled with its name and version.** A row, a Series file and a month file hold each Method's part under `derivations.<name>_v<version>`, each with its `method`, at the same paths and in the same words as the Method's file, so the two can be compared by eye. A Series can carry two: the 25 `http_get` Series are in both `series_v1` and `requests_v1`, 187 Series in all on 2026-11-19. The build stops if the two Methods cite different Runs for one Series. A Series file carries its Methods' definitions, so it can be read alone.
6. **`v1` only ever gains fields.** A field, once in a `v1` file, keeps its name, its type and its meaning, and a reader ignores fields it does not know, so no object in the API's own schemas (`index`, `series-list`, `series`, `series-month`) forbids members it does not list. A new Method, or a new version of one, is a new key beside the old ones. A change that would break a reader is published as `v2`, beside `v1`. The table of contents and every one of those schemas say so. The price files are the exception: each is the Runs repository's price file, byte for byte, and follows its own schema, `ledgermath.prices/1`, whose root and LedgerMath's own objects are closed. The check validates every file against this repository's schemas, with every object of the API's own closed, so a field the schemas do not describe still fails the build. Because the files only re-cut what the Methods emit, the schemas admit everything the Methods can emit, not only what today's data show: a percentile of bytes per second, for one, can be null, when a counted Run's time per repetition is 0; and a percentile of time per repetition, when a counted Run's time per repetition, the mean of its two middle samples, overflows a double.
7. **The same inputs give the same bytes.** File for file, whatever order the Series, price files and boot summaries come in, and whatever order the members of any object come in: known fields are written in the order their schema lists them, and the keys of a free-form object (params, a group's facts, a Method's definitions, a Service's inputs) in JavaScript's default string order, by UTF-16 code unit, which is byte order for the ASCII names in use. Because the order of known fields follows the order of the schemas' properties, reordering a schema's properties would change the bytes of every file and empty every cache; a golden test (`tests/api-golden.test.ts`) compares every file the build writes from a small fixture with a committed copy, so such a change, or any other change to the bytes, shows in review as a diff of the copies. No clock is read. A Series file depends only on its own Runs, its Methods' words and the base address, so a Series that gained no Run keeps its file byte for byte and caches go on holding it; a month file depends only on its month's Runs, the Runs before them in its Series and the base (rule 9). No file carries the time it was made. `v1/index.json` and `v1/series.json` carry the data's own moment instead, the start of the newest Run of any Series.
8. **What a Method could not count, or read, is shown.** A Run a Method does not count is a point with `counted: false` and its `failure`, linked to its evidence and counted in the row and the Series file as `failed_runs`. A Run file no Method could read is in no Series; `v1/series.json` lists it under each Method's `unreadable`, with why and its `evidence`.
9. **Each Series is split by month, and a month, once passed, does not change** (#64, decision of 2026-11-19, built before the API goes public). What grows with every Run is in the month files, never in the Series file: each Method's points, and series v1's `differed` entry for each pair of consecutive Runs, filed under the month of the later Run (so the first entry of a month may come from the previous month's last Run). A Run's month is the first seven characters of its `started_at`, which the Run schema writes in UTC to the nanosecond. The Series file keeps everything else: the head, each Method's fixed words, its summary (percentiles, groups with their facts and figures, section counts, how many Runs it counts and does not), the list of its months, and the points of its newest Runs in full, so its latest figures take one request. How many is a fixed count, 12 (three days at four Runs a day), written in every Series file as `newest_runs`; those points are the same, value for value, as their month file's. The Series file does not grow with its Runs beyond one entry a month: a test builds a Series of 24, 192 and 576 Runs and finds its Series file of one shape (the same keys, array lengths and string lengths) apart from the month list, and the same size but for the digits of its counts.

    Three lists in the Derivations grow with every Run and are not in the Series file; each is recovered exactly from the month files' points, by the Method's own rule: the Runs behind each of series v1's percentiles of time per repetition are the counted points (of the Series, or of the group), since every counted Run has a time per repetition, an infinite one written null included; behind each percentile of bytes per second, the counted points whose `bytes_per_repetition` is not null, since Method series v1 only ever observes a finite positive one; and a group's Runs, under either Method, are the points of its letter. The build refuses Derivations where any of them is not so (`recoverable()` in `scripts/lib/api.ts`), and the check confirms it against the month files it reads.

    Nothing in a point depends on later Runs but one field. A group's letter is given in the order each first appears, and requests v1's `through` pools the counted Runs that started at or before the point, so both depend only on the Runs before it. But requests v1's `group_through` is the group's pooled figures "when the Series has more than one group": when a later Run first brings a second group, the Method gives every earlier point its group's figures in place of null, and every earlier month file would change. Before the Series' first Run of a second group every Run is of the first group, whose figures are the Series' own, so the Derivation's value there is exactly the point's `through`. The tree writes `group_through` as it stood through each Run, null on those points, and the schemas say how to recover the Derivation's value (that point's `through`, when the Series has more than one group); the build refuses Derivations where it is not so (`asOfRun()`).

    A month file thus changes only when a Run of its month is added, and when a boot summary that was missing arrives (`boot_summary` turns from null into its address; see Costs). Adding a Run after every Run of its Series leaves every earlier month file of every Series byte for byte, whatever the new Run does to the groups; a test shows it, on a Run that splits a Series. A Run that arrives after a later Run of its Series is added to its own month, and changes every later month's `differed`, `through`, `group_through` and letters, as it changes the Derivations: `scripts/check-api.ts --previous DIR` compares every month file with the tree readers were last served and reports each that changed otherwise.
10. **Every file has a ceiling of bytes, and the check enforces it** (`CEILINGS` in `scripts/lib/api-check.ts`, each with a sentence on what to do when it is hit). From the data of 2026-11-19 with room to spare: the table of contents 100 KB (4.9 KB then), the list of Series 1 MB (193 KB), a Series file 1 MB (302 KB at most), a month file 5 MB (714 KB at most, for nine days; a full month of `http_get` at four Runs a day is about 2.7 MB), a price file 1 MB (39 KB), a schema 256 KB (32 KB). A ceiling says a file has outgrown what a reader, an agent above all, should fetch in one request; it is raised only once that is decided, not to make the check pass.
11. **Whatever can be checked mechanically, the check checks.** Beyond what the README lists: every file of the tree is reached from `v1/index.json` by following the links in the files; every schema in the tree is a valid JSON Schema by its meta-schema; every file is of a kind exactly one schema the table of contents lists describes, and every schema file is listed; no number in any file of the tree is one a double does not hold exactly. And in `bun test`: the definitions the Series schema and the month schema share are word for word the same, and every file of a built tree is of a kind with a ceiling.

## Rejected

- **Serving the files of Derivations as they are.** One file of 60 MB, growing with every Run, that a reader must fetch whole to read one number.
- **A file per Method per Series** (`series/<id>/series-v1.json`). A reader would need two fetches for an `http_get` Series, and attribution is already plain from the key.
- **A time of generation in the files.** It would change every file on every run of the workflow, unchanged or not, and defeat every cache. The data's own moment says what a reader needs: how far the data reach.
- **A "latest" price file**, or a summary of the prices. The maintainer ruled it out; the table of contents marks the newest file.
- **Leaving out each Run's samples.** They are evidence; with the split, they cost a month file, not the Series file.
- **A Series file holding every point, or every Run id.** It would pass 30 MB within a year. The lists of Run ids behind the percentiles and in the groups are recoverable from the month files, so they are left out rather than moved.
- **A unit smaller than a month, or a fixed number of Runs per file.** A month is a unit a reader can name and an agent can cite; at four Runs a day its largest file is about 2.7 MB. Files of a fixed number of Runs would have no such name, and their last file would change with every Run.
- **`group_through` exactly as the Method writes it.** Every month file of a Series would change the day a Run first splits it. The tree writes it as it stood through the Run, and the Derivation's value stays recoverable (rule 9).

## Costs

- What grows is the month files. Measured between the builds of two snapshots of 2026-11-19 (`page-3` and `page-4`) in which every Series gained one Run: a month file grows by 4,182 to 4,537 bytes a Run for the 162 Series of the other benchmarks, and 9,943 to 21,951 bytes a Run for the 25 `http_get` Series, whose samples are its requests; a Series file changed by −24 to +27 bytes (the digits of its counts) and, for `http_get`, by up to 822 bytes (one newest point in for another, of a different size). A full month at four Runs a day is so about 0.56 MB, or 2.7 MB for `http_get`; a year adds twelve month files and twelve entries (about 2 KB) to the Series file. The whole tree grows by about 1.8 GB a year at that rate, and the files of Derivations the same way: the `runs` workflow keeps the whole tree as an artifact, and reads the whole of both files of Derivations, every day.
- The table of contents lists every price file, so it gains 124 bytes a day, and reaches its ceiling about two years on. Listing the price files by month, as the Series are, would change `v1/index.json`'s shape; it is left until then, and the ceiling's sentence says so.
- Once `v1` is served, a published Method version's output keeps its shape for as long as the API serves it (`methods/README.md` already freezes a version once its data are published), and a Method version can leave the files only in a new API version.
- A point's `boot_summary` is null while the Runs repository holds no summary of its boot. The box uploads the summary with the boot's Runs, so a month file (and a Series file, for a newest point) changes once more only if the workflow copies between the two; it is the one change a past month may see (rule 9).
- `docs` names the README's section until the docs have pages of their own (#64, decision 9); the README is readable there once the repository is public.
