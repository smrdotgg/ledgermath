# The data API is static files cut from the Derivations

LedgerMath's first readers are agents, and what they read is a data API (#64, decision 1). It is a tree of small static JSON files, each kind with a JSON schema, regenerated by the `runs` workflow from the Derivations that workflow already makes and from the daily price files. It is a re-cut of the Derivations, not a new Method: it computes no statistic, and every number in it is a Derivation's, written exactly as the Derivation holds it. The decisions below were agreed with the maintainer on 2026-11-18 and 2026-11-19 (#64 and its two last comments); `scripts/build-api.ts` builds the tree and `scripts/check-api.ts` checks it (README, "The data API"). The tree is built in private and kept as the workflow's artifact `api`. Serving it is the next step, and making it public needs the maintainer's explicit go.

## The layout

Everything is served from one host, `https://api.ledgermath.com`, and the tree is laid out exactly as it is served from that host's root:

| Path | Holds |
|---|---|
| `v1/index.json` | The table of contents: the list's address, every price file held with the newest marked, the schemas, the docs' address, and the template of a blob's address |
| `v1/series.json` | One row per Series: what it is (benchmark, params, build, instance type, zone ID), how many Runs, its oldest and newest Run, a summary of each Method's Derivation of it, and the `url` of its own file; and each Method's own words, with the Run files it could not read |
| `v1/series/<id>.json` | One Series in full: each Method's Derivation of it, every point with the sha256 of its Run file and an `evidence` link to it |
| `v1/prices/<yyyy-mm-dd>.json` | That day's price file, byte for byte as the Runs repository holds it. There is no summary and no "latest" file |
| `v1/schemas/<name>.schema.json` | The schema of each kind of file: `index`, `series-list`, `series` (kept in `schemas/api/v1/`) and `prices` (`schemas/prices.schema.json`) |

The evidence is served from the same host at the bucket's own keys, `/runs/<yyyy>/<mm>/<dd>/<id>.json`, `/boots/<yyyy>/<mm>/<dd>/<boot>.json` and `/blobs/sha256/<hex>`. The tree links it and never copies it.

## The rules

1. **Static files, not a server.** A query server is added only when static files demonstrably fail (#64, decision 2). The one large file of Derivations, 60 MB on 2026-11-19, is split into a list and a file per Series.
2. **Every address a reader needs is written in the files.** Each row carries its Series file's `url`, each point its Run file's `evidence` and its boot's `boot_summary`, each unreadable Run file its `evidence`, and the table of contents every other file's address; a reader never builds an address from an id. One exception is unavoidable: a Run file names its binary, streams and dumps by hash, and a Run file is never edited, so `v1/index.json` gives the blob address as a template, `…/blobs/sha256/{hex}`. All addresses start with a base taken from an option, so a private or test address can stand in for `https://api.ledgermath.com`.
3. **Exact figures.** Nothing is rounded, in the API or on the page. Numbers are parsed from the Derivations and written back by `JSON.stringify`, as the Derivations were written, so each reads back as the same number, digit for digit. The figures are the numbers the Methods serialise, which are IEEE 754 doubles; a producer that emitted integers above 2^53 or values outside a double's range would lose them here.
4. **A re-cut, not a Method.** A number the Derivations do not hold is not in the API. The only figures added are taken straight from a Series' points: how many Runs it has, how many each Method counts and does not, how many groups, and when its oldest and newest Run started. The newest is the moment a citation of the Series names (ADR-0029, decision 12).
5. **Each Method's output is labelled with its name and version.** A row and a Series file hold each Method's Derivation under `derivations.<name>_v<version>`, each with its `method`, at the same paths and in the same words as the Method's file, so the two can be compared by eye. A Series can carry two: the 25 `http_get` Series are in both `series_v1` and `requests_v1`, 187 Series in all on 2026-11-19. The build stops if the two Methods cite different Runs for one Series. A Series file carries its Methods' definitions, so it can be read alone.
6. **`v1` only ever gains fields.** A field, once in a `v1` file, keeps its name, its type and its meaning, and a reader ignores fields it does not know, so no object in the API's own schemas (`index`, `series-list`, `series`) forbids members it does not list. A new Method, or a new version of one, is a new key beside the old ones. A change that would break a reader is published as `v2`, beside `v1`. The table of contents and every one of those schemas say so. The price files are the exception: each is the Runs repository's price file, byte for byte, and follows its own schema, `ledgermath.prices/1`, whose root and LedgerMath's own objects are closed. The check validates every file against this repository's schemas, with every object of the API's own closed, so a field the schemas do not describe still fails the build. Because the files only re-cut what the Methods emit, the schemas admit everything the Methods can emit, not only what today's data show: a percentile of bytes per second, for one, can be null, when a counted Run's time per repetition is 0; and a percentile of time per repetition, when a counted Run's time per repetition, the mean of its two middle samples, overflows a double.
7. **The same inputs give the same bytes.** File for file, whatever order the Series, price files and boot summaries come in, and whatever order the members of any object come in: known fields are written in the order their schema lists them, and the keys of a free-form object (params, a group's facts, a Method's definitions, a Service's inputs) in JavaScript's default string order, by UTF-16 code unit, which is byte order for the ASCII names in use. Because the order of known fields follows the order of the schemas' properties, reordering a schema's properties would change the bytes of every file and empty every cache; a golden test (`tests/api-golden.test.ts`) compares every file the build writes from a small fixture with a committed copy, so such a change, or any other change to the bytes, shows in review as a diff of the copies. No clock is read. A Series file depends only on its own Runs, its Methods' words and the base address, so a Series that gained no Run keeps its file byte for byte and caches go on holding it. No file carries the time it was made. `v1/index.json` and `v1/series.json` carry the data's own moment instead, the start of the newest Run of any Series.
8. **What a Method could not count, or read, is shown.** A Run a Method does not count is a point with `counted: false` and its `failure`, linked to its evidence and counted in the row as `failed_runs`. A Run file no Method could read is in no Series; `v1/series.json` lists it under each Method's `unreadable`, with why and its `evidence`.

## Rejected

- **Serving the files of Derivations as they are.** One file of 60 MB, growing with every Run, that a reader must fetch whole to read one number.
- **A file per Method per Series** (`series/<id>/series-v1.json`). A reader would need two fetches for an `http_get` Series, and attribution is already plain from the key.
- **A time of generation in the files.** It would change every file on every run of the workflow, unchanged or not, and defeat every cache. The data's own moment says what a reader needs: how far the data reach.
- **A "latest" price file**, or a summary of the prices. The maintainer ruled it out; the table of contents marks the newest file.
- **Leaving out each Run's samples.** They are evidence, and they keep the largest file under 0.8 MB today.

## Costs

- A Series file grows with its Series. Measured between two builds of 2026-11-19 in which every Series gained one Run: 4,366 to 4,731 bytes a Run for the 162 Series of the other benchmarks, and 10,275 to 22,758 bytes a Run for the 25 `http_get` Series, whose samples are its requests. At four Runs a day the largest file passes 30 MB in a year. The files of Derivations grow the same way. Splitting a Series file by time changes what `points` holds, so once `v1` is public it would be a `v2` change: issue #64 records the decision to split each Series by month before the API is made public (the Series file keeping the summary and the recent Runs, linking one file per past month). That is a later change, not part of this first slice.
- Once `v1` is served, a published Method version's output keeps its shape for as long as the API serves it (`methods/README.md` already freezes a version once its data are published), and a Method version can leave the files only in a new API version.
- A point's `boot_summary` is null while the Runs repository holds no summary of its boot. The box uploads the summary with the boot's Runs, so the file changes once more only if the workflow copies between the two.
- `docs` names the README's section until the docs have pages of their own (#64, decision 9); the README is readable there once the repository is public.
