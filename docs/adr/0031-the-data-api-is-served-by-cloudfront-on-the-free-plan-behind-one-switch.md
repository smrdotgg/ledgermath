# The data API is served by CloudFront on the Free plan, behind one switch

The data API (ADR-0030) is a tree of static files, built and checked by the `runs` workflow. This records how it reaches readers: from one host, `https://api.ledgermath.com`, by a CloudFront distribution on the Free flat-rate plan, in front of two private buckets of `production-runs`, built in code and off until the maintainer turns it on (#64: decisions of 2026-11-19, "build in private", and its slice 2). The upload of the tree to its bucket runs now; the serving does not exist until one setting says so. `infra/runs/api-bucket.ts` and `infra/runs/public-blobs.ts` hold the decisions as data, `infra/runs/public-blobs-stack.ts` makes the resources, `scripts/upload-api.ts` and `scripts/check-api-bucket.ts` upload and check the tree, and the README ("The public data API" under "The daily box", and "The API bucket" under "The data API") says how to turn it on and off.

## The decisions

1. **One host, the tree at its root.** `https://api.ledgermath.com` serves `/v1/…` from the API bucket exactly as the build wrote it, and `/runs/…`, `/boots/…` and `/blobs/sha256/<hex>` from the Runs bucket at the bucket's own keys, which is what the tree's links already say. Nothing else of either bucket is reachable: not the Runs bucket's `source/` or `logs/`, not a listing, not an older version, not whatever is put there later, and not an object under a served prefix that is of no shape the project writes there. Three locks: each bucket's policy grants this distribution (`AWS:SourceArn`) `s3:GetObject` on its served prefixes only, and only in the state `on`; the distribution reaches a bucket only from the behaviour of a served prefix, its default behaviour answering 404 from a function; and on each served behaviour a viewer-request function lets through only a key of a served shape (`SERVED` in `infra/runs/public-blobs.ts`: the tree's kinds, as `TREE_KINDS` and ADR-0030's layout give them; a Run file named by the Run schema's version 7 UUID, as `runner/run.py` names it; a boot summary named by the kernel's boot id, a UUID; a blob by its SHA-256), answering 404 to anything else before the cache or a bucket sees it, and refuses with 403 any `Host` but `api.ledgermath.com`, the distribution's own `*.cloudfront.net` name included: one host. The default behaviour's function applies the same `Host` check first, so every request under another host gets the same 403, whatever its path. The shapes are exact: a schema is one of the generator's own `API_SCHEMAS`, imported from `scripts/lib/api-schemas.ts` (a module with no imports, so that the stack's bundle does not load the build) and held equal to the build's list by a test; a price file's date, a month file's month and the date in a Run file's or boot summary's key must be real calendar values (`2026-02-29`, `2026-13`, `2026/04/31` are refused; `2024-02-29` and `2000-02-29` are served), which a test checks against JavaScript's `Date` for every day of eight years, leap and not. On 2026-11-21 every Run file (7,270) and boot summary (197) of the Runs repository had those shapes. A file the tree links that no box writes (the test fixture's `not-a-run.json`, listed as unreadable, or a boot not named by a kernel's boot id) is therefore not served. A test routes every kind of key both buckets hold or may hold, served prefix or not, served shape or not, spelt as an attacker might, through the behaviours, the functions and the grants, and finds nothing but the served shapes read in any state, under no other host; another puts every one of those keys in a stand-in for S3 and finds the bucket never asked for one of no served shape.

2. **CloudFront on the Free flat-rate plan, as decided for public blobs on 2026-11-14**, so that the bill never depends on what strangers download: $0 for CloudFront at any traffic, 1,000,000 requests and 100 GB a month before AWS may slow delivery, never an overage. The plan decides much of the rest: a web ACL is required (the two AWS managed groups, a per-address limit and a limit on all requests together, 4 rules of 5); only AWS managed cache and response-headers policies (custom ones are a Business feature); at most 5 cache behaviours (all 5 used: the four served prefixes and the default); one apex domain; no access logs. The plan also decides what a rule may be made of. As built, the limit on all requests together, whose aggregation `CONSTANT` ("count all") requires a scope-down statement, was scoped down to URI paths that start with `/`, a byte match, which AWS's feature table does not list as a paid feature. On 2026-11-24 the first deploy of `dark` showed that the plan gates WAF's features beyond that table: the subscription failed, the web ACL "not eligible for this subscription tier", and on a web ACL already on the plan, in the development account, WAF refused the rule (`WAFFeatureNotIncludedInPricingPlanException`, "String match statement", `PRO`; a size constraint likewise). Since then the scope-down is a geographic match and its negation, "from Antarctica, or not from Antarctica" (`everyRequest` in `infra/runs/public-blobs.ts`): it must match every request, so that none reaches a bucket uncounted, and the plan allows no string match, size constraint or regular expression to say "every path" with; geographic matches, Or and Not it accepts, and with this rule the web ACL held all four rules and the plan stayed `ACTIVE`. A test (`tests/free-plan-waf.ts`) walks every statement of every rule, nested ones included, and fails on a statement type, field, managed group, aggregation or action not seen accepted on the plan, and on more than 5 rules; a new one must first be shown to be accepted by a web ACL on the plan. What the plan accepts is AWS's to decide. Should it narrow it later, the web ACL's update or the subscription is refused out loud and the deploy fails, a refused update leaving the web ACL as it was; nothing is served on other terms, since a subscription refused leaves the distribution disabled in `dark`, `on` is deployed only while an ACTIVE plan covers the distribution, and the watch disables it whenever none does. The states that keep the distribution from ever serving off a plan stay as built: `off` (nothing exists), `dark` (everything but the grants, the distribution disabled, the plan subscribed), `closed` (enabled, serving nothing, only if AWS will not subscribe a disabled distribution), `on` (serving, and only if an ACTIVE plan covers it, which the deploy asks AWS); the guard that reads what is deployed and refuses a transition out of order; and the watch that disables a distribution no ACTIVE plan covers.

3. **One switch.** `PUBLIC_API.state` decides whether the serving exists: the distribution, its web ACL, functions and access control, the certificate, its validation record, the `api.ledgermath.com` alias records, the plan, the watch, and, in `on` only, the grant in each bucket's policy. It is `off` as merged, for every stage. Its `stage` is typed as `production-runs` alone, and a setting naming another stage, in any state, `off` included, stops every deploy (`checkSetting`), so that a typo is caught while it is harmless. With it off, the stack declares none of those resources and neither bucket's policy grants anything to CloudFront; a test holds it to that, and another to exactly what `on` declares. Turning it on is a change of that one line, `off` to `dark`, then `dark` to `on`, each reviewed and deployed in order (README, "Turning it on"), and each changing in the same commit, on purpose, the one constant that pins the committed switch, `RELEASED_STATE` in `tests/public-blobs.test.ts`, which the release gate ("RELEASE GATE: the committed switch is the released state, for production-runs") compares with `PUBLIC_API`. Every other test builds each state from a fixture. A test rehearses the change: for every state and both plan attachments, it copies the repository, sets the switch and `RELEASED_STATE` there, runs the whole suite in the copy with Bun's JUnit reporter, and requires every test file to have run and no test to have failed, counted from the report rather than from printed lines (Bun's console output differs under GitHub Actions, where it repeats each failure in a recap; parsing it is why the first version of this rehearsal passed locally and failed in CI). `checkSetting` also refuses, at run time, a state or plan attachment it does not know, or none. The stack's wiring is type-checked against SST's platform types in CI (`scripts/check-stack-types.ts`), once for every state, since the switch is declared as the union of its states; and `tests/public-api-graph.test.ts` builds the resources of `dark`, `closed` and `on` with the stack's own code under Pulumi's mocks, with no AWS, and holds each to `declaredResources`.

4. **Headers from three places, because policies must be managed.** The tree's objects carry their own `Content-Type: application/json` and `Cache-Control`, set by the upload; the managed response-headers policy `CORS-and-SecurityHeadersPolicy` adds `Access-Control-Allow-Origin: *` and `nosniff` to every response; S3's `ETag` passes through (weak when CloudFront compresses). The evidence is uploaded by the boxes with no `Cache-Control`, the box is not changed for this, and the workflow may not write to the Runs bucket, so one viewer-response function gives it `Cache-Control: public, max-age=31536000, immutable`, `nosniff`, a CSP sandbox and, for `.json`, `Content-Type: application/json`. The default behaviour's function answers 404, because CloudFront has no behaviour that reaches no origin. The third is the request function of decision 1, since only a function can look at a request's path or host. Three functions, each far under CloudFront Functions' 10 KB; the Free plan's feature table sets no number of them.

5. **Cache times held to ADR-0030's contract.** No address under `/v1/` is named by its content: the table of contents, the list and active Series files change every round, a month file whenever one of the four causes applies, a schema when its words are edited. So none is immutable, and since a Series file lists each month file's sha256, a month file must not outlive the Series file that lists it: the whole tree carries `public, max-age=300`, which the managed policy `CachingOptimized` honours at the edges too. Five minutes is under 2% of the six hours between the workflow's runs; for up to five minutes after a round a reader can see two rounds at once, and the month's sha256 says so. What saves requests is the sha256, not a long cache: a reader whose copy has the listed sha256 does not fetch it. The evidence is immutable: a Run file is never edited and is cited with its sha256, a boot summary is written once, a blob is named by its hash.

6. **The tree has a private bucket of its own, filled now.** Not a prefix of the Runs bucket: the workflow's role writes there and must stay unable to write to the Runs bucket; the Runs bucket is written once and versioned for good, the tree rewritten every round; and each bucket gets one list of what readers may reach. The bucket is not behind the switch, not versioned, has no CORS, and grants nothing until `on`. The workflow's existing role gets a second policy, `RunsApiUploadPolicy`: list the API bucket, read and write its `v1/*`, no delete; its first policy, and the role itself, are unchanged.

7. **The upload is a job of its own, writes only what changed, in order, and deletes nothing.** The `runs` workflow's first job, `runs`, does what it did before this change and knows nothing of S3 (since ADR-0032 its alarm reads one object of the bucket, and writes nothing): it builds the tree, checks it, and keeps it as the artifact `api`. A second job, `publish`, `needs` it and runs only when it succeeded and the repository variable `API_BUCKET` names the bucket (the stage's `apiBucket` output, set by hand after the deploy that made it, as `RUNS_BUCKET` is); while the variable is unset the job is skipped. It has its own timeout (15 minutes) and only the permissions it uses (read the repository, the OIDC token), downloads the artifact `api` of its own run, and runs three steps: a preflight that writes nothing, the upload, and the check. Its failure is visible, as a red job and a failed run, and does not change the first job's outcome, its artifacts, or the next run's baseline: the previous-tree gate (ADR-0030) takes the artifact `api` of the latest earlier run that kept one, and a run keeps it only when its tree passed the check, so a run whose `publish` failed is a baseline and a run whose check failed is not (tests hold both). The shared lock is held exactly as long as before: the group `runs`, which `prices.yml` holds for its whole run, is held by the first job alone (job-level, never cancelled in progress), and the `publish` job holds only `api-bucket`. GitHub's groups are one namespace for the repository's jobs and workflow runs: "use `concurrency` to ensure that only a single job or workflow using the same concurrency group will run at a time" and "concurrency group names must be unique across workflows to avoid canceling in-progress jobs or runs from other workflows" ([Control the concurrency of workflows and jobs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)), so a job's group `runs` and `prices.yml`'s workflow-level group `runs` exclude each other. The next run's first job may therefore start while this run's `publish` job uploads, and its baseline lookup searches runs of every status: an artifact v4 can be downloaded "immediately ... after being uploaded" ([Artifacts v4 GA](https://github.blog/changelog/2023-12-14-github-actions-artifacts-v4-is-now-generally-available/)), so a run whose `publish` job is still going is a baseline (a test holds it). Two `publish` jobs never run at once; of those waiting in `api-bucket`, GitHub keeps one: "any existing `pending` job or workflow in the same concurrency group will be canceled and the new queued job or workflow will take its place", so an older waiting `publish` job, whose tree is older, gives way to the newer. Every other order is the run guard's: every object carries the id of the run that wrote it (`x-amz-meta-ledgermath-run`), and every upload that succeeds leaves its run on the table of contents even when it had nothing else to write (the stamp, below), so an upload finding a later run anywhere in the bucket writes nothing and fails. That stops a re-run of an old run's `publish` job, a job that began waiting after a newer one published, and either after a newer run's upload stopped halfway or published a tree equal to the bucket's. The one order left overwrites nothing newer: a `publish` job re-run by hand while a newer one waits takes its place, which cancels it, and the older tree is published until the next run. The upload first lists the whole bucket: if the bucket holds a key the new tree does not have, under `v1/` or anywhere else, it writes nothing, fails the step, and names each key (decision 9). Then one `HEAD` per file gives back the SHA-256 S3 verified and kept when the object was written, its headers and its run; a file is written only when it is new, has no SHA-256, differs in bytes or differs in headers. The preflight does exactly this much and reports what the upload would write. The phases, each whole before the next: schemas; month files and price files; Series files; the list; the table of contents, so a reader following links down from the table of contents never meets a file not yet there. A failed write stops the upload in its phase, starts no later one, and fails the step, naming the phase and each key. When every phase is written and the table of contents was not rewritten and does not record this run already, the upload's last act is the stamp: `v1/index.json` written again, the same bytes and headers, with this run in its metadata. It adds no key and at most one `PUT` a round, and "changed files only" still holds for the bytes: only the run, which is never a reason to write a file, is recorded. A retry of the same run finds its run there and writes nothing. To a reader it changes the time alone: S3's ETag "reflects changes only to the contents of an object, not its metadata", and for an object written by PUT under SSE-S3 is "an MD5 digest of [its] object data" ([S3 API, Object](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Object.html)), so it stays the same and a reader revalidating with `If-None-Match` gets 304; `Last-Modified` moves on, so a reader revalidating by date alone downloads the same bytes once more, after the five minutes its copy may be kept, at most once a round. Nothing a reader relies on is dated: the contract is the sha256s. No `DELETE` is sent and the role may not send one, so nothing the previous tree published can go. Then the whole bucket is checked against the tree: the same keys, each with the tree's SHA-256, size and headers, and nothing else; given the run (the `publish` job passes it), also that the table of contents records it and no object a later run, so a stamp that did not happen fails the job. A run recorded too high by mistake stops every later upload until a person writes the objects over themselves with a true run (README, "A run recorded too high"). As built, a failed `publish` job alerted no one but through GitHub's own failed-run email, which goes to whoever last changed the workflow's schedule, as their notification settings allow; the stale-Series alarm ran in the first job and did not see it. ADR-0032 adds the route: the alarm reads, with the first job's existing read of the bucket, when `v1/index.json` was last written, and raises publishing that has stopped. That route, its notification confirmed once by hand, is a precondition of turning the API on (README, "Turning it on", step 0), not of this change. Uploads must also never overlap: the run guard reads the bucket before writing, not during, so two uploads at once could leave the older tree written last; the group `api-bucket` is what keeps them apart, and an upload by hand goes through the workflow.

8. **A Series file and a month file can be of different rounds, and the reader checks the sha256.** A month file changes in place, at the same address, so no order of upload changes the pair at once. When an upload stops after the month files and before the Series files, a Series file lists a month's previous sha256 while the month's address gives the new bytes, and no cache expiry repairs it; the `publish` job fails, visibly, naming the phase and key, and the next run's upload repairs it by itself, writing only the Series files, the list and the table of contents, which still differ (a test stops an upload there on a filled bucket, shows the mismatch, and shows the next run end it). For up to five minutes after each round, a cache may also hold one of the pair from before. The rule a reader follows: verify a month file's bytes against the `sha256` its Series file lists; on a mismatch fetch the Series file again, then the month file, and retry; while they still differ, use neither. The README says so for readers, and so do the tree's own words. As built, they did not: `MONTH_CONTRACT` (`scripts/lib/api.ts`, written into `v1/index.json`'s `months` and the schemas `series` and `series-month`) told a reader holding a copy to fetch it again when its sha256 differs, and not to fetch the Series file again when a fresh month file does not match it. Since 2026-11-23, before the API was public, its last sentences give this rule (ADR-0030, rule 9), and the schema `series` says it beside each month's `sha256` too.

9. **A key the tree no longer has stops the upload before anything is published.** The previous-tree gate (ADR-0030, rule 9) keeps every Series file and month file in every new tree, so neither can be the cause; a price file can leave the tree (taken out of the Runs repository) and so can a schema (dropped from the build), and the gate says nothing of either, nor of a key put in the bucket by hand. Publishing a table of contents that no longer lists a file the bucket still serves would leave the bucket unequal to the tree for good, every later run failing its check, since the workflow cannot delete; no kind of disappearance is so clearly allowed that the workflow should pass over it. So the upload lists the whole bucket first and writes nothing at all while it holds a key the tree lacks; the published files stay those of the last upload that succeeded, every run fails, naming the keys, and a person settles each key by hand, putting the file back in the tree or deleting the key with the stage's own profile (README, "A key the tree does not have"). The workflow never gains a delete permission.

10. **The evidence is written once, which its immutable caching assumes.** A key under `runs/`, `boots/` or `blobs/` is taken to be written once: readers keep it a year. The box (`runner/box.sh`) copies Run files and boot summaries with unconditional `aws s3 cp` and blobs with `aws s3 sync --size-only`, and it is not changed for this. What holds the assumption: a Run file's key carries a version 7 UUID minted per launch and a boot summary's the kernel's boot id, so two boxes never write one key (a boot without a boot id writes `boots/<day>/unknown.json`, which two such boots of one day would share, and which is not served); a blob's key is its SHA-256, so its bytes cannot change without its key changing, and every reader checks the hash; a box re-sending its own files sends the same bytes. What would catch a rewrite: the copy job (`scripts/copy-runs.ts`) stops, every round, when a Run file or boot summary it already copied differs from the bucket's, so a rewrite fails the `runs` workflow within six hours; and the Runs bucket is versioned, so the first bytes are kept. What would break it: a box, or a person, writing different bytes to a Run file's or boot summary's key; readers who fetched the first bytes would keep them, and CloudFront's edges for up to 24 hours, whatever the copy job then says.

11. **The certificate and DNS are the stage's.** `api.ledgermath.com` is delegated from Vercel DNS to a Route 53 hosted zone in the production account, `Z03039811C7UWLHZE7CZQ`, whose `CAA 0 issue "amazon.com"` lets Amazon issue for it. The stage makes, behind the switch, an ACM certificate for that name alone in us-east-1, its DNS validation record in that zone, and `A` and `AAAA` alias records to the distribution; the TLS policy is `TLSv1.2_2025`. The parent domain is not touched.

## What became of public blobs

The design before this one (README and dev log, 2026-11-14) served `/blobs/sha256/<hex>` alone from the Runs bucket at the distribution's `*.cloudfront.net` name, with the same plan, states, guard and watch. Kept: the plan, the states and their order, the guard, the watch, the web ACL's managed groups and per-address limit, Origin Access Control and grants only in `on`, managed policies, the evidence's immutable headers and sandbox from a viewer-response function, the blob reader at a public address. Changed: the setting (`PUBLIC_API`, refusing any other stage instead of ignoring it), what is served (four prefixes from two buckets), the total limit (every request, since every served prefix now reaches a bucket and S3's 403 for a missing key is never cached), compression of JSON, the comment the guard and the watch recognise the distribution by, and every resource's name. Replaced: the optional `domain` setting (a name and an existing certificate) by the certificate and records the stage makes; the request function that answered 404 to any address under `/blobs/sha256/` that was not a hash, by one that does the same for every served prefix, from `SERVED`'s shapes, and refuses any other host. Nothing of the design before was ever deployed (the production account held no distribution, web ACL or certificate on 2026-11-19), so its renamed resources replace nothing in AWS. The files keep their names, `public-blobs*.ts`, which a later change may rename.

## Rejected

- **Pay-as-you-go CloudFront.** Custom cache and response-headers policies would set every header with no function, and AWS's always-free tier (10 million requests and 1 TB a month) covers today's traffic; but past it the bill grows with strangers' downloads ($1.00 per million HTTPS requests and $0.085 per GB in the United States), which the maintainer ruled out for public blobs on 2026-11-14.
- **A prefix of the Runs bucket for the tree.** The workflow's role would hold `PutObject` one wildcard away from every Run.
- **Versioning the API bucket.** It would keep every overwritten copy of the current month, several GB a month, of files the Runs repository and the build reproduce.
- **Month files cached for long, or as immutable.** A month file changes for causes (b), (c) and (d) of ADR-0030 at the same address, and a reader would be served a copy whose sha256 the Series file no longer lists. Invalidating changed paths after each upload would cost $0.005 a path past the first 1,000 a month, about 56,000 paths a month at today's rate.
- **Learning the bucket from AWS at run time** (a parameter the stack writes, or a bucket name to probe). Before the deploy the role may not read it either, so "not deployed" and "not allowed" would look alike; a repository variable set from the stage's output is how the workflow already learns the Runs bucket.
- **Letting the grants alone decide what is served, with no request function** (this ADR's first draft). The grants stop at a prefix, so every object under one would be served whatever its name: a `.bak` left by hand, a boot's `unknown.json`. The request function costs a function run per request, which the Free plan includes.
- **Taking the copy job's looser key shape** (`[0-9A-Za-z][0-9A-Za-z_.-]*` for a Run file's or boot summary's name). It admits names no box writes; the served shapes are what the boxes write, and a file of another name that reaches the tree's `unreadable` list keeps its listing, unserved.
- **Fetching the Series file and month files atomically, or content-addressed month files.** No order of upload makes a file that changes in place change with its Series file; a month file named by its hash would change the tree's layout and its links, which are the generator's, and the reader's sha256 check already makes the mismatch visible.
- **Uploading the leaves and Series files when the bucket holds an unexpected key, and holding back only the list and the table of contents.** It keeps the data fresher, but leaves the bucket half of one round and half of another for as long as the key stands; writing nothing keeps the published files those of one round.
- **Uploading in steps of the first job** (this ADR's first draft). A failed upload then marked the tree's job failed, and a stuck one spent its timeout; the job that builds the evidence would depend on S3 for its colour.
- **Choosing the baseline as the latest run that succeeded, or by the `runs` job's conclusion through the jobs API.** A run is marked failed when its `publish` job fails; and the `runs` job can fail after its check passed (a stale-Series alarm). What the gate needs is a tree that passed the check, and the artifact `api` is kept exactly then, so the artifact is the mark.
- **Relying on concurrency groups alone for the order of uploads.** They keep two jobs apart, but a re-run of an old run's `publish` job enters the group as a new job and would write an older tree over a newer one; the run id kept on each object refuses that.
- **Recording the run only on the objects an upload writes** (this ADR's second draft). A run whose tree equalled the bucket's wrote nothing and so left no trace, and a retry of an earlier run then wrote its older tree over it and passed its check. The stamp on the table of contents closes that; a key of its own for the run (a marker object) would be a key no tree has, which the upload's own rule refuses.
- **The workflow-level group `runs` over both jobs** (this ADR's third draft). It made the `publish` job hold the lock `prices.yml` shares for its queue time and up to 15 minutes more, during which a third arrival could cancel a waiting `runs` or `prices` run.
- **`queue: max` on `api-bucket`**, so that no waiting `publish` job is cancelled. The older ones would then run only to be refused by the run guard or to write a tree a newer job is about to replace; GitHub's single waiting slot drops them first.
- **Narrowing the role's listing to `v1/` with a condition on `s3:prefix`.** S3 answers a `HEAD` of a missing key with 404 only to a requester allowed to list the bucket, and a `HEAD` carries no prefix, so a missing file would come back as a 403, like a refusal.

## Costs

- With the switch off, as merged: the API bucket, at $0.023 per GB-month in us-east-2 (AWS's Price List API, 2026-11-19), about $0.001 a month for the 46.6 MB tree and $0.04 a year on; at most about 57,000 `PUT`s a month at $0.005 per 1,000, $0.29; about 176,000 `HEAD`s a month at $0.0004 per 1,000, $0.07, growing with the tree to about $0.47 a year on (three passes of a `HEAD` per file a run, the preflight's, the upload's and the check's; first written here as two, and corrected on 2026-11-21: README, "Requests and time"). Under a dollar a month.
- With it on, on the Free plan: $0 for CloudFront, the web ACL, the certificate and the alias queries; the hosted zone's $0.50 a month exists already; the watch is within Lambda's free tier. S3 bills $0.40 per million requests that miss the cache (the tree is cached five minutes at each edge, the evidence 24 hours), at most $21.43 a month at the total limit's steady rate, and more in bursts WAF lets past, since nothing caps S3 request charges.
- The total limit, 6,000 requests in 5 minutes for everyone, now counts every request, cache hits included, so it is also the most the API serves in all; it suits a launch with few readers and is to be revisited once there are readers to count.
- All five of the Free plan's cache behaviours are used: a sixth path, or a website on this host, needs Pro ($15 a month, 10 behaviours) or a second distribution.
