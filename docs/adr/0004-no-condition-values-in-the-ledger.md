# No condition or procedure values in the Ledger

_Changed by ADR-0029: LedgerMath states a condition only when the Run holds proof of it, such as a CDN's own cache header kept beside it; this replaces the amended wording below._

No Variant value and no Run field records a condition such as cold, warm, fresh, or first fetch, even though a Benchmark may be built to provoke such paths. We cannot verify a provider's internal state, a provider can game a procedure, and any such label leads readers to a conclusion we cannot back. Facts a provider hands our own code are kept as event attributes, and the numbers speak for themselves.

Amended by Service benchmark trustworthiness (#19), 2026-10-26. The precise rule: nothing LedgerMath asserts names a condition. No Variant value, no field of the Run's own schema, and no observed counterpart says cold, warm, fresh, or first. The Run's events are in the Ledger, and a report by the provider, or by our own code running inside the provider such as a Lambda stub noting that its process had just initialized, may be among them as an event attribute, kept verbatim and compared with nothing. The test that decides each case: a value may be declared only if it is something we set up before the Run and something of ours proves it held on that Run, by the Provisioner's read-back of the Target Instance before and after the Run or by the binary's own events; the code that was supposed to set it up is never the proof, and what a request turned out to be is evidence, never a declared value. A Benchmark may attempt to bring about a cold path, best effort, with its PRD saying in plain words what is attempted; the outcome is never tagged.
