## 1. What LedgerMath is

Simon Eskildsen's napkin-math project is a list of first-principles performance numbers: how long a system call takes, how fast one core can read a gigabyte of RAM, what a random SSD read costs. You multiply a handful of them on a napkin to estimate a whole system. Those numbers were measured once, on one laptop, years ago, and they are slowly going stale.

LedgerMath is continuous napkin math. It measures those numbers every day, on real data-center hardware and real cloud services. It keeps every raw measurement forever in an open, append-only store called the Ledger. It publishes the math that turns raw measurements into the numbers people actually use, versioned, so anyone can recompute them. And it exposes all of it through an open data interface that a website, business-intelligence tools, and an agent skill all read from.

The agent skill is the payoff. Someone asks "what would it cost to push a Fortnite update to 30 million players", and the agent multiplies bandwidth and storage numbers from the Ledger, cites each one by a permanent URL, and shows its work.

The project is a monorepo. Runners, Ledger, derivation math, and the data interface are all built here. The website and the agent skill are clients of the data interface and are out of scope for the current planning effort.

## 2. History in two eras

### Era 1, July 2026: the C runner. Decided and built.

This is the only part of LedgerMath that exists as running code.

**The benchmarks.** Thirteen standalone C programs live in `benchmarks/c/`, one source file each, all linking a shared harness. Tier 1 is CPU, memory, and operating system: `memory_read`, `compressed_memory_read`, `memory_write`, `memory_read_random`, `syscall`, `hash`, `sort`, `mutex`, `tcp_echo`. Tier 2 is disk: `disk_write`, `disk_read_sequential`, `disk_read_random`, `disk_read_io_uring`. Tier 3 would be Redis and MySQL, Tier 4 would be S3. Neither was started. The first two came with the initial commit; pull requests 1 through 11 landed the other eleven on 2026-07-05.

**The output contract.** Each program prints a JSON array to stdout and diagnostics to stderr. Every array element has exactly these fields: `benchmark`, `variant`, `unit`, `mean_ns`, `median_ns`, `throughput_bytes_per_second`, `bytes_per_op`, `threads`, `checksum`, `samples_ns`. This contract is the language-agnostic seam. A Rust or Zig benchmark is a first-class citizen the moment it prints the same shape. Ticket #13 later decided the derivable numbers will be removed from this contract; see section 2.2.

**The harness.** It warms up, calibrates a repetition count until one sample takes about one second, then takes ten timed samples and prints the mean, median, and raw samples. A `--quick` flag shrinks buffers to three samples of a tenth of a second for development. Every benchmark's hot function returns a checksum derived from the data it processed so the optimizer cannot delete the measured loop. Builds use `-O3 -march=native`, meaning the compiler tunes the binary for whatever CPU it is compiled on.

**The daily pipeline.** An SST stack in `sst.config.ts` runs it. An EventBridge cron invokes a Lambda that launches one EC2 instance. The instance downloads the benchmark source from S3, builds it on the box, runs every binary, uploads the merged JSON plus a metadata file and a log to S3, and terminates itself. A second Lambda runs hourly and kills any runner older than two hours. Two details you should know: the cron is still on the 23:10 UTC smoke-test schedule that was meant to move back to 06:00, and the account's 32 vCPU quota forces a c6i.8xlarge instead of the c6i.metal the project wants.

**Decisions from that era that still hold.** Machine benchmarks require owned machines, because the machine type is the measurement. Disk reads use `O_DIRECT` so the page cache cannot turn a disk benchmark into a RAM benchmark. Disk scratch files refuse to live on tmpfs. Raw per-sample timings are always kept because the north star is histograms, not averages.

### 2.2 The Observation record schema, ticket #13. Decided 2026-08-16.

This is the largest decision on GitHub and the one this month's conversations amend. Its resolution, condensed:

- One **Observation** is one (Benchmark, Variant) result on one Target. It is an envelope with a closed set of root fields: a UUIDv7 id minted once at append time, benchmark, variant, a structured target identity, the artifact hash, the run id, a timestamp, an `emitted` field holding the binary's stdout verbatim, and a content hash. Its canonical URL is `/o/{id}`.
- Canonical records hold references, not embedded copies. Wide, denormalized rows are Derivations built by the pipeline.
- An **Artifact** is the binary identified by the hash of its bytes. Build records attach as provenance: source commit, containerized build environment, build parameters, every pinned dependency version. Two builds yielding identical bytes are the same Artifact.
- Every binary execution writes exactly one **Run** record, success or failure, with exit code, captured stderr, timestamps, and an environment object whose required keys depend on the Target kind. A failed Run has zero Observations.
- The stdout contract drops every derivable number. `mean_ns`, `median_ns`, and `throughput_bytes_per_second` go away. Aggregates become Derivations computed by versioned Methods. The contract change itself is specced in #22.
- Comparability is handled by **Annotations**, not version numbers. An Annotation is an append-only record with a declarative scope filter over benchmark, variant, and target fields, an anchor that is either an artifact hash or a timestamp, free-text content, and optional supersedes or cancels pointers. The pipeline materializes each effective Annotation to segment labels on the Series it matches, recomputed on every run, so retroactive notes re-partition history automatically.
- The note policy: write an Annotation eagerly when you expect numbers to move, none for refactors, and retroactively when an alarm catches an undeclared shift. Section 4 describes how this month flipped the default.
- The trust invariant: **no code change can move a Series' numbers without moving that Series' artifact hash.**
- The packaging guideline: Variants share a binary if and only if they share the measured hot path. Section 4 describes how this month replaced it.

## 4. Story one: copying memory

The question this Benchmark answers is: how fast can one machine copy bytes from one place in RAM to another? It is a **Machine** benchmark, meaning we own the box root-to-metal while it runs, and the machine type is the measurement.

### 4.1 The author writes it down

A contributor writes a PRD and adds rows to the **manifest**. The manifest is a typed TypeScript file in git that declares four tables: Benchmarks, Variants, Targets, and Stations. TypeScript here is used as a very strict JSON with a type checker, nothing more. CI executes it to produce build recipes and provisioning actions. (Proposed. The manifest was your idea on 2026-09-22.)

The **Benchmark** is named `memcpy`. A Benchmark is a name, a source directory, a PRD, and a reproduction kit. It is an ownership unit, not a category. "All the memory stuff" is a display tag added later, never a Benchmark. The Benchmark row declares which parameters the source understands and, for each, whether it is a **code-selecting parameter** or a data parameter:

```ts
benchmarks: {
  memcpy: {
    params: {
      size:    { delivered: "launch", type: "bytes" },   // data: the loop is the same for every size
      threads: { delivered: "build",  type: "1 | all" }, // code-selecting: many-thread path is different code
    },
  },
},
```

A **Variant** is one fixed, named set of parameter values for a Benchmark. The author fixes three:

```ts
variants: [
  { benchmark: "memcpy", name: "1 MiB, 1 thread",    size: MiB(1), threads: 1 },
  { benchmark: "memcpy", name: "1 GiB, 1 thread",    size: GiB(1), threads: 1 },
  { benchmark: "memcpy", name: "1 GiB, all threads", size: GiB(1), threads: "all" },
],
```

Why fixed rows and not a size flag someone passes in at launch: one mebibyte fits inside the CPU's cache and copies at cache speed. One gibibyte does not fit and streams from main memory, several times slower. Those are two different facts about the machine. A memcpy number with no fixed size is not a fact about anything, and a Series whose meaning depends on what someone typed that morning is not a Series. (Decided that Variants are fixed. Agreed this month that they are declared in the manifest.)

Variant rows and Target rows are **immutable**. You add rows and you retire rows. A diff that edits an existing row fails CI. Otherwise someone changes "1 GiB" to mean two gibibytes and every old point on that Series becomes a lie. (Proposed.)

### 4.2 The source

One file. It reads `size` from an environment variable at launch, because size is a data parameter. `threads` is a compile-time constant, because the many-thread path is different code. The program allocates a source buffer and a destination buffer, fills the source with a known pattern, and then runs the **measured region**: copy source to destination, repeated some number of times. After the region it computes a checksum of the destination, so the compiler cannot delete the copy.

The program emits **events**, not summary numbers. An event is a timestamped fact: `sample_start`, `sample_end` with the repetition count attached, `verified` with the checksum. It also emits the **observed counterparts** of everything the manifest declared about it: the number of bytes it actually copied per repetition, and the number of CPUs the process actually saw. It emits nothing it did not observe. `size` is not printed as a configured value; the bytes-per-repetition it counted is printed as an observed one. (Agreed: events. Proposed: observed counterparts.)

The rule that keeps the measurement clean: no clock read happens inside the measured region. Events sit at the region's edges only. Reading the clock costs real time. On your laptop on 2026-09-22 a `clock_gettime` call cost 58 to 77 nanoseconds and the raw `rdtsc` instruction cost 23 to 27. The error on any interval derived from two events is about one clock read divided by the interval's length. So the harness makes intervals long by putting many repetitions of the operation between the two events, and it calibrates the repetition count so one sample lasts about a second. For a slow operation it uses a count of one. At startup the harness measures its own clock cost by timing a few million back-to-back reads and emits the result as a Run-level fact, so the Ledger can compute an error bound for every interval in every Observation without trusting anyone. (Agreed.)

The harness also never discards. It still does warmup passes, because calibration needs them, but it emits the warmup samples too, tagged as warmup. Whether to ignore them is a downstream decision. (Agreed.)

### 4.3 The build

CI compiles the file once per distinct set of code-selecting parameter values. `threads` has two values, so two binaries: one for one thread, one for all threads. Size is not compiled in, so the "1 MiB, 1 thread" and "1 GiB, 1 thread" Variants share the one-thread binary. CI hashes each binary. Each hash names an **Artifact**: the exact bytes that will run. The build happens in a pinned container so rebuilding the same commit yields the same bytes and therefore the same Artifact. Each Artifact carries build records: the git commit, the container image, the compiler flags, the code-selecting parameter values, and the pinned version of the shared harness package. (Decided: Artifact is the hash, builds are containerized. Proposed: build-time compilation only for code-selecting parameters. Note that today's runner compiles on the instance with `-march=native` and none of this exists yet; that is #14.)

Why compile per code-selecting parameter and not per Variant: a change to the many-thread path changes only the all-threads binary's bytes, so only its hash moves, so only the Series that could have been affected get a boundary. Compiling per size would buy nothing, because size is data and the loop is the same code for every size.

### 4.4 Targets and Stations

A **Target** is the thing measured. For a Machine it is a provider-specific identity: instance type, region, availability zone, operating system, rendered to a slug. Two Targets here:

```ts
targets: [
  { kind: "ec2", instance: "c6i.metal", region: "us-east-1", az: "us-east-1a", os: "al2023" },
  { kind: "ec2", instance: "c7g.metal", region: "us-east-1", az: "us-east-1a", os: "al2023" },
],
```

The vCPU count, RAM, and disk are metadata of the instance type, not identity. Availability zone is identity, because a zone incident in one zone must not annotate another, and because you can always merge Series later with a Method but can never split a Series that mixed zones. (Decided in #13, with the full model owned by #18.)

A **Station** is one Variant standing on one Target. Think of a weather station: one fixed instrument at one fixed place, taking readings on a schedule. The place is the Target, the instrument is the Variant, the instrument installed at the place is the Station. The schedule is written in Stations. A staleness alarm fires on a Station. An Annotation's scope selects Stations. A Station exists before it has any data. (Agreed.)

```ts
stations: [
  { variant: "memcpy / 1 MiB, 1 thread",    target: "ec2 / us-east-1a / c6i.metal / al2023", cadence: "daily" },
  // ... six rows: three Variants times two Targets
],
```

Every Station has a **setup hash**: the hash of its Variant row, its Target row, and the version of the **provisioner** code for its Target kind. The provisioner for EC2 Machines is the instance bootstrap: which AMI, which kernel settings, which CPU governor. Today that bootstrap script can change without any record. Under the setup hash, a change to it moves the hash of every Machine Station and therefore puts a boundary on every Machine Series. (Proposed.)

### 4.5 A Visit

The scheduler launches one c6i.metal. That launch, and everything that happens on it, is a **Visit**: one instance on one Target, during which every scheduled Station on that Target gets one Run. The technician visits the site and reads every instrument there. (Agreed.)

The bootstrap sets the CPU governor to performance, disables simultaneous multithreading if the Target says so, and records the kernel version, microcode, NUMA layout, instance type from the instance metadata service, and the operating system release file.

Then, for each of the three Stations on this Target, one **Run**. A Run is one execution of one Artifact against one Target. Take the "1 GiB, 1 thread" Station. The one-thread binary starts with `size` set to one gibibyte in its environment. It measures its clock cost, say 24 nanoseconds on this box. It allocates, fills, runs three warmup samples and emits them tagged, calibrates to about one second per sample, and takes ten samples. It emits twenty-seven events: two per warmup sample, two per real sample, and one `verified`. It emits its observed facts: bytes per repetition, CPUs seen. It exits zero.

The Run record stores the exit code, the captured stderr, the start and end timestamps, the environment the bootstrap recorded, the manifest commit the Visit was launched from, the Artifact hash, and the Station's setup hash. Every Run is recorded, success or failure. (Decided: Run. Proposed: the manifest commit and setup hash fields.)

At ingest, the pipeline compares every declared property of the Station with its observed counterpart. Declared instance type c6i.metal, observed c6i.metal from the metadata service. Declared operating system, observed release file. Declared size one gibibyte, observed bytes per repetition 1,073,741,824. All match, so an **Observation** is minted: a UUIDv7 id, the canonical URL `/o/{id}`, the envelope fields, and the event log as the payload. It is appended to the git Ledger as one signed commit and lands on its Station's **Series**, the time-ordered history of that one Station, one chart line. CI republishes the Parquet mirror to R2. (Decided: Observation, Series, Ledger. Agreed: the payload is events.)

Had any pair mismatched, say the launch used a c6a.metal by mistake, the Run would be recorded with a status naming the mismatch, "declared c6i.metal, observed c6a.metal", it would produce zero Observations, an alert would fire, and a human would fix the launch. The failed Run stays in the Ledger as evidence. The Series shows a gap for that day, and the staleness alarm fires if the gap persists. A silently corrected Observation is worse than a missing one. (Proposed, on your suggestion of loud failure.)

Then the same on the c7g.metal.

### 4.6 Reading the numbers

Nothing in the Observation says "nanoseconds per byte". A **Method** computes it. A Method is a versioned, auditable procedure that turns Observations into a **Derivation**, a number that cites the Method version and the Observations it used and that anyone can recompute from the Ledger. For each sample: `sample_end` minus `sample_start`, divided by the repetition count, divided by the size. The size comes from the Variant row in the manifest, joined by Variant name, not from the payload. A second Method drops the warmup samples and turns the ten real ones into a P50 and a P99. A third averages across Targets for a headline chart. All three are Derivations. When a Method changes, old Derivations are superseded, never overwritten. (Decided.)

Every Derivation inherits the union of the Annotations of every Series that fed it. A comparability break in any input is a break in the aggregate. That is the fix for the failure the prior-art research found in Lucene's charts, where hardware swaps caused unlabeled jumps across the board. (Decided.)

### 4.7 A code change, and the three states

A contributor rewrites the many-thread copy to use non-temporal stores. That code lives in a block compiled only for the all-threads build. So only the all-threads binary changes bytes, only its hash moves, and only its two Stations get a **boundary**. The one-thread Series do not notice. Had the contributor touched the shared inner loop instead, both binaries would change and all six Stations would get a boundary. No person decides which case it is. The compiler does.

A boundary splits the Series into a new segment by default, and each boundary is in one of three states:

1. **Verified unchanged.** A transition run on that Target showed no movement, so the segments are joined again.
2. **Declared changed.** A human wrote an Annotation with a reason.
3. **Unverified.** Nothing yet. The segments stay split, and the chart shows a marker.

A **transition run** is a controlled experiment: on the pull request that changes a Benchmark, CI launches the canonical Target once and runs the old Artifact and the new Artifact interleaved on the same machine within the same hour, several rounds, and reports the delta per Variant. Same machine, same hour, so the day-to-day and machine-to-machine noise that makes time-series detection unreliable is gone. It costs one instance launch per benchmark-changing pull request.

In this story the transition run on c6i.metal shows the all-threads Variant fifteen percent faster. The contributor writes an Annotation whose scope filter matches `memcpy` / "1 GiB, all threads" on every Target, anchored at the new Artifact hash, and that boundary becomes declared changed. Nobody ran a transition run on c7g.metal, so that boundary sits at unverified and the chart shows it split until someone does. (Agreed. This flips the #13 default, which treated an unannotated boundary as comparable.)

This is also the answer to the question that started the month. You asked what protects a sibling Variant that a change accidentally affected, given that detection cannot be trusted. The answer is that nothing has to detect it. The boundary is in the data mechanically, the default is split, and only a controlled experiment or an explicit human declaration can join the segments. Detection is a second layer that checks declarations, never the first line of defense.

### 4.8 Adding a Variant

Someone wants 64 MiB. They add one line to the Variants table and two to the Stations table. Because size is a data parameter, no new binary is built. Two new Stations, two new Series born on their first Visit. Nobody adds a size flag, and nobody edits the existing rows.

## 5. Story two: fetching over HTTP

The question: how long does it take to fetch one object over HTTPS from a machine in the same region, with connection setup kept apart from transfer, and how does a cold Lambda invocation compare to a warm one? These are **Service** benchmarks: the Target is managed by the provider, we cannot see inside it, and we measure it from the outside.

### 5.1 The Benchmark is `http_get`, not `s3_get`

You asked whether the Benchmark would really be `s3_get` or whether it would be `fetch`. It is the generic one. The client code that measures an S3 download has no S3 in it: it connects, completes TLS, sends GET, reads the body to the last byte, checksums it, and emits events and response headers. That same code measures a Lambda function URL and a CloudFront distribution. So there is one Benchmark, `http_get`, and S3, Lambda, and CloudFront are three Targets of it. Sharing one Artifact across them is correct: the client code is identical, so a change to it should put a boundary on all three. What differs between the three lives in the Target rows and in the provisioners. (Proposed.)

```ts
benchmarks: {
  http_get: {
    params: {
      body:        { delivered: "launch", type: "bytes" },  // realized by the provisioner, not the binary
      connections: { delivered: "build",  type: "1 | 4" },  // the multi-connection path is different code
      condition:   { delivered: "launch", type: "repeated | first-fetch | cold | warm | cache-hit | cache-miss" },
    },
  },
},
variants: [
  { benchmark: "http_get", name: "1 MiB, 1 connection, repeated",    body: MiB(1), connections: 1, condition: "repeated" },
  { benchmark: "http_get", name: "1 GiB, 1 connection, repeated",    body: GiB(1), connections: 1, condition: "repeated" },
  { benchmark: "http_get", name: "1 GiB, 1 connection, first fetch", body: GiB(1), connections: 1, condition: "first-fetch" },
  { benchmark: "http_get", name: "1 KiB, 1 connection, cold",        body: KiB(1), connections: 1, condition: "cold" },
  { benchmark: "http_get", name: "1 KiB, 1 connection, warm",        body: KiB(1), connections: 1, condition: "warm" },
],
targets: [
  { kind: "s3",         region: "us-east-1", storageClass: "STANDARD", vantage: "ec2 / us-east-1a" },
  { kind: "lambda",     region: "us-east-1", vantage: "ec2 / us-east-1a" },
  { kind: "cloudfront", region: "us-east-1", vantage: "ec2 / us-east-1a" },
],
```

Two things to notice. First, `body` is a Variant parameter even though the binary never uses it. It is a workload parameter, like `size` in memcpy, and it is realized by the provisioner uploading an object of that size rather than by the binary allocating a buffer. The binary observes it back by counting the bytes it received. Second, `condition` is also a Variant parameter, realized by the provisioner and proven by an observed fact. Both of these are grilling questions: whether a parameter the binary never touches belongs on the Variant, and whether a condition is a Variant parameter or something else. (Proposed.)

Not every Variant pairs with every Target. Lambda cannot return a one gibibyte body, so a Station pairing the 1 GiB Variant with the Lambda Target is invalid, and CI rejects it because the Lambda provisioner declares which parameter values it can realize. (Proposed.)

### 5.2 Fixtures and provisioners

A **fixture** is the concrete thing the measured region acts on, created for a Station, whose content is fully determined by the Station's definition. It is not the Target, which is the service. It is not the Variant, which is the parameters. It is the parameters made real on the Target. (Proposed.)

| Station | Fixture | Who creates it |
|---|---|---|
| 1 GiB repeated, on S3 | a one gibibyte object of seeded random bytes in a bucket | the S3 provisioner |
| 1 GiB first fetch, on S3 | ten fresh one gibibyte objects, one per sample, never requested before | the S3 provisioner, before every Visit |
| 1 KiB cold, on Lambda | a deployed function that returns one kibibyte and reports whether it just initialized, plus its init duration | the Lambda provisioner |
| 1 KiB cache-miss, on CloudFront | a distribution in front of the bucket, and a fresh object key per sample | the CloudFront provisioner |
| memcpy on a Machine, from story one | the source and destination buffers | the binary itself |

The last row shows that Machine benchmarks usually create their own fixtures, and the rule is the same either way: the fixture's content is fully determined by the definition and verified before the measured region runs.

A **provisioner** is code, one per Target kind, that creates and verifies fixtures and puts the Target into the declared condition. Fixtures are created when a Station is commissioned, meaning its row is first added, and re-verified before every Visit: the object exists, its size matches, its checksum matches. Random bytes come from a seeded generator whose seed and version are recorded, so a fixture can be regenerated byte-identically anywhere. The fixture's location, a URL or an ARN, is provisioner output. It is delivered to the binary at launch and recorded in the Run's environment for reproduction. It is never baked into the binary, because a URL is an address that changes when a bucket is recreated while the definition does not, and because a build that embedded a freshly generated URL would produce a new Artifact hash every time for the same code. It is not a secret either. Access is controlled by the runner's IAM role, not by hiding the name. If publishing bucket names in a public Ledger is a concern, the Run records a fixture id and the id-to-URL map stays private. (Proposed. You reasoned your way to the same conclusion on 2026-09-22.)

The provisioner's version is part of every Station's setup hash. Switch the S3 provisioner from single-part to multipart upload, and every S3 Station gets a boundary while the Lambda Stations do not.

### 5.3 Cold is manufactured and proven, never assumed

Today's harness discards warmup on purpose because it wants the steady-state number. A cold start is a different number, and both are legitimate napkin numbers. A cold condition is manufactured by the provisioner and proven by an observed fact recorded at Run time. What "cold" means differs per Target kind:

| Target kind | What cold means | How the provisioner manufactures it | The proving fact |
|---|---|---|---|
| Lambda | no live execution environment | publish a fresh function version, or invoke after the idle window | the function reports an init flag and its own init duration in the response, because we wrote the function |
| CloudFront | edge cache miss | a fresh object key per sample | the `X-Cache` response header says Miss or Hit |
| S3, first fetch | an object never requested before | a fresh object per sample, with the provisioner recording that it made no request | the provisioner's record, since S3 does not report this |
| EBS restored from snapshot | block never read since restore | restore a fresh volume | the volume's creation time from the API |
| Page cache on a Machine | file not in RAM | drop the page cache before the sample, which root allows | cached bytes from `/proc/meminfo` before the sample |

You made the point on 2026-09-22 that S3 first-fetch matters to people designing database services even if S3 has no cold start in the Lambda sense. So it is a Variant, the provisioner manufactures it, and the Series shows whether a penalty exists instead of anyone assuming. Note the third row: the proving fact comes from the provisioner rather than the binary. Whether that is acceptable under the declared-and-observed rule is a grilling question. (Proposed.)

### 5.4 The build

`connections` is the only code-selecting parameter and every Variant above uses one connection, so one binary and one Artifact serve all five Variants and all three Targets. The build record pins the HTTP client library version. These are ordinary portable client programs, so the same Artifact serves every region.

### 5.5 A Visit

One instance launches in us-east-1a. For each Station whose vantage is that zone, one Run. Take the "1 GiB, 1 connection, repeated" Station on S3. The binary starts with the fixture URL, the expected body size, and the condition in its environment, and credentials from the instance role. It measures its clock cost. For each of ten downloads it emits `connect_start`, `connect_done`, `tls_done`, `request_sent`, `first_byte`, `last_byte`, and `verified` with the checksum. Seventy events. Calibration is irrelevant here: one download takes seconds, so each sample is one repetition, and a 70 nanosecond clock read against a multi-second interval is an error of less than one part in ten million. What limits a slow benchmark is the Visit's time budget. Ten samples of one gibibyte is ten gibibytes, and S3 to EC2 in the same region carries no transfer charge.

The binary emits its observed facts: bytes received, the regional endpoint host it connected to, the resolved address, and the response headers. At ingest: declared body one gibibyte, observed 1,073,741,824 bytes. Declared region us-east-1, observed endpoint host `s3.us-east-1.amazonaws.com` and an address inside AWS's published us-east-1 ranges. Declared condition repeated, and the provisioner's record shows the object was requested before. All match, so an Observation is minted.

Now the "1 KiB, 1 connection, cold" Station on Lambda. Before each of its ten samples the provisioner publishes a fresh function version. The binary invokes, and the function's response body carries `initialized: true` and an init duration of, say, 412 milliseconds. The binary emits both as observed facts. Declared cold, observed initialized true. Match. Had the provisioner failed to force a fresh environment and the function reported `initialized: false`, the Run would fail with "declared cold, observed warm", zero Observations, and an alert.

### 5.6 Reading the numbers

Connect time is `connect_done` minus `connect_start`. Time to first byte is `first_byte` minus `request_sent`. Transfer time is `last_byte` minus `first_byte`. Throughput is the body size from the Variant row divided by transfer time. Cold init is the function-reported init duration. The first-fetch penalty is a Derivation across two Series, the first-fetch Series minus the repeated Series, and it inherits both Series' Annotations. The problem ticket #19 was opened for, where a ten-second download hides two seconds of setup and eight of transfer, does not arise. They were never mixed.

### 5.7 Changes

A contributor bumps the pinned HTTP library. The one Artifact changes, so every `http_get` Station gets a boundary. Transition runs are needed per Target kind, since old and new client must be compared against the same service in the same hour. On S3 the 1 MiB Variant is unchanged, verified. The two 1 GiB Variants are twenty percent faster because the new library reads with larger buffers, so an Annotation, declared changed. On Lambda nobody runs the transition, so unverified, and the chart says so.

Someone wants eu-central-1. That is not a new Variant. It is a new Target row and new Station rows. Same Artifact, new fixtures created by the same provisioner in the new region, new Series.

Someone wants a 100 MiB body. One new Variant row, new Station rows, no new binary, new fixtures.

A bug in the provisioner uploads a five mebibyte object under the 1 MiB fixture id. The next Visit's binary receives 5,242,880 bytes. Ingest fails the Run with "declared 1,048,576 bytes, observed 5,242,880". Zero Observations, an alert, a fix, and the failed Run stays in the Ledger.

## 7. The rules, numbered

These are the mechanical rules the stories rely on. The point of each is that no judgement is required to apply it.

1. **The measured region is empty of instrumentation.** No clock read inside it. Events only at its boundaries. Repetitions inside it, calibrated to a target length, never fewer than one.
2. **The harness measures and records its own clock cost** at startup. Every derived interval gets an error bound from it.
3. **Nothing observed is discarded.** Warmup samples are emitted and tagged. Choosing which samples count is a Method.
4. **The payload holds only observed facts.** Configured values come from the manifest by joining on the Variant.
5. **Every declared property has an observed counterpart recorded at Run time.** Ingest compares them. A mismatch is a failed Run with zero Observations and a loud alert. The failed Run stays in the Ledger.
6. **Manifest rows are immutable.** Add or retire. CI rejects edits.
7. **Every Run records the manifest commit, the Artifact hash, and the Station's setup hash.**
8. **The invariant, extended:** no change to measurement code or to a Station's setup can move a Series' numbers without moving that Series' Artifact hash or its setup hash.
9. **A boundary splits a Series by default.** It is joined only by a transition run showing no movement or by an Annotation declaring the change. Otherwise it is unverified and the chart says so.
10. **Build-time compilation only for code-selecting parameters.** One binary per distinct set of their values. Everything else is delivered at launch from the manifest.
11. **Launch-time inputs come only from the manifest and from provisioner outputs.** Never from a human's hand at launch.
12. **A Benchmark is not taxonomy.** Grouping by service or by theme is a display tag. Generic client code is one Benchmark with many Targets.
13. **Annotations are scoped by filter, stored once, materialized many times.** They are cancelled, never deleted.
14. **Detection is the second layer.** It checks declarations. It is never what the data's honesty depends on.
15. **Aggregates inherit annotations.** A break in any input is a break in the Derivation.
16. **A Station row is valid only if its Target kind's provisioner can realize its Variant's parameters.** CI checks it.

### Quiz answers

1. Two. Only `threads` selects different code, and it has two values. Size is data, so the two one-thread Variants share a binary.
2. Three Runs and three Observations. One Run per Station on that Target, one Observation per successful Run.
3. One Run record with failure status, exit code, captured stderr, environment, manifest commit, Artifact hash, and setup hash. Zero Observations.
4. CI rejects the diff. Variant rows are immutable. The correct move is a new row named for two gibibytes and retiring the old one if wanted.
5. Every Series on a Machine Station, from the setup hash, because the Machine provisioner version is part of it. Artifact hashes do not move.
6. Verified unchanged, declared changed, unverified. Unverified is the default, and it splits the Series.
7. Benchmark `http_get`. Variant "1 GiB, 1 connection, repeated". Target: S3 Standard in us-east-1 with vantage us-east-1a. Station: that Variant on that Target. Fixture: the one gibibyte seeded-random object in the bucket. Provisioner: the S3 provisioner that uploads and verifies it.
8. A URL is an address that changes when a bucket is recreated while the definition does not, so baking it in would make an unrelated re-provisioning look like a change in what is measured. And a freshly generated URL embedded at build time would give a different Artifact hash for every build of the same code.
9. The function's own `initialized: true` flag and init duration in the response body, recorded by the binary as observed facts. We control the function, so we made it report this.
10. The copy loop is the same code for every size, so compiling per size would produce binaries that differ only in a constant and would buy no boundary precision. The many-thread path is different code, so compiling it separately means a change to it moves only that binary's hash.
11. One repetition per sample. Seventy nanoseconds against forty seconds is about one part in six hundred million.
12. Benchmark, Variant, Target. Equivalently, its Station. Time is the axis, not the identity.
13. Targets gains a row for S3 in eu-central-1. Stations gains rows pairing the existing `http_get` Variants with it. Benchmarks and Variants are untouched, and no binary is rebuilt.
14. The Ledger is the git repository of canonical records, the source of truth. The R2 bucket holds a Parquet mirror regenerated by CI for querying. If R2 vanished, CI would republish elsewhere. If GitHub vanished, every clone is the Ledger.
15. Nowhere in the Observation. It is a Derivation produced by a Method over the sample events, recomputable by anyone, superseded if the Method changes.
