# Prior art: public, verifiable, mirrored binary stores

- **Date:** 2026-10-02
- **Ticket:** [#28 — Prior art: public, verifiable, mirrored binary stores](https://github.com/smrdotgg/ledgermath/issues/28) (part of #12)
- **Question:** How do projects that publish thousands of binaries keep them public, verifiable, and mirrored for years — and what should LedgerMath's Artifact store copy, avoid, or reconsider? The store's decided shape (from #14): content-addressed objects in a Cloudflare R2 bucket keyed by sha256; build records and an index of expected hashes committed to the Ledger's git repository by CI only, with signed commits and branch protection forbidding force-push; a `verify` command that walks the index and checks every object in a named mirror; an S3 Object Lock compliance-mode second copy; one-command community mirrors; expendable public archives (Software Heritage, Zenodo).

## Method and scope

Seven systems were surveyed against primary sources only — official documentation, the systems' own source code, specs, live service responses, and first-party incident posts — plus two optional "expendable archive" candidates and the components of the decided shape itself (R2 bucket locks, S3 Object Lock, GitHub protections, git's hash, rclone). For each system the same five questions were asked: (a) how the index of expected objects is kept tamper-evident, (b) how objects are content-addressed and verified on fetch, (c) whether deletion or overwrite is prevented or merely detected, (d) how third parties mirror and verify, (e) what rotted, broke, or was attacked. Claims that could not be pinned to a primary source are flagged inline as *(not verified)*; secondary coverage is marked *SECONDARY*.

Scale context: LedgerMath produces one Artifact per Benchmark per architecture per source change (ADR-0002), each a small static binary, so the store grows by megabytes per change, not terabytes per year. Several lessons below are about systems whose problems were caused by scale LedgerMath will never reach; those are noted as such.

## 1. crates.io / cargo

**(a) Index tamper-evidence.** The index exists in two forms: a git repository (`https://github.com/rust-lang/crates.io-index`) and, default since Rust 1.70 (2023-06-01), a sparse HTTP index at `sparse+https://index.crates.io/` where "the sparse protocol downloads each index file using an individual HTTP request" ([registry index reference](https://doc.rust-lang.org/cargo/reference/registry-index.html), [1.70 release post](https://blog.rust-lang.org/2023/06/01/Rust-1.70.0/)). **Neither form is signed.** The newest index commits report `"verified": false, "reason": "unsigned"` via the GitHub API ([commits endpoint](https://api.github.com/repos/rust-lang/crates.io-index/commits?per_page=2)); RFC 2789 concedes "crates-io plans to add a cryptographic signatures to the index as an extra layer of protection on top of HTTPS" and "signing of a sparse HTTP index may be challenging" ([RFC 2789](https://rust-lang.github.io/rfcs/2789-sparse-index.html)). Signing has been proposed since 2018 (RFC PR 2474, postponed 2019: "we don't have bandwidth at this time"), via sigstore (PR 3403, closed), a PKI (PR 3579, closed) and TUF (PR 3724, still open); the 2025 project goal chose "TAP-16 Merkle Tree implementation of TUF" with "the source-of-truth TUF repository will live in an S3 bucket", and as of February 2026 it was still being built ([project goals July 2025](https://blog.rust-lang.org/2025/08/05/july-project-goals-update/), [program management update 2026-01](https://blog.rust-lang.org/inside-rust/2026/02/11/program-management-update-2026-01/)). Trusted Publishing (shipped 2025-07-11) is authentication only; "Provenance verification of published crates (e.g. sigstore or other signing mechanisms)" is explicitly out of scope ([RFC 3691](https://rust-lang.github.io/rfcs/3691-trusted-publishing-cratesio.html)).

More important for LedgerMath: **the git index history is deliberately destroyed.** It is periodically "squashed into one commit to minimize the history Cargo needs to download" ([snapshot branches post, 2022-02-14](https://blog.rust-lang.org/2022/02/14/crates-io-snapshot-branches/)); the pre-squash history is parked as `snapshot-YYYY-MM-DD` branches in `rust-lang/crates.io-index-archive`, which held 34 snapshots from 2018-09-26 to 2026-09-28, nine of them in 2026 alone ([archive branches](https://api.github.com/repos/rust-lang/crates.io-index-archive/branches)). The `SquashIndex` job "Collapses the index into a single commit by driving the GitHub API directly" and force-updates the ref ([squash.rs](https://github.com/rust-lang/crates.io/blob/main/src/worker/jobs/index/squash.rs)); cargo tolerates this because it fetches with a forced refspec — `"+HEAD:refs/remotes/origin/HEAD"`, "needed if there is ever a force push" ([cargo git utils](https://raw.githubusercontent.com/rust-lang/cargo/master/src/sources/git/utils.rs)). So the git index is a distribution format, not a ledger: the only integrity mechanism is HTTPS plus the per-object checksum.

**(b) Content addressing and verification.** Each index entry carries `cksum`: "A SHA256 checksum of the `.crate` file." The live `config.json` points downloads at `https://static.crates.io/crates` ([index config](https://index.crates.io/config.json)); files are name-addressed (`/crates/{name}/{name}-{version}.crate`), with the hash living in the index and in `Cargo.lock` ("a sha256 checksum of the tarball" — [encode.rs](https://github.com/rust-lang/cargo/blob/master/src/resolver/encode.rs)). Cargo's `finish_download` recomputes the hash and hard-fails on mismatch:

```rust
let actual = Sha256::new().update(data).finish_hex();
if actual != checksum {
    anyhow::bail!("failed to verify the checksum of `{}`", pkg)
}
```
([download.rs](https://github.com/rust-lang/cargo/blob/master/src/sources/registry/download.rs)). A lockfile-vs-index disagreement is also fatal, and the message names mirrors as the suspect: "a replacement source in use (e.g., a mirror) returned a different checksum" ([resolve.rs](https://github.com/rust-lang/cargo/blob/master/src/resolver/resolve.rs)). Storage: "Crates are static and stored in Amazon S3, and served through a CloudFront distribution" ([forge CDN docs](https://forge.rust-lang.org/infra/docs/cdn.html)); "Crate files are immutable once published and are served to users from `static.crates.io` through the CDNs" ([ARCHITECTURE.md](https://raw.githubusercontent.com/rust-lang/crates.io/main/docs/ARCHITECTURE.md)).

**(c) Deletion and overwrite.** The documented rule is strong — "a publish is generally permanent. The version can never be overwritten, and the code cannot be deleted"; yank "does not delete any data, and the crate will still be available for download" ([publishing](https://doc.rust-lang.org/cargo/reference/publishing.html), [cargo yank](https://doc.rust-lang.org/cargo/commands/cargo-yank.html)); version numbers are never reusable (`"crate version `{version}` is already uploaded"` — [publish.rs](https://github.com/rust-lang/crates.io/blob/main/src/controllers/krate/publish.rs)). But the rule has grown exceptions. Owner self-deletion (RFC 3660, 2025) is allowed when a crate "has been published for less than 72 hours, or the crate only has a single owner, the crate has been downloaded less than 1000 times for each month it has been published, and the crate is not depended upon by any other crate" ([policies source](https://github.com/rust-lang/crates.io/blob/main/svelte/src/routes/policies/+page.svelte); the February 2025 announcement said 500 downloads — [development update](https://blog.rust-lang.org/2025/02/05/crates-io-development-update/)); the code comments "All crates with reverse dependencies are blocked from being deleted to avoid unexpected historical index changes" ([delete.rs](https://github.com/rust-lang/crates.io/blob/main/src/controllers/krate/delete.rs)). Admins do remove bytes: the 2023 malware was deleted "entirely from static.crates.io" on 2023-08-18 ([postmortem](https://blog.rust-lang.org/inside-rust/2023/09/01/crates-io-malware-postmortem/)), and `arrayref@0.3.10`, a version with many dependents, was "Published 2026-08-20T07:15:00Z, deleted 2026-08-20T08:41:40Z" ([arrayref post](https://blog.rust-lang.org/2026/08/20/supply-chain-attack-on-arrayref/)), leaving dependents with it locked to downgrade ([RUSTSEC-2026-0260](https://rustsec.org/advisories/RUSTSEC-2026-0260)). Deletion is therefore policy-constrained, not prevented, and leaves no tombstone in the index.

**(d) Mirrors.** Source replacement rests on byte identity: "Cargo has a core assumption about source replacement that the source code is exactly the same from both sources" ([source replacement](https://doc.rust-lang.org/cargo/reference/source-replacement.html)), enforced by the unconditional checksum check above. Panamax mirrors the index, `.crate` files and rustup toolchains ([panamax](https://github.com/panamax-rs/panamax)) and verifies each download, renaming failures to `.badsha256` ([download.rs](https://github.com/panamax-rs/panamax/blob/master/src/download.rs)). There is no official mirror list; the Data Access page offers the index, `static.crates.io`, and a daily database dump with a 1 request/second API limit ([data access source](https://github.com/rust-lang/crates.io/blob/main/svelte/src/routes/data-access/+page.svelte)). The TUF effort's stated motivation is mirrors: "making sure they serve the same content as crates.io would: that there's no tampering either on the mirror's side or during transit" ([program management update](https://blog.rust-lang.org/inside-rust/2026/02/11/program-management-update-2026-01/)).

**(e) Rot and incidents.** 2020-07-14 token advisory (non-CSPRNG tokens, plaintext storage) ([advisory](https://blog.rust-lang.org/2020/07/14/crates-io-security-advisory/)); 2023-07-20 all downloads broken for 13 minutes by a URL bug, "About 3.7M failed requests" ([postmortem](https://blog.rust-lang.org/inside-rust/2023/07/21/crates-io-postmortem/)); the git index repeatedly lags the sparse one (2025-11-01 "approximately 245 crate versions behind"; 2026-04-14 "sparse index … is unaffected") and a 2025-09-02 CDN invalidation backlog stalled ~350 crates ([status history](https://status.crates.io/history.atom)); 2025-04-11 session cookies leaked into error monitoring ([post](https://blog.rust-lang.org/2025/04/11/crates-io-security-session-cookies/)); 2025-09-12 phishing against crate owners ([post](https://blog.rust-lang.org/2025/09/12/crates-io-phishing-campaign/)); malicious crates 2025-09-24 and 2025-12-03; cargo extraction CVEs 2026-03-21 and 2026-05-25; 2026-08-20 account compromise (`arrayref`); 2026-09-17 targeted attacks on maintainers ([post](https://blog.rust-lang.org/2026/09/17/targeted-attacks/)). Scale in January 2026: "static.crates.io served approximately 1.6 PB across 11 billion requests, while index.crates.io served approximately 740 TB across 19 billion requests" ([development update 2026-01](https://blog.rust-lang.org/2026/01/21/crates-io-development-update/)).

## 2. Debian (apt, the pool, snapshot.debian.org, the mirror network)

**(a) Index tamper-evidence.** `dak` writes `Date`, optional `Valid-Until`, `Acquire-By-Hash` and MD5Sum/SHA1/SHA256 lists of every index file into `Release`, then produces both a detached `Release.gpg` and a clearsigned `InRelease` ([generate_releases.py](https://salsa.debian.org/ftp-team/dak/-/raw/master/dak/generate_releases.py)); apt "will try to fetch an InRelease or, if that fails, a Release file and its associated Release.gpg file" ([sources.list(5) source](https://salsa.debian.org/apt-team/apt/-/raw/main/doc/sources.list.5.xml)). Live headers: unstable carries a seven-day window ("Date: Thu, 01 Oct 2026 20:17:47 UTC / Valid-Until: Thu, 08 Oct 2026 20:17:47 UTC"), while stable (Debian 13.7, dated 2026-09-12) has `Acquire-By-Hash: yes` but **no `Valid-Until`** ([sid InRelease](https://deb.debian.org/debian/dists/sid/InRelease), [stable Release](https://deb.debian.org/debian/dists/stable/Release)). Keys: "there is one ftp-master key per release", stable releases "are signed by both the ftp-master automatic archive signing key … and a per-release stable key" ([ftp-master keys](https://ftp-master.debian.org/keys.html)), shipped in the `debian-archive-keyring` package and generated years ahead so they can ride along in the previous release ([2021 announcement](https://lists.debian.org/debian-devel-announce/2021/01/msg00003.html)). apt-secure(8) is candid about limits: it "does not defend against a compromise of the master server itself … or against a compromise of the key used to sign the Release files" ([apt-secure source](https://salsa.debian.org/apt-team/apt/-/raw/main/doc/apt-secure.8.xml)). `Valid-Until` "prevents replay attacks over a long timescale, and can also for example help users to identify mirrors that are no longer updated" ([apt.conf(5) source](https://salsa.debian.org/apt-team/apt/-/raw/main/doc/apt.conf.5.xml)); apt refuses expired data ("Release file for %s is expired (invalid since %s). Updates for this repository will not be applied.") and will not downgrade to an older still-valid `Release` ([acquire-item.cc](https://salsa.debian.org/apt-team/apt/-/raw/main/apt-pkg/acquire-item.cc)). `by-hash` serves index files under `dists/**/by-hash/SHA256/<hash>` so a client racing a mirror update never sees a hash mismatch ("Using this can avoid hashsum mismatches, but requires a supporting mirror"), and dak keeps superseded by-hash files around ([live by-hash directory](https://deb.debian.org/debian/dists/trixie/non-free-firmware/binary-amd64/by-hash/)).

**(b) Content addressing and verification.** The chain is Release → Packages → .deb: "The checksums of all of the Packages files are then computed and put into the Release file. The Release file is then signed by the archive key for this Debian release" ([apt-secure(8)](https://manpages.debian.org/bookworm/apt/apt-secure.8.en.html)). A live `Packages` stanza carries `Filename`, `Size`, `MD5sum`, `SHA256` ([Packages.gz](https://deb.debian.org/debian/dists/trixie/non-free-firmware/binary-amd64/Packages.gz)); apt treats MD5 and SHA-1 as not "usable" and reports "Insufficient information available to perform this download securely" when only weak hashes exist ([hashes.cc](https://salsa.debian.org/apt-team/apt/-/raw/main/apt-pkg/contrib/hashes.cc)). On mismatch the file is renamed `.FAILED` with "Hash Sum mismatch" / "Size mismatch" and `StatAuthError` ([acquire-item.cc](https://salsa.debian.org/apt-team/apt/-/raw/main/apt-pkg/acquire-item.cc)). **The pool is name-addressed, not hash-addressed**: `poolify()` builds `pool/main/a/apt/` from the source name ([utils.py](https://salsa.debian.org/ftp-team/dak/-/raw/master/daklib/utils.py)) and `apt_2.2.4_amd64.deb … apt_3.3.3_amd64.deb` sit side by side ([pool listing](https://deb.debian.org/debian/pool/main/a/apt/)); only index files are hash-addressed via by-hash.

**(c) Deletion and overwrite.** Filenames are unique forever by rule: "This restriction gives each file on the ftp site a unique name, which helps to ensure consistency across the mirror network"; to change content, "The only way to do this is to increase the version number and upload a new version" ([Developer's Reference §5.11.3](https://www.debian.org/doc/manuals/developers-reference/pkgs.en.html)); dak rejects re-uploads ("however {3} already has version {2}") and replayed `.changes` files ([checks.py](https://salsa.debian.org/ftp-team/dak/-/raw/master/daklib/checks.py)). Removals are explicit, bug-driven and logged ([removals.txt](https://ftp-master.debian.org/removals.txt)). Permanence comes from a separate service: snapshot.debian.org "is a wayback machine that allows access to old packages based on dates and version numbers. It consists of all past and current packages the Debian archive provides", importing every six hours, holding 172 TB as of 2024-10 ([snapshot.debian.org](https://snapshot.debian.org/)). Its own integrity model is a content farm — "each file is stored under a name that depends on its content: its sha1-hashsum", with "Replacing SHA-1 with SHA-256 for file identities is planned" ([snapshot README](https://salsa.debian.org/snapshot-team/snapshot/-/raw/master/README)) — and it imports whatever the mirror holds, even a tree with no `Release` file ([debian-snapshot, 2024-02](https://lists.debian.org/debian-snapshot/2024/02/msg00001.html)). Growth is "~8T/year" on donated hardware ([debian-snapshot, 2024-02](https://lists.debian.org/debian-snapshot/2024/02/msg00003.html)). Old snapshots need `Check-Valid-Until` disabled, which is the price of signed freshness windows.

**(d) Mirrors.** "The recommended method of mirroring is with the ftpsync scriptset … Do not use your own scripts, and do not just use single-pass rsyncs" ([ftpmirror](https://www.debian.org/mirror/ftpmirror)). The reason is ordering: "The archive mirroring must be done in 2 stages. The first rsync run must ignore the index files … If archive mirroring is done in a single stage, there will be periods of time during which the index files will reference files not yet mirrored" ([archvsync README](https://salsa.debian.org/mirror-team/archvsync/-/raw/master/README.md)); stage one excludes `Packages* Sources* Release* InRelease`, stage two deletes with `--delete-delay`, and a lock file `Archive-Update-in-Progress-<mirror>` marks the window ([ftpsync](https://salsa.debian.org/mirror-team/archvsync/-/raw/master/bin/ftpsync)). Every mirror writes a trace file under `project/trace/` with its last completion time; the mirror checker scores mirrors by trace age ([mirror status](https://mirror-master.debian.org/status/mirror-status.html)). `debmirror` checks `Release.gpg` by default but full content hashing is opt-in: "`--checksums` … Not enabled by default, because it is too paranoid, and too slow" ([debmirror(1)](https://manpages.debian.org/unstable/debmirror/debmirror.1.en.html)). Client selection moved from the httpredir redirector (2015) to `deb.debian.org`, "Debian mirrors backed by Fastly CDN", after reports of httpredir "redirecting to mirrors that are out of date" ([debian-project, 2016-04](https://lists.debian.org/debian-project/2016/04/msg00012.html), [deb.debian.org](https://deb.debian.org/)).

**(e) Rot and incidents.** 2003-11: master, murphy, gluck and klecker compromised via a sniffed password; the archive was cleared using "externally stored lists of MD5 sums accumulated over the past weeks on not compromised machines" and signed `.changes` files — "The package archives were not altered by the intruder" ([2003 report](https://chronicles.debian.org/www/News/2003/20031202)); 2006-07 gluck compromised again ([2006 report](https://chronicles.debian.org/www/News/2006/20060713)). 2016-12 DSA-3733 (CVE-2016-1252): apt could be made to "circumvent the signature of the InRelease file, leading to arbitrary code execution" ([DSA-3733](https://lists.debian.org/debian-security-announce/2016/msg00316.html)); 2019-01 DSA-4371 (CVE-2019-3462): HTTP redirect handling let a man-in-the-middle "inject malicious content", workaround `-o Acquire::http::AllowRedirect=false` ([DSA-4371](https://lists.debian.org/debian-security-announce/2019/msg00010.html)). Key rollovers were planned, not failures ("Debian's archive signing keys regularily expire after three years" — [2011 announcement](https://lists.debian.org/debian-announce/2011/msg00002.html)). Snapshot has its own rot: 2010 disk-controller failure and corrupt files, 2010-11 master down with debian-ports snapshots lost ("for this archive we have no data"), 2019-09 imports lost and a debian-debug mirror silently stale for months because "A symlink had been replaced with a directory causing rsync to fail", and a June 2024 gap ([snapshot news](https://snapshot.debian.org/), [oldnews](https://snapshot.debian.org/oldnews), [Bug#1072675](https://lists.debian.org/debian-snapshot/2024/06/msg00012.html)).

## 3. Nix (cache.nixos.org)

**(a) Index tamper-evidence.** There is no global index: a cache is a `nix-cache-info` file plus, per store object, a `<hash>.narinfo` named by the hash part of the store path ([binary cache protocol](https://raw.githubusercontent.com/NixOS/nix/master/doc/manual/source/protocols/binary-cache/index.md), [narinfo](https://nix.dev/manual/nix/latest/protocols/binary-cache/narinfo.html)). The parser recognises `StorePath, URL, Compression, FileHash, FileSize, NarHash, NarSize, References, Deriver, Sig, CA`, only four of them mandatory ([nar-info.cc](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/nar-info.cc)). `Sig` is an Ed25519 signature over exactly `"1;" + storePath + ";" + narHash + ";" + narSize + ";" + references` — so **`URL`, `Compression`, `FileHash`, `FileSize` and `Deriver` are not signed** — verified with `verifyDetached(fingerprint(store), sig, publicKeys)`; content-addressed paths skip the check ([path-info.cc](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/path-info.cc)). Keys carry a revocation counter in their name: "a suffix denoting the number of the key (to be incremented every time you need to revoke a key)" ([generate-binary-cache-key](https://raw.githubusercontent.com/NixOS/nix/master/doc/manual/source/command-ref/nix-store/generate-binary-cache-key.md)). Client settings: `substituters` defaults to `https://cache.nixos.org/`; `trusted-public-keys` defaults to `cache.nixos.org-1:6NCHdD59X431o0gWypbMrAURkbJ16ZPMQFGspcDShjY=`; `require-sigs` (default true) means "any non-content-addressed path added or copied to the Nix store (e.g. when substituting from a binary cache) must have a signature by a trusted key" ([nix.conf](https://nix.dev/manual/nix/latest/command-ref/conf-file.html)), and the gate runs before download: "ignoring substitute for '%s' from '%s', as it's not signed by any of the keys in 'trusted-public-keys'" ([substitution-goal.cc](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/build/substitution-goal.cc)). The store path itself is input-addressed — its digest hashes the masked derivation, not the output ([store path](https://raw.githubusercontent.com/NixOS/nix/master/doc/manual/source/protocols/store-path.md)) — so the signature is what binds recipe to bytes, which is exactly the Artifact-hash-to-build-record binding LedgerMath wants. But nothing signed says which paths *should* exist: the channel's `store-paths.xz` list is unsigned, and the de facto inventory is Hydra's database, which the 2026 garbage collection correlated with the bucket ("~99.5% of all narinfos within the S3 bucket have a corresponding entry in buildstepoutputs" — [GC post, 2026-01-13](https://discourse.nixos.org/t/garbage-collecting-cache-nixos-org/74249)).

**(b) Content addressing and verification.** Nix's own writer names NAR objects by the hash of the compressed bytes — `narInfo->url = "nar/" + narInfo->fileHash->to_string(HashFormat::Nix32, false) + ".nar" + <compression extension>` ([binary-cache-store.cc](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/binary-cache-store.cc)) — but cache.nixos.org's Hydra uploads differ by era: xz-era objects are named by `FileHash`, current zstd objects by `NarHash` (live narinfos [azvn85…](https://cache.nixos.org/azvn85cras6xv4z5j85fiy406f24r1q0.narinfo) and [09hmdf…](https://cache.nixos.org/09hmdfh1i61532nvhi1p1f37l9hjl6z7.narinfo)); clients never derive the URL, they read it from the narinfo. `FileHash`/`FileSize` are informational — the HTTP store performs no hash or length check on the download ([http-binary-cache-store.cc](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/http-binary-cache-store.cc)) — and the real check happens at import against the *signed* `NarHash`/`NarSize`: `"hash mismatch importing path '%s';\n  specified: %s\n  got:       %s"` and the matching `size mismatch` ([local-store.cc](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/local-store.cc)); a truncated download is `"NAR for '%s' fetched from '%s' is incomplete"` ([store-api.cc](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/store-api.cc)). `nix store verify` checks that "its contents match the NAR hash recorded in the Nix database" and that each path "is signed by at least one trusted signing key, is content-addressed, or is built locally", with composable exit codes (1 corrupted, 2 untrusted, 4 other), `--sigs-needed n`, and remote verification `nix store verify --store https://cache.nixos.org/ /nix/store/…` ([nix store verify](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-store-verify.html)).

**(c) Deletion and overwrite.** A swapped NAR fails the signed `NarHash`; a swapped narinfo needs the private key; but absence is silent — a missing narinfo is simply "not here" and clients cache the negative for `narinfo-cache-negative-ttl` = 3600 s ([binary-cache-store.cc](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/binary-cache-store.cc), [nix.conf](https://nix.dev/manual/nix/latest/command-ref/conf-file.html)). Overwrites are unlocked by design: "this is inherently racy since there is no locking on binary caches" ([binary-cache-store.cc](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/binary-cache-store.cc)). Until 2026 nothing was ever deleted — "In the history of the cache, we always have taken an approach trying to preserve as much as possible all our history and all our store paths built once" ([GC announcement, 2024-01-31](https://discourse.nixos.org/t/upcoming-garbage-collection-for-cache-nixos-org/39078)) — and the record since is a cost story. 2023-05-30: 667M objects, 425 TiB (107 standard + 318 infrequent-access), 1,508 TiB of CDN traffic in a month, and the estimate that keeping only NixOS releases "would shrink it to 6.3% of its current size" ([financial summary thread](https://discourse.nixos.org/t/nixos-foundations-financial-summary-a-transparent-look-into-2022/28107/16)). 2023-06-02: ~$9,000/month, the long-time sponsor (LogicBlox, later Infor) asking to "transfer the ownership of the costs", a July 1 deadline, and options of migrating to Cloudflare R2 (a $32K migration fee), fundraising, or "reducing storage by 70% through garbage collection" ([call to action](https://discourse.nixos.org/t/the-nixos-foundations-call-to-action-s3-costs-require-community-support/28672)). 2023-06-20: AWS "committed to sponsoring all our storage costs for the next 12 months ($9,000/month)" ([short-term resolution](https://discourse.nixos.org/t/nixos-s3-short-term-resolution/29413)). 2023-12-05: a funded deduplication programme ([phase 1](https://discourse.nixos.org/t/nixos-s3-long-term-resolution-phase-1/36493)), shelved on 2024-01-31 because "$0.0005 per 1000 requests is cheap, until you have 800M objects", with garbage collection announced instead, preserving "all fixed output derivations" and current release channels ([GC announcement](https://discourse.nixos.org/t/upcoming-garbage-collection-for-cache-nixos-org/39078)) — still unexecuted at the 2024-06-06 meeting ([minutes](https://discourse.nixos.org/t/2024-06-06-re-long-term-s3-cache-solutions-meeting-minutes-6/46617)). 2025-07-21: AWS "covering the full cost of hosting cache.nixos.org" for 2025 at $15,743.51/month, nearly 1 PB served weekly, the bucket past 700 TiB ([2025 sponsorship](https://discourse.nixos.org/t/2025-s3-sponsorship-more-resources-for-a-sustainable-nix/67019)). 2026-01-13: 720.2 TiB and 297.6 million narinfos, with NixOS images (~100 TiB, 13.6%) identified as the first target ([GC post](https://discourse.nixos.org/t/garbage-collecting-cache-nixos-org/74249)). 2026-02-19: the first actual deletion in the cache's history, executed by enabling S3 bucket versioning with a 30-day lifecycle rule as the undo window — "the default version served by cache.nixos.org will return a HTTP 404 response … The data will automatically be removed after 2026-03-21" (same thread; [infra commit 9cf1919](https://api.github.com/repos/NixOS/infra/commits/9cf1919)). 2026-08-24: AWS credits of $20,000/month for 2026–27 ([year 4](https://discourse.nixos.org/t/aws-nixos-s3-partnership-continues-year-4/79725)). Deletion is prevented by nothing; it is a budget decision taken by the operator.

**(d) Mirrors.** `nix copy --to file:///tmp/cache …`, `--to s3://my-bucket?region=eu-west-1`, or any S3-compatible endpoint copies closures into a new cache; `--no-check-sigs` relaxes the trusted-key requirement on the receiving side ([copy.md](https://raw.githubusercontent.com/NixOS/nix/master/src/nix/copy.md), [nix copy](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-copy.html)). Signatures travel with the path info — `NarInfo(ValidPathInfo info)` carries `std::set<Signature> sigs`, re-emitted as `Sig:` lines ([nar-info.hh](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/include/nix/store/nar-info.hh), [path-info.hh](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/include/nix/store/path-info.hh)) — so a mirror re-serves `cache.nixos.org-1` signatures and clients accept them because trust is per key, not per URL; `nix store copy-sigs --substituter https://cache.nixos.org --store file:///tmp/binary-cache` imports upstream signatures into an existing mirror ([store-copy-sigs.md](https://raw.githubusercontent.com/NixOS/nix/master/src/nix/store-copy-sigs.md)). The uploader's own post-upload integrity check is commented out — `// assert(info.narHash == nar.first);` beneath "We need to throw here in case we uploaded a corrupted store path." ([binary-cache-store.cc](https://raw.githubusercontent.com/NixOS/nix/master/src/libstore/binary-cache-store.cc)). Clients try substituters by priority (cache.nixos.org advertises `Priority: 40` in its [nix-cache-info](https://cache.nixos.org/nix-cache-info)); unprivileged users may only enable `trusted-substituters`; `fallback` to building from source is off by default ([nix.conf](https://nix.dev/manual/nix/latest/command-ref/conf-file.html)). Community servers include nix-serve, harmonia, attic ("Signing is done on-the-fly by the server when store paths are fetched" — [attic](https://raw.githubusercontent.com/zhaofengli/attic/main/README.md)) and Cachix; one documented community mirror of the public cache exists (TUNA, 2020 — [announcement](https://discourse.nixos.org/t/announcing-tuna-nix-mirror/6144)). No official mirror list exists *(not verified: none found on nixos.org, nix.dev or Discourse)*.

**(e) Rot and incidents.** The cache has sat behind Fastly since 2018-10-04 ("previously was running on AWS CloudFront" — [Fastly announcement](https://discourse.nixos.org/t/the-nixos-cache-is-now-hosted-by-fastly/1061)) and is still the `nix-cache` S3 bucket in us-east-1 with a 365-day transition to infrequent access ([cache-bucket terraform](https://raw.githubusercontent.com/NixOS/infra/main/terraform/cache-bucket/main.tf)). The 2023–2026 cost crisis and the 2026 deletion are the notable events. status.nixos.org keeps no incident history; slowness is explained as backfilling from S3 after large channel bumps ([slow cache thread](https://discourse.nixos.org/t/slow-cache-nixos-org/20131)); no security incident against the cache was found *(not verified: nothing found)*. Whether the garbage collection announced for February 2024 ever ran is inferred from silence — the first recorded deletion is 2026-02-19 *(not verified)*.

## 4. Go modules (proxy.golang.org and sum.golang.org)

**(a) Index tamper-evidence.** The checksum database "is a Transparent Log (or "Merkle Tree") of `go.sum` line hashes, which is backed by Trillian" ([Go Modules Reference](https://go.dev/ref/mod#checksum-database); same at [launch, 2019-08-29](https://go.dev/blog/module-mirror-launch)). The `tlog` package "implements a tamper-evident log used in the Go module go.sum database server" in RFC 6962 style, serving hashes as static tiles (`tile/H/L/NNN`) with a three-line signed tree head ([x/mod/sumdb/tlog](https://pkg.go.dev/golang.org/x/mod/sumdb/tlog)); the client "performs "inclusion" proofs (that a specific record exists in the log) and "consistency" proofs (that the tree hasn't been tampered with) before adding new `go.sum` lines". The verifying key is compiled into the toolchain — `"sum.golang.org": "sum.golang.org+033de0ae+Ac4zctda0e5eza+HJyk9SxEdh+s3Ux18htTTAD8OuAn8"` ([key.go](https://raw.githubusercontent.com/golang/go/master/src/cmd/go/internal/modfetch/key.go)) — and the last-seen tree head is kept in `$GOPATH/pkg/sumdb/<name>/latest`, which survives `go clean -modcache`; the design doc: "No `go` command (only a manual `rm -rf $GOPATH/pkg`) will wipe out the memory of the latest observed tree size and hash" ([design doc](https://go.googlesource.com/proposal/+/master/design/25530-sumdb.md)). A fork is fatal and self-proving: "SECURITY ERROR / go.sum database server misbehavior detected! … proof of misbehavior" ([sumdb client.go](https://raw.githubusercontent.com/golang/mod/master/sumdb/client.go)); the design states the threat model plainly — a victim-specific fork must be served "forever, or else the `go` command's consistency checks will fail loudly, and with enough information to cryptographically prove the compromise". Detection of a global fork depends on auditors the design only hopes for: "We hope that proxies run by various organizations in the Go community will also serve as auditors"; no Go-team-run public auditor exists, only tooling and one self-reported personal monitor ([trillian-examples sumdbverify](https://pkg.go.dev/github.com/google/trillian-examples/clone/cmd/sumdbverify)). The tree held 66,281,821 records on 2026-10-02 ([latest](https://sum.golang.org/latest)).

**(b) Content addressing and verification.** `h1:` is "the "h1:" directory hash function, using SHA-256" over a sorted manifest of per-file SHA-256s, where "the exact zip file format encoding, compression method, per-file modification times, and other metadata are ignored" ([dirhash](https://pkg.go.dev/golang.org/x/mod/sumdb/dirhash)). Mismatch with `go.sum` is a security error and the file is deleted rather than cached; the exact text is "SECURITY ERROR / This download does NOT match an earlier download recorded in go.sum. / The bits may have been replaced on the origin server, or an attacker may have intercepted the download attempt", with a sibling message for the checksum server ([fetch.go](https://raw.githubusercontent.com/golang/go/master/src/cmd/go/internal/modfetch/fetch.go)). `go mod verify` re-hashes the cache and prints "all modules verified" or exits non-zero. `GOSUMDB=off` or `-insecure` skips the database; `GONOSUMDB` defaults to `GOPRIVATE`; `GOINSECURE does not disable module checksum database validation` ([environment variables](https://go.dev/ref/mod#environment-variables)). `GONOSUMCHECK`, named in the ticket, does not exist in the reference, the source, or the Go 1.13 notes *(not verified: treat as a non-existent variable)*.

**(c) Deletion and overwrite.** The mirror outlives origins: "this bad release may still be available in the mirror even if it is not available at the origin. The same situation applies if you delete your entire repository" — yet "proxy.golang.org does not save all modules forever" (license detection yields "only a temporarily cached copy"), and "The checksums will still remain in the checksum database regardless of whether or not they have become unavailable in the mirror" ([proxy.golang.org](https://proxy.golang.org/)). Versions are immutable; the remedy is `retract`; removal is possible by request to security@golang.org. Live evidence of the log remembering what the mirror forgot: `sum.golang.org/lookup/github.com/boltdb-go/bolt@v1.3.1` still returns record 7586054 while the proxy returns HTTP 403 for the same module ([lookup](https://sum.golang.org/lookup/github.com/boltdb-go/bolt@v1.3.1)). `index.golang.org?include=all` "will return all module versions proxy.golang.org or sum.golang.org ever served".

**(d) Mirrors.** `GOPROXY` is a list with `,` (fall back on 404/410) and `|` (fall back on any error) separators, default `https://proxy.golang.org,direct`. Mirrors relay the checksum database at `<proxyURL>/sumdb/<databaseURL>` after `/sumdb/<name>/supported`, and "the client should use the proxied access method only, never falling back to a direct connection" ([sumdb.go](https://raw.githubusercontent.com/golang/go/master/src/cmd/go/internal/modfetch/sumdb.go)). Athens "automatically proxies it to `https://sum.golang.org`" and claims no independent verification ([Athens sumdb docs](https://docs.gomods.io/configuration/sumdb/)); goproxy.cn says clients "can use the trusted checksum database sum.golang.org to verify that modules obtained from us remain untampered" ([goproxy.cn](https://github.com/goproxy/goproxy.cn)), and its proxied `/latest` was byte-identical to Google's on 2026-10-02 ([goproxy.cn latest](https://goproxy.cn/sumdb/sum.golang.org/latest)). Mirrors therefore carry bytes while verification keys and heads stay with the origin log.

**(e) Rot and incidents.** Launched 2019-08-29. Outages: 2023-10-23 ("Google is having an infrastructure failure" — [#63684](https://github.com/golang/go/issues/63684)), 2024-09-20/21 (Google frontend rollout), 2025-06-12 (GCP incident — [#74132](https://github.com/golang/go/issues/74132)). A typosquat (`boltdb-go/bolt`) sat cached in the proxy from November 2021 until February 2025 — *SECONDARY* for the timeline ([Socket](https://socket.dev/blog/malicious-package-exploits-go-module-proxy-caching-for-persistence)); first-party record [GO-2025-3451](https://pkg.go.dev/vuln/GO-2025-3451). On 2026-08-13 two HIGH bugs in the verifier itself were fixed: "A malicious GOPROXY was previously capable of forging up to two sumdb tiles that allow for a requested module to bypass the GOSUMDB check" (CVE-2026-56865) and "A malicious GOSUMDB was capable of serving arbitrary module content not contained within the transparency log" (CVE-2026-56864) ([golang-announce](https://groups.google.com/g/golang-announce/c/94pEornpRlI)). No key rotation in seven years: the key hash `033de0ae` in `key.go` still matches today's signatures ([note format](https://pkg.go.dev/golang.org/x/mod/sumdb/note)).

## 5. Sigstore Rekor

**(a) Index tamper-evidence.** Rekor "aims to provide an immutable, tamper-resistant ledger of metadata"; "Auditors can monitor the log for consistency, meaning that the log remains append-only and entries are never mutated or removed" ([logging overview](https://docs.sigstore.dev/logging/overview/)). An upload returns a Signed Entry Timestamp — "Signature over the logID, logIndex, body and integratedTime" — and an inclusion proof carrying "The checkpoint (signed tree head) that the inclusion proof is based on" ([openapi.yaml](https://raw.githubusercontent.com/sigstore/rekor/main/openapi.yaml)); the checkpoint is a signed note of origin, tree size and root hash ([tlog-checkpoint](https://c2sp.org/tlog-checkpoint)). Offline verification is "inclusion proof verification up to a verified root hash, SignedEntryTimestamp verification, and checkpoint verification", and `VerifyCurrentCheckpoint` checks consistency against a freshly fetched checkpoint ([verify.go](https://raw.githubusercontent.com/sigstore/rekor/main/pkg/verify/verify.go)). The maintainers' own framing: "logs are tamper-evident but not tamper-proof" ([rekor-monitor](https://github.com/sigstore/rekor-monitor)). Rekor v2 narrows entry types to `hashedrekord` (DSSE dropped in v2.3.0, 2026-06-10), returns the inclusion proof synchronously instead of a SET, and "can be configured to subscribe to a network of log witnesses" ([rekor-v2-spec](https://github.com/sigstore/architecture-docs/blob/main/rekor-v2-spec.md)); the production v2 checkpoint on 2026-10-02 carried cosignatures from three independent witnesses ([log2025-1 checkpoint](https://log2025-1.rekor.sigstore.dev/api/v2/checkpoint)).

**(b) Content addressing and verification.** Rekor stores no artifacts: `hashedrekord` "allows hashed data instead of supplying the full content that was signed" ([types.md](https://github.com/sigstore/rekor/blob/main/types.md)), and live v2 leaves are `{"algorithm":"SHA2_256","digest":…}` ([entries tile](https://log2025-1.rekor.sigstore.dev/api/v2/tile/entries/000)). A verifier recomputes the artifact digest, checks the signature, then the log inclusion ([cosign verify](https://docs.sigstore.dev/cosign/verifying/verify/)); the bundle format "supports offline verification". Log, CA and CT keys reach clients through the TUF trust root ([root-signing](https://github.com/sigstore/root-signing)), whose `trusted_root.json` lists `rekor.sigstore.dev` (ECDSA P-256, valid from 2021-01-12) and `log2025-1.rekor.sigstore.dev` (Ed25519, from 2025-09-23) ([trusted_root.json](https://raw.githubusercontent.com/sigstore/root-signing/main/targets/trusted_root.json)).

**(c) Deletion, retention, sharding.** Append-only by construction ("once entries are added they cannot be modified" — [security model](https://docs.sigstore.dev/about/security/)), but the operational history matters: before GA "maintainers periodically had to make breaking changes or reset data" ([GA post, 2022-10-25](https://blog.sigstore.dev/sigstore-ga-ddd6ba67894d/)). Sharding exists for "Freezing the current log and rotating signing keys if needed"; frozen shards stay queryable, with `EntryID = TreeID + UUID` routing ([sharding](https://docs.sigstore.dev/logging/sharding/)). On 2026-10-02 the v1 log exposed two inactive shards (4,163,431 and 117,740,831 entries) and an active one of 2,922,150,349 ([live log info](https://rekor.sigstore.dev/api/v1/log)). For v2 the operators are explicit that shards are mortal: "We will eventually turn down this 2025 Rekor v2 instance when we deploy a 2026 instance", hence inclusion proofs "should be persisted alongside artifacts and their signatures"; v1 freezing "will be announced one year in advance" ([Rekor v2 GA, 2025-10-10](https://blog.sigstore.dev/rekor-v2-ga/)); GA features need "at least 6 months notice" to deprecate ([API stability](https://docs.sigstore.dev/about/api-stability/)). The public-good instance "is run and managed by the OpenSSF; in particular, several member companies have volunteered engineers" with a 99.5% availability SLO, and its operations repo is private "to protect operational details" ([OpenSSF tour, 2023-10-03](https://openssf.org/blog/2023/10/03/running-sigstore-as-a-managed-service-a-tour-of-sigstores-public-good-instance/)). No explicit "entries are retained permanently" commitment was found *(not verified)*.

**(d) Mirrors and auditors.** `rekor-monitor` verifies "that the log is immutable and append-only" as a reusable GitHub Actions workflow; a public BigQuery dataset is "an easily-queryable mirror of the public good instance" ([BigQuery dataset, 2025-08-15](https://blog.sigstore.dev/rekor-bigquery-dataset/)). v2 is built on tiles — "a finite set of static resources which can be fetched with HTTP GET requests" ([tlog-tiles](https://c2sp.org/tlog-tiles)) — and production tiles are served straight from Google Cloud Storage with `cache-control: max-age=604800,immutable` and `access-control-allow-origin: *` ([tile 0/000](https://log2025-1.rekor.sigstore.dev/api/v2/tile/0/000)), so anyone can mirror the whole log with a crawler. Witnesses: omniwitness lists every Rekor shard ([omniwitness logs.yaml](https://raw.githubusercontent.com/transparency-dev/witness/main/omniwitness/logs.yaml)), and a witness policy "will be distributed by Sigstore's TUF root" ([CLIENTS.md](https://github.com/sigstore/rekor-tiles/blob/main/CLIENTS.md)).

**(e) Rot and incidents.** 2021-06-18 first root-key ceremony; 2022-09-30 the production sharding broke clients ("the STH refers to the active shard, not the shard the entry was on" — [#1087](https://github.com/sigstore/rekor/issues/1087)); 2022-10-25 GA; 2025-04-17 v2 alpha, replacing Trillian with Tessera for cost ("turn down Trillian log server and log signer instances"; tiles "fully cacheable and can be served by a CDN"); 2025-10-10 v2 GA; 2025-11-10 witnessing enabled; 2026 v1 CVEs (SSRF via key URL, gzip OOM); 2026-06-28 the operators decided the public instance "will continue using Rekor v1 as the default log for the foreseeable future" pending post-quantum changes ([Rekor evolution](https://blog.sigstore.dev/rekor-evolution/)). TUF root version 15, threshold 3 of 5, expires 2026-11-20 ([15.root.json](https://tuf-repo-cdn.sigstore.dev/15.root.json)).

## 6. Homebrew bottles on GitHub Packages (ghcr.io)

**(a) Index tamper-evidence.** The expected sha256 of every bottle per platform lives in the formula file in the `homebrew-core` git repository (`sha256 arm64_tahoe: "38024004…"` — [wget.rb](https://raw.githubusercontent.com/Homebrew/homebrew-core/HEAD/Formula/w/wget.rb)). Bottle commits are CI-only after human approval: "If the formula builds successfully on each supported platform and a maintainer approves the change, BrewTestBot updates its `bottle do` block and uploads each bottle to GitHub Packages" ([Bottles](https://docs.brew.sh/Bottles)); the publish workflow runs `brew pr-pull … --root-url="https://ghcr.io/v2/homebrew/core"`, `actions/attest`, then `gh pr merge --auto --merge` ([publish-commit-bottles.yml](https://raw.githubusercontent.com/Homebrew/homebrew-core/HEAD/.github/workflows/publish-commit-bottles.yml)); `master` is `"protected": true` ([branch API](https://api.github.com/repos/Homebrew/homebrew-core/branches/master)). Since 4.0.0 (2023-02-16) clients read the index as JSON from formulae.brew.sh rather than cloning the tap ([4.0.0 post](https://brew.sh/2023/02/16/homebrew-4.0.0/)) — and that JSON **is signed**: `formula.jws.json` is a JWS verified client-side with RSA-PSS (`PS512`, key id `homebrew-1`, added 2023-02-19), failing with "Potential MITM attempt detected" ([api.rb](https://raw.githubusercontent.com/Homebrew/brew/HEAD/Library/Homebrew/api.rb), [security docs](https://docs.brew.sh/Homebrew-Security-and-Supply-Chain)). The 2024 audit listed "Use of RSA for JSON API signing" as acknowledged ([audit post, 2024-07-30](https://brew.sh/2024/07/30/homebrew-security-audit/)).

**(b) Content addressing and verification.** Each bottle is an OCI blob; the manifest's layer descriptor is `digest: "sha256:#{tar_gz_sha256}"` with annotations `sh.brew.bottle.digest`, `sh.brew.tab`, `org.opencontainers.image.ref.name` and more ([github_packages.rb](https://raw.githubusercontent.com/Homebrew/brew/HEAD/Library/Homebrew/github_packages.rb)). The download URL is built from the formula's own hash — `"#{image_name}/blobs/sha256:#{checksum}"` ([utils/bottles.rb](https://raw.githubusercontent.com/Homebrew/brew/HEAD/Library/Homebrew/utils/bottles.rb)) — so the address *is* the expectation, and after download `raise ChecksumMismatchError.new(self, expected, actual) if expected != actual` ([pathname.rb](https://raw.githubusercontent.com/Homebrew/brew/HEAD/Library/Homebrew/extend/pathname.rb)) prints "SHA-256 mismatch / Expected: … / Actual: … / File: …" ([exceptions.rb](https://raw.githubusercontent.com/Homebrew/brew/HEAD/Library/Homebrew/exceptions.rb)). OCI makes this generic: "Before consuming content targeted by a descriptor from untrusted sources, the byte content SHOULD be verified against the digest string" ([image-spec descriptor](https://github.com/opencontainers/image-spec/blob/main/descriptor.md)). Build-provenance attestations arrived in 4.3.0 (2024-05-14): "If `HOMEBREW_VERIFY_ATTESTATIONS` is set, `brew install` will verify the bottle artifact's attestation when pouring bottles using GitHub's `gh` CLI" ([4.3.0 post](https://brew.sh/2024/05/14/homebrew-4.3.0/)); the check is `gh attestation verify <bottle> --repo Homebrew/homebrew-core` with the bottle filename as subject ([attestation.rb](https://raw.githubusercontent.com/Homebrew/brew/HEAD/Library/Homebrew/attestation.rb)), proving the workflow, repository and commit that built the bytes via the Sigstore public-good log ([GitHub artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)). It is still opt-in in 2026 and was extended to third-party taps in 7.0.0 (2026-09-13) ([7.0.0 post](https://brew.sh/2026/09/13/homebrew-7.0.0/)).

**(c) Deletion and overwrite.** GitHub lets owners delete package versions; a public package with "more than 5,000 downloads" needs GitHub Support, and deletions can be restored "within 30 days" ([deleting packages](https://docs.github.com/en/packages/learn-github-packages/deleting-and-restoring-a-package)). Nothing structural prevents the Homebrew org from deleting; in practice migration-era bottles (wget 1.21.1, 2021) are still published ([wget package versions](https://github.com/Homebrew/homebrew-core/pkgs/container/core%2Fwget/versions?filters%5Bversion_type%5D=tagged)) and no workflow deletes from ghcr.io. Overwrite is defeated by construction and by separation of credentials: "An exploited token granting GitHub Packages access could upload a malicious bottle, but that bottle would not match the `sha256` checksum recorded in the GitHub-hosted repository" ([security docs](https://docs.brew.sh/Homebrew-Security-and-Supply-Chain)); the uploader refuses tag reuse without `--keep-old`.

**(d) Mirrors.** `HOMEBREW_BOTTLE_DOMAIN`: "Use this URL as the download mirror for bottles and their manifests. If a bottle or manifest is unavailable at the mirror, the default bottle domain will be used as a fallback"; `HOMEBREW_API_DOMAIN` mirrors the JSON API; `HOMEBREW_ARTIFACT_DOMAIN` prefixes every download URL ([env_config.rb](https://raw.githubusercontent.com/Homebrew/brew/HEAD/Library/Homebrew/env_config.rb)). The mirror protocol is the OCI distribution spec (`/v2/<name>/blobs/<digest>`; "Clients SHOULD verify that the response body matches the requested digest" — [distribution-spec](https://github.com/opencontainers/distribution-spec/blob/main/spec.md)). The sha256 and JWS checks do not depend on the domain, so mirrors cannot tamper. Homebrew publishes no mirror list; the USTC mirror documents only client variables (*SECONDARY*: [USTC](https://mirrors.ustc.edu.cn/help/homebrew-bottles.html)).

**(e) Rot and incidents.** The move was forced: "GitHub Packages is the default package download/upload location on macOS and Linux. This is due to Bintray's shutdown on May 1st 2021" ([3.1.0 post, 2021-04-12](https://brew.sh/2021/04/12/homebrew-3.1.0/)) — about three months' notice (JFrog's own post could not be fetched; *not verified* beyond Homebrew's statement). Old Bintray URLs now fail TLS (`homebrew.bintray.com` is "not in the cert's altnames: DNS:*.jfrog.io"). 2021-04-21: a `review-cask-pr` action bug "would allow an attacker to inject arbitrary code into a cask and have it be merged automatically"; Homebrew "removed the ability for our bots to commit to `homebrew/cask*` repositories" and required human review ([incident disclosure](https://brew.sh/2021/04/21/security-incident-disclosure/)). ghcr.io degradations on 2023-01-30 and 2023-03-15 broke manifest fetches ([GitHub status](https://www.githubstatus.com/incidents/zf2tk6x40gmh), [Homebrew discussion](https://github.com/orgs/Homebrew/discussions/4156)). 2024-07-30 Trail of Bits audit (25 items, 16 fixed). 2026-04-27 GitHub-wide incident touched the Package Registry ([availability report](https://github.blog/news-insights/company-news/github-availability-report-april-2026/)).

## 7. Software Heritage

**(a) Index tamper-evidence.** "the Software Heritage archive is conceptually a single (big) Merkle Direct Acyclic Graph (DAG)" of contents, directories, revisions, releases and snapshots, where "each node is identified by an intrinsic identifier computed as a cryptographic hash of the node content" ([data model](https://docs.softwareheritage.org/devel/swh-model/data-model.html)). A SWHID is `swh:1:<snp|rel|rev|dir|cnt>:<40 hex>` ([syntax](https://www.swhid.org/specification/v1.2/4.Syntax/)); the hash is SHA-1 over a Git-style header plus a canonical serialisation — for a content, "the SHA1 of the byte sequence obtained by concatenating: the ASCII string "blob" (4 bytes), an ASCII space, the length … a NULL byte, and the actual content" — so "SWHIDs for contents, directories, revisions, and releases are compatible with the way the current version of Git proceeds for computing identifiers", while snapshots hash a byte-sorted branch manifest under a "snapshot" header ([core identifiers](https://www.swhid.org/specification/v1.2/5.Core_identifiers/), [git_objects](https://docs.softwareheritage.org/devel/apidoc/swh.model.git_objects.html)). The identifier "is intrinsic: it can be computed from the object itself" with the `swh identify` tool ([persistent identifiers](https://docs.softwareheritage.org/devel/swh-model/persistent-identifiers.html)). SWHID "has been officially adopted as ISO/IEC 18670:2025 on April 23, 2025" ([swhid.org](https://www.swhid.org/)), with reference implementations in Rust, Python and Go a year on ([one-year post](https://www.softwareheritage.org/2026/04/23/one-year-swhid-iso-iec-18670-standard/)).

**(b) Content addressing and verification.** Each content row stores `sha1, sha1_git, sha256, blake2s256, length` with a unique composite index over all four hashes ([schema](https://raw.githubusercontent.com/SoftwareHeritage/swh-storage/master/swh/storage/sql/30-schema.sql), [indexes](https://raw.githubusercontent.com/SoftwareHeritage/swh-storage/master/swh/storage/sql/60-indexes.sql)). The object store is keyed by a single hash — "using their SHA1 or SHA256 identifiers as keys" depending on backend, the Ceph-backed Winery using "the sha256 sum of the content of the object by default" ([archive copies](https://docs.softwareheritage.org/devel/swh-storage/archive-copies.html), [winery](https://docs.softwareheritage.org/devel/swh-objstorage/winery.html)) — and `check()` verifies "that the content matches the object id" ([objstorage interface](https://docs.softwareheritage.org/devel/apidoc/swh.objstorage.interface.html)). Raw bytes come from `GET /api/1/content/[(hash_type):](hash)/raw/` for any of the four hash types, and directories or revisions from the Vault as tarballs or git bundles ([API scheme](https://docs.softwareheritage.org/devel/swh-web/uri-scheme-api.html), [vault](https://docs.softwareheritage.org/devel/swh-vault/index.html)). Scrubbers "continuously read objects from a data store, compute checksums, and write any failure in a database", repairing from another copy or from origins ([scrubber](https://docs.softwareheritage.org/devel/swh-scrubber/index.html)). Client-side verification is `swh identify --verify`: recompute and compare ([swh-model CLI](https://docs.softwareheritage.org/devel/swh-model/cli.html)). Anonymous API use is limited to 120 requests/hour, 1,200 authenticated ([developer FAQ](https://docs.softwareheritage.org/devel/faq/index.html)).

**(c) Deletion, overwrite, and what is not stored.** The charter promises source code "Together with its complete development history. Forever." ([ethical charter](https://www.softwareheritage.org/legal/users-ethical-charter/)); "all software source code artifacts are preserved for the long term" ([FAQ 2.3](https://www.softwareheritage.org/faq/)). Legal removal follows a French-law takedown process without a counter-notice, and the policy states the constraint: "we cannot alter or delete data in the software development history, as version control systems like Git are designed to maintain an immutable record" ([content policy](https://www.softwareheritage.org/legal/content-policy/)). The implementation separates hiding from deleting: masking makes objects "unavailable to the public" with states `VISIBLE`, `PENDING_DECISION`, `RESTRICTED` while the bytes stay ([object masking](https://docs.softwareheritage.org/devel/swh-storage/object-masking.html)); hard removal "only support[s] removal of origins and snapshots", must respect the DAG ("it is not possible to remove a single directory entry without changing the identifier for the directory"), and writes the deleted data into an encrypted, secret-shared recovery bundle because "A legal investigation might compel operators to keep a copy" ([removal algorithm](https://docs.softwareheritage.org/devel/swh-alter/removal-algorithm.html), [recovery bundles](https://docs.softwareheritage.org/devel/swh-alter/recovery-bundles.html)); mirrors are told "data removed from the main archive should be made inaccessible, but not deleted", and the project publishes "a list of removed objects" ([mirror takedown notices](https://docs.softwareheritage.org/sysadm/mirror-operations/takedown-notices.html)). Size cap: loaders default to `"max_content_size": 100 * 1024 * 1024` and production sets `104857600` ([loader.py](https://gitlab.softwareheritage.org/swh/devel/swh-loader-core/-/raw/master/swh/loader/core/loader.py), [puppet common.yaml](https://gitlab.softwareheritage.org/swh/infra/puppet/puppet-swh-site/-/raw/production/data/common/common.yaml)); larger files become `SkippedContent` records with all four hashes, the length, `status: "absent"` and a `reason` such as "Content too large" ([model.py](https://raw.githubusercontent.com/SoftwareHeritage/swh-model/master/swh/model/model.py), [journal spec](https://docs.softwareheritage.org/devel/journal.html)) — 734,373 of them on 2026-10-02 ([counters](https://archive.softwareheritage.org/api/1/stat/counters/)). The hash is kept even when the bytes are not.

**(d) Mirrors.** "A mirror is a complete copy of the Software Heritage Archive, operated by a partner institution": ENEA (Italy, 2019-10-03), GRNET (Greece, 2025-09-24), University of Duisburg-Essen (Germany, 2026-02-27), IMDEA Software (Spain) coming; "Because replication is asynchronous, a mirror is only eventually consistent", and partners commit for at least three years ([mirrors](https://www.softwareheritage.org/mirrors/)). A mirror is "populated and maintained up-to-date by consuming data from the Software Heritage Kafka-based journal and retrieving the blob objects (file content) from the Software Heritage object storage" ([mirror operations](https://docs.softwareheritage.org/sysadm/mirror-operations/index.html)) — the journal being "a Kafka-based stream of events for every added object" ([journal spec](https://docs.softwareheritage.org/devel/journal.html)) and the replayer copying blobs "by listening the content topic" ([objstorage replayer](https://docs.softwareheritage.org/devel/swh-objstorage-replayer/index.html)); mirrors need credentials ([onboarding](https://docs.softwareheritage.org/sysadm/mirror-operations/onboard.html)) and must plan for "about 3.6PB with an increase rate of about 750TB/year" of objects plus "a legal and operational structure to handle takedown requests" ([planning](https://docs.softwareheritage.org/sysadm/mirror-operations/planning.html)). A documented mirror-versus-main verification procedure does not exist yet — the monitoring page reads "Todo: This page is a work in progress" ([monitor](https://docs.softwareheritage.org/sysadm/mirror-operations/monitor.html)); verifiability rests on intrinsic identifiers alone.

**(e) What it archives and does not; scale; incidents.** Loaders cover bzr, cvs, git, mercurial and svn, plus package sources from arch, archive, aur, bioconductor, conda, cpan, cran, crates, debian, deposit, golang, hackage, hex, maven, npm, opam, pubdev, puppet, pypi, rpm and rubygems; listers include GitHub, GitLab, Gitea, Forgejo, Bitbucket, SourceForge, Launchpad and nixguix ([loaders](https://docs.softwareheritage.org/devel/apidoc/swh.loader.html), [listers](https://docs.softwareheritage.org/devel/apidoc/swh.lister.html)). On binaries: "we don't actively collect binaries. However, if binaries are included in a software repository, we do not filter them out" ([FAQ 2.6](https://www.softwareheritage.org/faq/)). No loader or lister reads object-storage buckets, release assets, container registries or git-LFS stores, and no FAQ text says so explicitly; their exclusion is inferred *(not verified)*. "Save code now" accepts git, hg, svn, cvs, bzr and tarball origins from anyone, auto-approved for known forges in "not more than a few hours", otherwise reviewed "within a few days" ([save page](https://archive.softwareheritage.org/save/), [user FAQ](https://docs.softwareheritage.org/user/faq/index.html)). Scale on 2026-10-02: 30,005,042,817 contents, 23.3 billion directories, 6.17 billion revisions, 445,695,962 origins ([counters](https://archive.softwareheritage.org/api/1/stat/counters/)); "the Archive hit the 2-petabyte mark in 2025" ([digital public good post](https://www.softwareheritage.org/2026/01/21/software-heritage-archive-digital-public-good/)). Incidents: everything runs in one Inria datacentre — "total power outage in our main datacenter" (2025-04-23), another on 2025-04-28, all services unavailable on 2025-07-17, yearly multi-day read-only windows, and a write suspension on 2025-01-15 ([status history](https://status.softwareheritage.org/pages/history/578e5eddcdc0cc7951000520)). Funding: Inria with UNESCO (agreement 2017-04-03, renewed for 2026–2030), sponsors from €10k to €250k+/year and a stated aim of "establishing an endowment fund" ([sponsor programme](https://www.softwareheritage.org/support/sponsors/program/), [2025 milestones](https://www.softwareheritage.org/2025/12/23/2025-milestones/), [UNESCO agreement](https://www.unesco.org/en/articles/agreement-software-preservation-signed-unesco)).

## 8. Expendable archives: Zenodo and the Internet Archive

**Zenodo.** Every record gets a version DOI and a concept DOI ("a DOI representing all of the versions of your record"), registered with DataCite ([versioning](https://zenodo.org/help/versioning), [API docs](https://developers.zenodo.org/)). Files expose an MD5 ("checksum": "md5:…") and are re-checked: "Files are regularly checked against their checksums to assure that file content remains constant"; two independent MD5s are kept, one by Invenio and one by CERN's EOS "used for automatic detection and recovery of file corruption on disks" ([policies](https://about.zenodo.org/policies/), [infrastructure](https://about.zenodo.org/infrastructure/)). Owners may delete or edit files only "within 30 days after publication"; later deletion is staff-only "in duly justified cases" and leaves a tombstone; retraction keeps the bytes ([manage records](https://help.zenodo.org/docs/deposit/manage-records/)). Retention: "Items will be retained for the lifetime of the repository. This is currently the lifetime of the host laboratory CERN, which currently has an experimental programme defined for the next 20 years at least" — but CERN "reserves the right, without notice … to alter, delete or block access to content that it deems to be inappropriate" ([terms](https://about.zenodo.org/terms/)). Limits: 50 GB and 100 files per record, a 150 GB extra allowance, more on request ([manage files](https://help.zenodo.org/docs/deposit/manage-files/), [quota](https://help.zenodo.org/docs/deposit/manage-quota/)); search API throttled to 30 requests/minute since 2025-11-25 ([blog](https://blog.zenodo.org/2025/11/25/2025-11-14-search-api-updates/)). Storage is a 5 PB EOS cluster with two replicas per file and backups 3.5 km away. 2026 brought bot-driven slowness and a session-reuse incident affecting ~3,000 accounts ([2026-05-21 incident](https://blog.zenodo.org/2026/05/21/2026-05-21-session-incident/)). No signatures anywhere.

**Internet Archive.** Identifiers are immutable ("Once defined an identifier can not be changed" — [metadata schema](https://archive.org/developers/metadata-schema/index.html)); every item publishes `<md5>`, `<sha1>`, `<crc32>` per file in `_files.xml` and via the metadata API ([metadata read API](https://archive.org/developers/md-read.html)). Uploaders can remove their own items and add, edit or delete files with no stated time window ([removing items](https://help.archive.org/help/removing-your-item-pages-from-archive-org/), [editing files](https://help.archive.org/help/how-to-delete-or-add-files-to-an-existing-item/)) — stronger self-service mutability than Zenodo. Stated intent: "As an archive our intention is to store and make materials in perpetuity"; "permanent storage costs us approximately $2.00US per gigabyte" ([about](https://help.archive.org/help/archive-org-information/)). Items are capped at 1 TB with ≤1000 files / 500 GB recommended ([uploading tips](https://help.archive.org/help/uploading-tips/)); the `ia` CLI does bulk upload/download with checksum skipping ([internetarchive CLI](https://archive.org/developers/internetarchive/cli.html)). Replication is two copies in separate data centres plus a Canadian copy ([20,000 hard drives, 2016](https://blog.archive.org/2016/10/25/20000-hard-drives-on-a-mission/)). Incidents: 2024-05 DDoS, 2024-10 breach with uploads offline for weeks ([2024-10-21 update](https://blog.archive.org/2024/10/21/internet-archive-services-update-2024-10-21/)), 2026-08-17 power outage ([post](https://blog.archive.org/2026/08/17/service-restored-from-overnight-power-outage/)). A 501(c)(3) funded by donations. No signatures, no documented periodic fixity audit *(not verified)*.

## 9. The decided shape's own components, checked

- **Cloudflare R2 bucket locks are owner-removable.** The product page: "Bucket locks prevent the deletion and overwriting of objects in an R2 bucket for a specified period — or indefinitely" — and in the same page, "Remove bucket lock rules from your R2 bucket": dashboard "Locate the rule you want to remove … select **Delete**", `npx wrangler r2 bucket lock remove <BUCKET_NAME> --id <RULE_ID>`, or a put-configuration API call that omits the rule; "A bucket cannot be emptied while any bucket lock rules are configured. Remove all lock rules before emptying a bucket" ([bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/), [wrangler r2 commands](https://developers.cloudflare.com/r2/reference/wrangler-commands/)). An "indefinite" rule is therefore a guard against accidents and against a compromised object-level token, not WORM against the account owner. This corrects the #15 survey's description of bucket locks as "real WORM". R2's S3 API lists `PutObjectLockConfiguration`, `GetObjectLockConfiguration`, `PutBucketVersioning` and `GetBucketVersioning` as unimplemented, and supports SHA-256 only as a COMPOSITE (multipart) checksum, with CRC-64/NVME as the full-object algorithm ([R2 S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/)).
- **S3 Object Lock compliance mode is the only prevention-grade copy.** "a protected object version can't be overwritten or deleted by any user, including the root user in your AWS account … its retention mode can't be changed, and its retention period can't be shortened"; "The only way to delete an object under the compliance mode before its retention date expires is to delete the associated AWS account" ([Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-overview.html)). Caveats: it needs versioning; retention is a fixed `Days`/`Years` default or an explicit retain-until date (no documented maximum on the API page — [DefaultRetention](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DefaultRetention.html)); "indefinite" exists only as a legal hold, which "can be freely placed and removed by any user who has the `s3:PutObjectLegalHold` permission"; and the escape hatch is real — after account closure "The post-closure period is 90 days … AWS will also delete content and resources in your account" ([closing an account](https://docs.aws.amazon.com/accounts/latest/reference/manage-acct-closing.html)).
- **GitHub branch protection does not bind administrators by default.** "By default, GitHub blocks force pushes on all protected branches" and "you cannot delete a protected branch", but "By default, the restrictions of a branch protection rule do not apply to people with admin permissions to the repository or custom roles with the 'bypass branch protections' permission" ([protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)); rulesets make the bypass list explicit and can be empty, but organisation-level rulesets need the Enterprise plan ([rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)). Whoever can edit rules can remove them; the protection is convention plus detection.
- **Signed CI commits without a managed key.** Commits created through the GraphQL `createCommitOnBranch` mutation "are automatically GPG signed and are marked as verified in the GitHub UI" ([changelog, 2021-09-13](https://github.blog/changelog/2021-09-13-a-simpler-api-for-authoring-commits/)) with GitHub's web-flow key ([commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification)). Such a signature attests that GitHub performed the commit for a token holder, not that a particular workflow built the bytes; that is what attestations are for.
- **git's hash is SHA-1.** Git "moved to a hardened SHA-1 implementation by default … but SHA-1 is still weak", and "using SHA-256 based storage on public-facing Git servers is strongly discouraged" until protocol support lands ([hash function transition](https://git-scm.com/docs/hash-function-transition)). The commit chain is good evidence against casual rewriting; the strong hash in the system must be the sha256 inside the index files.
- **`rclone` verifies MD5, not sha256.** The S3 backend "uses the `ETag:` header as an MD5 checksum", stores `X-Amz-Meta-Md5chksum` for multipart objects, and documents no SHA-256 support ([rclone S3](https://rclone.org/s3/)). A one-command mirror sync proves transfer integrity, not that the object matches its sha256 key; only hashing the bytes does.

## Recommendation for LedgerMath's Artifact store

The decided shape is sound in outline — content-addressed bytes, a reviewed index in git, independent copies, a verifier — and it matches what the healthiest systems above converged on. Prior art sharpens it in the following ways.

### Steal this

1. **Treat the index as a transparency log, not just a repository (Go, Rekor).** The git repository is already an append-only hash chain at LedgerMath's scale; make it one deliberately. Every CI append should publish a signed checkpoint — a tag or a small signed file naming the index commit, the tree hash and the number of entries — and every verifier and mirror should pin the last checkpoint it saw and refuse anything that is not a fast-forward of it, the way the `go` command keeps `$GOPATH/pkg/sumdb/<name>/latest` across cache wipes. Fork detection then does not depend on GitHub honouring branch protection.
2. **Put the hash in the address and always recompute (Homebrew, Nix, cargo).** Keying R2 objects by sha256 is the right call; the Homebrew pattern of deriving the download URL *from the reviewed index entry* means a mirror cannot even be asked for the wrong bytes. Cargo's and Homebrew's checks are unconditional on where the bytes came from; LedgerMath's `verify` and any fetch path must do the same, and must hash the bytes rather than trust ETags or R2's checksum headers (CRC-64 can serve as a cheap pre-filter, not as proof).
3. **Order writes like ftpsync (Debian).** Upload objects to every primary copy and read them back before the index commit that references them lands. A `verify` run against a mirror mid-sync then reports "missing" only for objects the index does not yet name, never "index points at nothing".
4. **Carry freshness in the index (Debian `Date`/`Valid-Until`).** Each checkpoint should carry its creation time so a stale mirror is identifiable; `verify` should report the age gap between a mirror's checkpoint and the origin's, and the Debian lesson is to make this a loud result rather than an optional flag (snapshot's debian-debug mirror sat stale for months unnoticed).
5. **Keep the hash when the bytes go (Software Heritage `skipped_content` and masking, Zenodo tombstones, Go's log retaining what the proxy removed).** Software Heritage is the model: masking hides an object without deleting it, hard removal is restricted to graph roots so no identifier changes, removed data goes into an encrypted recovery bundle, and mirrors are told to hide rather than delete. The decided shape has no tombstone concept. If an Artifact must ever be withdrawn (legal demand, leaked secret in a binary), the index entry must stay, marked withdrawn with a reason and date, so Runs citing it remain checkable and the removal itself is on the record. crates.io's deletions leave no such trace and produced the `arrayref` breakage.
6. **Separate the credential that writes bytes from the authority that changes the index (Homebrew).** CI's R2/S3 credentials should be unable to alter the index, and index commits should require the CI identity; a stolen upload token then produces objects nobody references and nothing more.
7. **Design `verify` like `nix store verify` and `go mod verify`.** Composable exit codes (corrupted / missing / untrusted / stale), a remote mode that checks a named mirror without downloading into a local store, a `--sigs-needed`-style option for checkpoints, and a one-line success message that scripts can grep. Debian's `debmirror --checksums` being off by default because it is "too paranoid, and too slow" is a scale problem LedgerMath does not have: full hashing can be the default.
8. **Persist proofs with the records (Rekor).** Each Run already references its Artifact by hash; it should also record the index checkpoint under which that Artifact was published. Sigstore's operators tell clients to keep inclusion proofs alongside artifacts because shards get turned down; LedgerMath's equivalent is that a Run's provenance must be checkable from the Ledger alone even if the live index service changes host.
9. **Emit build-provenance attestations if builds run on GitHub Actions (Homebrew).** It is a one-step addition (`actions/attest`) that puts a workflow-and-commit statement for each Artifact into the Sigstore public-good log — a free, independent, third-party witness that the bytes existed at a date. It proves who built, not that the build is correct, and should not replace the index.

### Avoid this

1. **Rewriting index history (crates.io squashes).** The squash habit makes the crates.io git index worthless as evidence. LedgerMath's repository must never squash; branch rules must forbid deletion as well as force-push; and the bypass list must be empty, since GitHub's defaults let administrators through.
2. **Mistaking owner-revocable locks for WORM (R2).** Keep R2 as the serving copy, but describe its bucket lock honestly: it stops accidents and object-token compromise, not a compromised or coerced account owner. Prevention lives only in the S3 compliance copy.
3. **Relying on one host's good behaviour (Bintray, Nix's sponsor, IA's outages).** Homebrew got about three months' notice; Nix's sponsor handed over a $9,000/month bill with a one-month deadline. The decided shape's multiple copies are right; what prior art adds is that the *index must reference hashes, not URLs* (crates.io's `{sha256-checksum}` template, SWHIDs), so a host change rots no citation.
4. **Unbounded growth without a written retention rule (Nix, snapshot.debian.org).** LedgerMath's growth is bounded by Benchmark source changes, but write the rule now: everything referenced by a Run is kept forever; nothing else is published to the store in the first place. Decide this before the first byte, not when the invoice arrives.
5. **Self-service deletion windows (crates.io 72 h, Zenodo 30 days, IA any time).** There should be none; withdrawal is a tombstone (steal #5), performed by a reviewed index commit.
6. **Opt-in verification (Homebrew attestations opt-in for two years; `debmirror --checksums`).** Make hashing the default behaviour of the mirror command; a mirror that has not verified should not be able to call itself complete.
7. **Trusting the sync tool's checksum (rclone MD5 ETags).** `rclone sync` is a fine transport for one-command mirrors; `verify` must still hash every object against its sha256 key. Nix's own uploader has its post-upload hash assertion commented out (`// assert(info.narHash == nar.first);`); LedgerMath's CI should read back and hash what it uploaded before the index commit lands.
8. **Signing that proves the wrong thing.** A GitHub-signed `createCommitOnBranch` commit proves GitHub acted for a token; a workflow attestation proves a workflow ran at a commit; neither proves the sha256 in the index matches the bytes on R2 — only `verify` does. Keep the three claims distinct in the docs.

### Flags on the decided shape

- **F1 — "R2 bucket lock" is detection-grade, not prevention-grade.** An indefinite rule can be removed by the account owner via dashboard, Wrangler or API, and the bucket can then be emptied. The shape should stop calling it WORM; its WORM property comes solely from the S3 compliance copy.
- **F2 — "Indefinite" compliance-mode retention does not exist on S3.** Compliance mode needs a retain-until date or a `Days`/`Years` default; the only open-ended lock is a legal hold, which is removable. Pick an explicit horizon (the API documents no maximum; the accepted upper bound was not tested — *not verified*) and record that account closure deletes everything after 90 days, so the compliance copy must sit in an account whose billing cannot lapse.
- **F3 — "Branch protection forbidding force-push" does not bind admins by default.** Enable the no-bypass setting or a ruleset with an empty bypass list, forbid deletion too, and accept that the people who can edit the rule can remove it: the real guarantee is external pinning of checkpoints by mirrors and verifiers (steal #1).
- **F4 — "Signed commits by CI" needs a stated signer.** Either `createCommitOnBranch` (GitHub-signed, no key to manage, proves GitHub-for-token) or a CI-held key; either way the signing policy must restrict pushes to that identity, because GitHub's "require signed commits" accepts any collaborator's valid signature.
- **F5 — git's SHA-1 is not the strong hash.** The commit chain detects casual rewriting; cryptographic strength must come from the sha256s inside the index and from the signed checkpoint naming the index tree. Do not describe the Ledger's history as "cryptographically verifiable for decades" on the strength of SHA-1 alone.
- **F6 — `verify` against "a named mirror" must download.** R2 exposes SHA-256 only as a composite multipart checksum and CRC-64 as full-object; a HEAD-based check proves a server's claim, not the bytes. Budget for full reads (zero-egress R2 makes this free from the primary).
- **F7 — The expendable archives are more expendable than their names suggest.** Software Heritage takes only source origins, skips files over 100 MiB, and has no loader for buckets or release assets; Zenodo caps records at 50 GB, lets owners edit for 30 days, and reserves CERN's right to delete; the Internet Archive lets uploaders delete at will. Use them for what they are good at — Software Heritage for the Ledger repository itself (which carries the index and build records), Zenodo for dated bundles of index plus binaries with DOIs — and store the DOIs and SWHIDs back in the index. Expect none of them to be the copy of last resort.
- **F8 — Withdrawal is unspecified.** Add the tombstone rule (steal #5) to the shape; without it the first legal takedown forces a choice between breaking Runs and lying in the index.
