How a figure is made

Nothing on this page is estimated. Each mark goes back through a Method to the Runs it summarises, and each Run to its evidence.

  1. Boot

    A fresh machine of each type, four times a day.

  2. Run
    6,335

    Every execution of a benchmark is kept as a Run, with what it printed and what was recorded about the machine. Failed Runs are kept and shown too.

  3. Series
    187

    The Runs of one benchmark, parameter set, build, instance type and Availability Zone ID.

  4. Method
    series v1

    Turns a Series' counted Runs into its percentiles. A new version of a Method is published beside the old one.

One Run, as its Series' file holds it

The first of the 33 Runs in the file of Lock and unlock a mutex on c8i.2xlarge, where one repetition is 10,000 critical sections, each a lock, an increment and an unlock. Its evidence is the Run file, which names the binary, the streams and the dumps by hash.

The evidence is served at the keys of LedgerMath's bucket of Runs, under the same address as the API: each point of a Series file links its Run file (evidence) and its boot's summary (boot_summary). A Run file names its binary, streams and dumps by hash, sha256:<hex>; each is a blob at blob_url_template with {hex} replaced by the 64 hex digits.

Method series v1, in the API's own words

time_per_repetition
Per Run: for each counted sample (warmup samples left out), sample_ended.t minus sample_started.t, divided by the sample's repetitions; the Run's number is the median of those (the mean of the two middle values when there is an even number of samples).
bytes_per_second
Per Run, where the benchmark observed bytes_per_repetition: bytes_per_repetition × 10^9 / the Run's time per repetition in nanoseconds.
percentiles
5th, 50th and 95th percentiles across the counted Runs of a Series, and of each group, by linear interpolation between closest ranks (R type 7): with n values sorted, h = (n − 1) × p / 100 and the percentile is x[⌊h⌋] + (h − ⌊h⌋) × (x[⌊h⌋+1] − x[⌊h⌋]). Each number's percentiles are taken over that number's values, so the bytes-per-second percentiles are not the time percentiles inverted.
counted
A Run counts when:
  • its binary exited 0
  • every stdout line is an event that matches the events schema
  • the stream obeys every order rule scripts/check-events.py checks:
    • started first and once (not a --quick stream)
    • finished last and once
    • samples numbered from 0
    • each closed by its own sample_ended before the next starts and never ending before it starts
    • observed keys once
    • exactly one verified
    • as many counted samples as the Run asked for
Any other Run is failed: shown, with the reasons, and in no percentile.

Method requests v1, for the S3 requests

Method series v1's Series: the Runs that share a benchmark, params, build, instance type and zone ID. A Series is this Method's when any of its Runs' streams holds a request (a response_ended or request_failed event carrying `request`); every Run of it is then shown, counted or not.
