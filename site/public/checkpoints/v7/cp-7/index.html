The Methods

A versioned Method turns a Series' Runs into its figures. Their definitions are published in v1/series.json, beside the figures they made.

series v1time per repetition, bytes per second, percentiles · 7 definitions
series
The Runs that share a benchmark, params, build, instance type and zone ID.
time_per_repetition
Per Run: for each counted sample (warmup samples left out), sample_ended.t minus sample_started.t, divided by the sample's repetitions; the Run's number is the median of those (the mean of the two middle values when there is an even number of samples).
bytes_per_second
Per Run, where the benchmark observed bytes_per_repetition: bytes_per_repetition × 10^9 / the Run's time per repetition in nanoseconds.
percentiles
5th, 50th and 95th percentiles across the counted Runs of a Series, and of each group, by linear interpolation between closest ranks (R type 7): with n values sorted, h = (n − 1) × p / 100 and the percentile is x[⌊h⌋] + (h − ⌊h⌋) × (x[⌊h⌋+1] − x[⌊h⌋]). Each number's percentiles are taken over that number's values, so the bytes-per-second percentiles are not the time percentiles inverted.
counted
A Run counts when its binary exited 0, every stdout line is an event that matches the events schema, and the stream obeys every order rule scripts/check-events.py checks: started first and once (not a --quick stream), finished last and once, samples numbered from 0, each closed by its own sample_ended before the next starts and never ending before it starts, observed keys once, exactly one verified, and as many counted samples as the Run asked for. Any other Run is failed: shown, with the reasons, and in no percentile.
groups
Within a Series, the Runs whose split facts are all equal make one group. Groups are lettered in the order each first appears, and may interleave in time. A dump section is compared whole, apart from the per-boot values listed as left out; a fact read from such a section is canonical-json-sha256:<hex>, the sha256 of what remains as JSON with keys sorted and no whitespace (lscpu's output is re-written that way too).
differed
For each pair of consecutive Runs in a Series, every split fact and every dump section of the before-dump whose hash changed, split on or not, with the top-level keys that changed for the sections that are read. Each changed section is marked: it splits, its change lies only in what is left out, or it is not split on.
requests v1Series whose Runs record requests: each request's phases · 13 definitions
series
Method series v1's Series: the Runs that share a benchmark, params, build, instance type and zone ID. A Series is this Method's when any of its Runs' streams holds a request (a response_ended or request_failed event carrying `request`); every Run of it is then shown, counted or not.
request
One counted sample of the stream (warmup false): the events from its sample_started to its sample_ended. Its phases are differences of event timestamps, in nanoseconds of the Run's clock (see phases). A request over a reused connection has only send, first_byte, headers, body and total.
succeeded
A request whose response status (response_headers.status) is 2xx and whose body matched the Fixture and S3's checksum (response_ended.fixture and .s3_checksum both "match"). Only succeeded requests are in a time.
failed
A counted request that holds a request_failed (counted by its phase and error) or whose status is not 2xx (phase response, kind status_<code>), or one of whose lines the binary withheld (phase record, kind line_withheld_<event>). Counted per Run and pooled; never in a time. The warmup request's failure and failed reused-connection setups (connection_failed, outside any sample) are counted apart.
per_run
For each phase of a counted Run: the count of its succeeded requests, the least and greatest time, and each percentile the count supports, exactly, by linear interpolation between closest ranks (R type 7): with n times sorted and h = (n − 1) × q / 1000 for the q-th per mille, x[⌊h⌋] + (h − ⌊h⌋) × (x[⌊h⌋+1] − x[⌊h⌋]).
support
The q-th per-mille percentile of n requests is reported only when n × (1000 − q) ≥ 1000: at least one request is expected above it. So the 50th needs 2, 90th needs 10, 95th needs 20, 99th needs 100, 99.9th needs 1000 requests. Beside each percentile reported, at_or_above is how many requests are ranked at or above it: n − ⌈h⌉ (ties counted by rank). For a 99th percentile of 200 requests that is 2.
histogram
Each phase's times are tallied in fixed bins, the same for every Run, so tallies add: below 128 ns every nanosecond is a bin of its own; from 128 ns each doubling [2^e, 2^(e+1)) is cut into 64 bins of width 2^(e−6): bin = 64 × (e − 5) + ⌊ns / 2^(e−6)⌋ − 64, with e = ⌊log2 ns⌋. A bin is at most 1/64 as wide as the least time in it.
pooled
Across the counted Runs of a Series, and of each group: the Runs' tallies summed. The count, least and greatest time are exact; each percentile is read from the sum by the same rule as per Run, with each ranked time taken as the middle of its bin (the time itself in a bin of width 1), held between the least and greatest, so it is within 0.78% of the exact percentile of the same requests. A Series with one Run therefore pools to figures within that of the Run's own.
through
On each Run of a Series, the pooled figures (without histograms) of the counted Runs that started at or before it, in the Series' time order; and of its group's, when the Series has more than one group. A citation of the Series as of a Run's start is checked against these.
breakdown
The pooled figures again for the requests that had each value of a fact each request records of its connection or of itself (see request_facts), for every fact that took more than one value among the pool's succeeded requests.
recorded
What a Series' Runs record beside their requests, for a reader: the box's Region (provider.region), the Service each Run names and its inputs that are not secret, as delivered (Run.service), and in each pool every value each request fact took. Words, not figures, and nothing about the path between the box and the server, which each Run's environment dumps record (network, ec2_route_tables, ec2_vpc_endpoints).
groups
Method series v1's groups: within a Series, the Runs whose split facts are all equal, lettered in the order each first appears; the same letters series v1 gives the same Runs.
counted
A Run counts when its binary exited 0 or 4 (4: the Run completed and holds at least one failed request), every stdout line is an event that matches the events schema and the stream obeys every order rule of scripts/check-events.py, the stream has as many counted samples as the Run asked for (fewer: the Run was cut short), every timestamp is a whole number a JavaScript number holds exactly (at most 2^53 − 1), every request in it reads as the binary's README says (every event naming a request names its sample's; a complete response's events in their order on one open connection, each phase at least 0, sample_ended at the clock read that ended the request; a failed request's events, before its request_failed, the start of that order up to where its phase says it got), and an exit 0 has no failed request, no failed warmup request and no failed setup of a kept connection. Any other Run is failed: shown, with the reasons, and in no figure. A counted Run's failed requests are counted; its succeeded requests are in the figures.

The API, in its own words LedgerMath runs small benchmarks on real AWS machines several times a day and keeps every execution as a Run. A Series is the Runs of one benchmark, parameter set, build, instance type and Availability Zone ID; a versioned Method turns its Runs into a Derivation. This is version 1 of the data API: static JSON files cut from the Derivations and the daily price files, each kind with a JSON schema.
